# NovaLoc 新译

> 把任意游戏翻译成中文 —— 包括**贴图里的文字** —— 并且保证游戏内**不出现口口口**。

NovaLoc 是一个**完全离线**的游戏汉化工具。它把三类文本都翻译成中文：

| 类型 | 举例 | 处理方式 |
|---|---|---|
| **结构化文本** | 对白、道具名、任务、界面标签 | 解析引擎的数据文件，原地改写 |
| **脚本文本** | Ren'Py 的 `.rpy`、Unity 的文本资源 | 按语法定位字符串字面量 |
| **贴图文本** | 标题画面、按钮、Logo、UI 底图上的字 | OCR 识别 → 去字 → **用真实中文字体重绘** |

## v1.2.0 实测指标

### 一行命令汉化整个游戏库

```bash
novaloc auto "E:\你的游戏库"            # 逐个游戏：识别引擎 → 跳过中文 → 翻译 → 就地写回
novaloc auto "E:\你的游戏库" --watch    # 守望模式：后续新增的游戏也会自动处理
novaloc auto "E:\你的游戏库" --dry-run  # 先看会处理哪些
```

**实测**在该库（193 个游戏目录）上：待处理 **175**、已是中文跳过 **18**、
识别失败 **0**。引擎分布 unity 105 / rpgmaker 40 / loose 26 / unknown 4。

写回是**不可逆**操作，所以三条硬约束都有测试守住：
**写回前必备份**（数据根下 `_novaloc_backup/<游戏>-<时间戳>/`）、
**只回写真的变了的文件**（`out/` 是整份游戏副本含 .exe/.dll，
整目录覆盖会重写几百个二进制文件）、
**绝不按 mtime 判断"变了"**（`unpack` 会刷新 mtime，按时间比会让每个文件
都算变了）。想自己验收就加 `--no-write-back`。

> **Unity 的边界（如实说明）**：库里 105 个是 Unity，而 Unity 没有统一的
> 文本存放位置。`.assets` 序列化资源里的字符串**现在支持了** ——
> 用「原地等长改写」：文件总大小与内部偏移都不变，写回原值可逐字节还原
> （实测 36 MB 的真实游戏资源：区间外改动 **0 字节**、还原后 sha256 相同）。
> 代价是**译文必须不超过原文字节数**，装不下的条目会**保留原文并如实上报**，
> **绝不截断**。仍未支持的是 **AssetBundle（`.bundle`/`.unity3d`）未解包**
> 与 **文字画在贴图里的纯图游戏** —— 报告里会明确写出并给出下一步指引，
> **不会静默假装成功**。

### 一个必须说清的缺陷：约 10% 的"成功"译文缺内容

对 5,224 条**已判成功**的译文做质量审计，按**句子数**比对发现
**480 条（9.2%）**的译文句数少于源文。丢的常常是**玩法规则**：

```
Add 4 cards from the deck to hand. Then, randomly discard 2 cards.
  → 加入 4 张牌。                    ← 丢掉"随机弃 2 张"
Guaranteed escape from battle. Cannot be used on Area Bosses.
  → 保证在战斗中脱离。               ← 丢掉使用限制
```

**已排除最危险的可能**：在整份译文表里反查"这段译文是不是别的条目的" ——
106 条疑似里 **0 条是串条目**，所以**不是对齐 bug**，是模型自身问题。

**试过并否掉的三条路**：按换行逐行重译（12 条只救回 4 条 = 33%）；
再细一级按句末标点逐段翻译（**0/12**，碎片会让模型返回 `{}` 或垃圾）；
换模型（同一批 16 条上，两个 7B 只多保住 2 条，代价是**新增硬失败** ——
空译文/抛错从 0 变成 1，而 `qwen3-vl:4b` 做纯文本翻译 **16/16 全失败**）。

**已做的改进**：新增句子数守卫，但**只报不拦**。为什么不能拦 —— 人工抽查
发现开火样本**大部分是假阳性**（"语气词被合并"的风格差异，内容其实完整，
如 `「Sigh... Whatever, let's go...」→ 唉… 不管怎样，走吧…`），而且试过用
长度比把真丢与假阳性分开，**分不开**（风格性合并 0.28~0.56、真丢 0.10~0.22，
**区间重叠**）。设成致命会把几百条**正确**译文退回英文，比偶尔少译一句更糟。

**正确期待**：翻完**大部分可用**，约 **10% 的条目需要人工复核**。
这条守卫还**漏报**：句数相等但内容不全的（`Halve Damage → 半身防御`）抓不住。

### v1.1.0 修了什么（建议升级）

**1. 单条请求收到"多段 JSON"时整条译文被静默丢弃。** 模型对**单条**
文本会回**批格式**的多段答案（`{"0": …, "1": …}`），旧代码在
`len(parts) > 1` 处直接报「结果不是字符串」，**整条丢掉并保留原文**，
还不报错 —— 实测多行条目 **76/76** 都触发这条路径。

第一版修法（`"\n".join` 拼接）**是错的**：实测约 2/3 的第二段是**同一
句话的另一个措辞**而非续写，拼出来就是复读。用 bigram 覆盖率区分
"复读"与"互补"**实测不可行**（复读型 0.38–0.90、互补型 0.00–0.57，
**区间重叠**，没有阈值能分开）。最终用**无阈值**的优先级：
**占位符丢得最少 → 含换行 → 编号最小（段 0）**。

**2. 多行条目判死后逐行重译（新增）。** 多行条目失败率约 **48%**，
是全量失败率（1.5%）的三十多倍。已用实测**否掉**两个方向：

* **改判据**不行 —— 丢换行记号里混着"两行并成一行、内容完整"与
  "真的丢了第二行"两种，而现有校验对**两者都返回通过**
  （它比内容重叠，丢掉的第二行在还原前后都没有，于是"相等"）。
  **换行记号是唯一能抓住"少翻一行"的信号。**
* **换模型**不行 —— 同一批 24 条真实多行条目上，`translategemma:4b`
  成功 **16/24**，两个专精翻译的 7B（含腾讯混元翻译）都只有 **14/24**，
  行结构完整度更低（0.62 / 0.71 vs **1.00**）、慢 **5~12 倍**。

所以改成**改任务形态**：模型一次面对多行才有合并/截断的机会，
那就逐行送翻。实测（40 条真实失败条目）**救回 21 条 = 52%**，
且原通过的条目**一条都没被改动**（有对照断言守住）。

**3. 回写阶段"零译文"时静默报成功（最危险）。** 真实踩过：手工删掉
`translations/entries.jsonl` 后重跑，输出 `回写 0 条文本` +
`✅ 已写入 2 个文件` + `🎉 全部完成` —— **报告全绿，游戏里一个字都没翻**。
现在这种情况**直接中止**并说明原因（零假阳性：真不需要翻译时
`units` 本身就是空的）。

另外修掉：掩码记号查询返回"裸下标"而非完整记号；模型把提示词规则
**连同原文一起回吐**（内含未转义真实换行）时 JSON 解析整体失败并给出
**误导性**报错；`units.jsonl` 里无法解析的行现在会留下痕迹。

### v1.0.1 修了什么

**多行条目会静默丢内容** —— RPG Maker 有大量对话是"一条台词被引擎
按显示宽度切成多个指令"，而模型会**看着换行自己切条**：它把同一条目里的
换行当成多个条目，于是编号错位、一条 3 行的台词只翻出第 1 行。
两种都**通顺、长度比也不越界**，所有检查全绿。

修法是把换行也当占位符屏蔽（`translate.mask_newlines`），
模型眼里每条只剩一行。实测内容完整度：

| 模型 | 修前 | 修后 |
|---|---|---|
| `translategemma:4b` | 0.33~0.70 | **0.87** |
| `HY-MT1.5-7B` | 0.75~0.94（5 条空译文） | **1.03（0 条空）** |

同时新增「提示词回声」守卫（模型把翻译要求当内容复述，
36 条实测 2 条命中；判据在真实译文上 0 误报）、
修掉两个潜伏的 `AttributeError` / 死代码判据、
新增 **RPG Maker VX Ace / VX / XP** 引擎、
新增 **`novaloc review`** 接触印样（把待复核贴图拼成一张大图）。

### 已知限制（如实说明，v1.1.0 未解决）

* **逐行送翻时会漏进原文的拉丁词**：实测 `translategemma:4b` 吐出过
  `「邪恶之 bane」`（原词 `bane` 泄漏）。现有守卫**抓不住**这种泄漏
  （既不是异体字脚本，也不触发重复/长度判据）。属于**质量瑕疵而非
  静默丢内容**，仍需人工审校。
* **Unity `.assets` 里的字符串：支持但有硬约束**。用「原地等长改写」
  （文件大小与内部偏移不变，可逐字节还原）。**译文超过原文字节数的条目
  会被跳过并如实上报**，保留原文 —— 这是有意的：截断会静默丢内容。
  实测抽样里约 20%~30% 的对白因放不下而未改写，用户需要知道这个比例。
* **AssetBundle（`.bundle`/`.unity3d`）未解包**，其中的文本读不到。
  可用 UABEA / AssetStudio 解包后走散装文件模式。
* **纯图游戏**（文字画在贴图里、资源里几乎没有字符串）：实测 `AliQ`
  613 MB 资源里只有约 13 句英文。这类要走贴图汉化流程，
  但若游戏用非标准图集，`scan --images` 可能报 0 张（已知缺口）。
* **TMP 静态图集重烘焙**（`m_AtlasPopulationMode = Static`）未实现。
  实测所用的真实 Unity 游戏**没有 TMP**（走传统 uGUI），所以对它是
  无关的，但仍是其它 Unity 游戏的缺口。
* **`units.jsonl` 过期检测**未做：实测因此出现过 **1,343 vs 6,758**
  的分母错误（差 5,415 条剧情对白），所有覆盖率数字都受影响。

## 为什么值得用

### 1. 贴图文字不靠生成模型"画"出来

很多同类工具用图像生成模型把英文"重画"成中文。**这条路不可靠**：
生成模型不保证笔画正确，也不需要真的存在这个字，
结果就是"看起来像中文但其实是错字"，而且尺寸、字重、描边每次都不一样。

NovaLoc 走的是另一条路：

```
OCR 识别出文字和它的四边形位置
   ↓
把原文字擦掉（inpaint：纯色区直接填充，复杂背景用 Telea/NS 算法修补）
   ↓
从原图采样前景色/背景色/描边，用**真实的中文字体文件**渲染译文
   ↓
按原文字的四边形做单应变换贴回（支持旋转、倾斜的文字）
```

因为是真实字体渲染，**笔画一定是对的**，而且颜色、描边、
倾斜角度都跟着原图走。代价是它不能"无中生有"地模仿特殊美术字，
但这是正确的取舍：**宁可风格略有差异，也不能画出错字。**

### 2. "不出乱码"是被硬保证的，不是"尽量"

游戏里出现 `口口口` 的根本原因是**字体缺字形**。
NovaLoc 把这个环节做成了一道**必须先通过的检查**：

1. 翻译完成后，先算出**这个项目实际会用到哪些字符**（汉字 + 标点 + 符号 + 原文里保留的字符）；
2. 逐个审计游戏自带字体，算出**具体缺哪几个字**；
3. 缺字就**注入字形**（把候选字体的对应字形合并进原字体，保留原字体的风格）；
4. 合并后再**验证一遍**：每个字符都要能在 cmap 里找到、能渲染出墨迹、
   不能是 `.notdef`、不能有重复 glyph id；
5. **只要有任何字符补不上，就硬失败并中止**，绝不输出一个会显示口口口的游戏。

最后一步尤其重要。多数工具会"尽力而为"然后交付，
用户装完游戏跑起来才发现某个界面全是方块。NovaLoc 的选择是：
**在能保证之前不交付。**

> 关于"为什么没有一个字体能搞定"
>
> 我们实测过常见字体对游戏文本的覆盖：SimHei 缺 `¶†‡•‹›↔↕♪♫✓✔✕✖❤`；
> 微软雅黑/等线/SimSun 同样缺 `↔↕♪♫✓✔✕✖❤`；`seguisym.ttf` 能覆盖 92.6% 的
> 符号但**一个汉字都没有**；霞鹜新晰黑汉字全覆盖却缺 `✔✕✖❤`。
> 所以**多字体贪心合并是必需的**，不是优化项。

### 3. 完全离线

翻译、OCR、图像处理全部在本机跑。没有 API Key，没有用量限制，
不会把你的游戏文本发到任何服务器。用 DirectML 走 GPU 加速。

实测性能（RTX 4060 Laptop，PP-OCRv6 medium）：

| 后端 | 720×300 一张图 |
|---|---|
| CPU | 23954 ms |
| **DirectML** | **284 ms** |

**84 倍差距**，所以 DirectML 是默认且必需的路径。

### 4. 原游戏目录永远只读

所有操作在独立的工作区里进行，产物写到 `out/`。
你不会因为工具跑了一半而毁掉原游戏。

### 关于 Unity 的诚实说明

Unity 没有统一的文本存放位置，文本可能在 `.assets` 二进制、
AssetBundle，甚至编译进 `Assembly-CSharp.dll`。

#### `.assets` 里的字符串：**支持**（原地等长改写）

旧版本这里写的是"我们不会去盲写这些二进制格式"。**这个结论一半对、
一半错** —— 实测把两种写法分开了：

| 写法 | 实测 | 结论 |
|---|---|---|
| 让资源库**重建**整个文件（UnityPy `save()`） | 66 KB 存回去只剩 **5.8 KB**，写回原值也**无法还原** | ❌ 会毁游戏 |
| **原地等长替换** | 36 MB 改 1,874 处：大小不变、区间外 **0 字节**、写回原值**逐字节相同** | ✅ 采用 |

原理：Unity 的序列化字符串是 ``<4字节长度><UTF-8 字节><0..3 对齐零>``。
只要译文**不超过原文字节数**，就能保持文件总大小与**所有内部偏移**不变，
只改那 4+N 个字节。

**代价与如实上报**：容量 = 原文英文字节数（4 字节对齐），所以"装得下"
等价于"中文不超过英文"。实测 EN→ZH 的字节比通常在 0.35~0.46，**大部分
装得下**；装不下的条目会**保留原文**并在报告里写明
"**N 处因原文空间不足未改写**"。

> **绝不截断。** 截断会让用户看到"翻译成功了"而内容其实少了一半 ——
> 这是本项目最危险的失效形态。宁可如实报告一部分没做到。

真实游戏实测（`ButtKnight`，2.4 GB）：抽取 **34,650 条**、其中 `.assets`
内可改写 **34,328 条**、真实对白候选 **771 条**；回写后文件大小不变、
区间外 **0 字节**、还原后 sha256 与原始相同。

#### 仍未做的：AssetBundle 与纯图游戏

```bash
novaloc unity-strings "D:\Games\SomeUnityGame"
```

这条命令**只读**扫描 `*_Data` 下的序列化资源（`level*`、`*.assets`），
把里面的候选文案连**文件名和偏移量**一起导成 CSV：

```csv
file,offset,confidence,reason,source,target
level0,1006896,0.85,多词文本,Would you like to save?,
level0,1103064,0.85,多词文本,"Quit to the Main Menu. \nAny unsaved progress will be lost.",
```

这份清单现在的定位是**审计与兜底**：核对工具打算改哪些字符串，
以及把**未解包的 AssetBundle**、**装不下的长句**交给
[UABEA](https://github.com/nesrak1/UABEA) 或
[AssetStudio](https://github.com/Perfare/AssetStudio) 处理。

实测一个真实 Unity 游戏（1329 MB 资源）：提出 **281 条**去重候选，
包含全部 UI 文案（`Would you like to save?`、
`Select Location to Teleport.`、`THANK YOU FOR YOUR SUPPORT!`）、
菜单/状态词（`Options`、`Status`）和贴图上的日文技能名。

**精度是有限的、而且是刻意偏保守的。** 同一个游戏里还有大量
动画状态名和资源名（`AdvanceFront`、`Tile_4_Bottom`），
它们**不在**清单里 —— 但清单里仍有约三成是引擎符号。
理由见下一节。

#### 为什么宁可混进噪音，也不从严

早先的版本判据很严，只报 28 条 —— **看着干净，但把
`Options`、`Game Over`、`Save Game` 这类最常见的菜单文案全漏了**。

这件事的代价不对称：

* 多收几条噪音 ⇒ 人扫一眼就能剔掉；
* 漏掉按钮文案 ⇒ 用户以为"这工具没找到东西"，然后放弃。

所以判据**偏保守**：先保证真实文案不漏，再尽量减少噪音。
排掉噪音的手段是**形态判据**（资源名分隔符 `--`/`__`、
PascalCase 的类名），不是"猜哪些词不算文案" ——
形态判据对**没见过的**资源名同样有效，黑名单不行。

**已知取舍**：`Main Texture`、`Normal Map` 这类资源名**会**通过筛选。
这是有意的 —— 多收噪声用户能一眼扫掉，漏掉真台词则会让用户以为工具没用。
真正被形态判据挡住的是路径/代码式的（`Hidden/Universal...`、
`_MainTex`、`UnityEngine.*`）。

#### 未解包的 AssetBundle

用 [UABEA](https://github.com/nesrak1/UABEA) 或
[AssetStudio](https://github.com/Perfare/AssetStudio) 把 AssetBundle
**解包**成普通文件，再用 NovaLoc 的**散装文件模式**处理。
NovaLoc 在扫描 Unity 工程时会明确告诉你检测到了多少个未解包的包 ——
而不是假装全都翻好了。

#### Unity 的字体这道坎（必须知道）

Unity 的界面文字几乎都走 **TextMeshPro**，而 TMP 渲染用的是
**预先烘焙好的图集**（`m_AtlasTextures` 指向一张贴图，字形是那张贴图上的
位图块）。这意味着：

> **只替换 TTF 字体文件对已经烘焙好的 TMP 资源没有任何影响。**
> 游戏根本不会去读那个 TTF。

要真正让中文出现，必须**重新烘焙图集**，而那需要解析
`TMP_FontAsset` 的序列化格式、按原有字号重新光栅化字形、
重算 `m_GlyphTable` / `m_CharacterTable` / `m_FaceInfo`，
并且必须用 Unity 自身的排版度量才能和游戏完全一致。
**这是一个独立的大工程，本版本没有实现。**

所以 NovaLoc 在 Unity 上做的是"把能做的做到位 + 把做不到的说清楚"：

1. 把补好的字体复制到 `*_Data/StreamingAssets/_novaloc_fonts/`
   （`StreamingAssets` 会被原样打进构建，是运行时最可能被读到的位置）；
2. 检测工程里有没有 TMP 字体资源，有就明确告诉你**需要重新烘焙**，
   并给出用 Unity 编辑器 Font Asset Creator 的具体步骤；
3. 绝不假装已经修好 —— **虚假的成功比明确的失败更浪费时间。**

有一个真实存在的例外：如果游戏用的是**动态（Dynamic）** TMP 字体资源
（`m_AtlasPopulationMode` 为 `Dynamic`），它运行时会按需把字形加进图集，
此时替换 `StreamingAssets` 里的字体**是有效的**。NovaLoc 会提示你先试这一条。

RPG Maker 与 Ren'Py 没有这个问题 —— 它们直接读字体文件，
所以这两个引擎上的"不出现口口口"是**完全被保证的**。

## 安装

### 环境要求

- Windows 10/11（其他平台可用，但 DirectML 加速仅 Windows）
- Python 3.11+
- 建议 NVIDIA 显卡（走 DirectML）；CPU 也能跑，只是慢很多
- 磁盘空间：模型约 200 MB，工作区按游戏大小而定（建议放非系统盘）

### 步骤

**推荐：用一键脚本**（自动建虚拟环境、装依赖、跑自检）

```powershell
git clone https://github.com/starchfurrycon/NovaLoc.git novaloc
cd novaloc
.\scripts\setup.ps1
```

**手动安装：**

```powershell
git clone https://github.com/starchfurrycon/NovaLoc.git novaloc
cd novaloc

python -m venv .venv
.\.venv\Scripts\Activate.ps1

# dml = DirectML GPU 加速（快 84 倍）；ocr = PP-OCRv6 文字识别
# **两个都不能省**：只装 dml 的话能翻译文本，但贴图文字识别不了。
pip install -e ".[dml,ocr]"

novaloc doctor      # 检查环境，会告诉你缺什么
```

> 关于 `onnxruntime`：本项目**不在基础依赖里**声明它，因为它和
> `onnxruntime-directml` 提供同一个包名，一起装会让 DirectML
> 静默消失、速度退回 CPU（慢 84 倍）。所以必须用 `dml` / `gpu` / `cpu`
> 三个 extra **三选一**显式指定。
>
> 关于 `opencv`：`rapidocr` 会带入 `opencv-python`（带 GUI 的那个）。
> 代码里没有用到任何 GUI 函数，所以功能上没问题；如果你在无桌面环境
> 部署、想把 GUI 依赖也去掉，可以卸掉 `opencv-python` 后单独装
> `opencv-python-headless`（注意不要再让 rapidocr 把 GUI 版装回来）。

### 还需要准备的两样

上面只装了 **NovaLoc 自己**。要完整跑通还需要：

1. **Ollama + 翻译模型**（本地推理运行时）
   ```powershell
   novaloc ollama status     # 看是否已装/已启动
   novaloc ollama pull       # 拉取推荐模型（约 4 GB）
   ```
2. **OCR 模型**（PP-OCRv6，约 140 MB）—— 首次运行识别贴图时自动下载，
   也可以提前下好；`novaloc doctor` 会告诉你缺哪个、该放哪里。
   > 模型缺失时自检会**明确报不可用**，不会假装就绪然后联网下载。

3. **韩语 / 俄语等语言的识别模型**（可选，约 8–14 MB）—— 按需下载。

   PP-OCRv6 的识别器覆盖中/繁/英/日 + 46 种拉丁字母语言，但
   **不含韩语，也不含任何西里尔文字（俄语等）**。对这类语言它不是
   "读得差"，而是**识别结果为空** —— 而这与"这张图本来没有文字"
   在结果上完全一样，属于最难排查的一类问题。

   工具会自动按源语言切换识别模型（检测仍用 PP-OCRv6）：

   | 源语言 | 识别模型 | 大小 |
   | --- | --- | --- |
   | 中文/日文/英文/拉丁语系 | PP-OCRv6 multi | 已含 |
   | 韩语 | PP-OCRv5 korean | 13.5 MB |
   | 俄语/白俄/乌克兰 | PP-OCRv5 eslav | 7.9 MB |
   | 其他西里尔（保/塞/马其顿） | PP-OCRv5 cyrillic | 8.1 MB |

   语种默认跟随 `translate.source_lang`；想手动指定就设 `ocr.lang`。
   完全离线时把 `ocr.allow_model_download` 设为 `false` ——
   缺模型会给出带下载链接的明确错误，而不是静默读成空串。

```powershell
novaloc doctor      # 这一步应显示"一切就绪"
```

## 使用

### 图形界面（推荐）

```powershell
novaloc serve
```

浏览器会自动打开，默认地址是 **http://127.0.0.1:8791**
（即配置里的 `ui.host` / `ui.port`）。想换端口：

```powershell
novaloc serve --port 9000
```

> 注意：`scripts/dev.ps1`（前端开发模式）用的是 **8000** 端口，
> 因为 `web/vite.config.ts` 把 `/api` 与 `/ws` 代理到 8000。
> 日常使用不需要 Node，用上面的 8791 即可 —— 前端构建产物已随包提供。

### 命令行

```powershell
# 1. 看引擎识别结果
novaloc scan "D:\Games\SomeGame"

# 2. 建项目
novaloc project new --name "某游戏" --game "D:\Games\SomeGame"

# 3. 跑完整流程（识别→抽取→翻译→字体→贴图→质检→回写）
novaloc run <项目id>

# 4. 看质检报告
novaloc qa <项目id>
```

产物在 `novaloc project show <id>` 显示的 `out_dir` 里。
**直接玩 `out/` 目录**，不要覆盖原游戏。

### 分阶段跑（推荐大项目这样用）

```powershell
novaloc run <id> --stage extract
novaloc run <id> --stage translate     # 最耗时的一步
novaloc text export <id> --format csv --out 译文.csv   # 导出人工校对
novaloc text import <id> --file 译文.csv               # 改完导回
novaloc run <id> --stage fonts
novaloc run <id> --stage images_localize
novaloc run <id> --stage qa
novaloc run <id> --stage apply
```

每个阶段都是幂等的，可以反复重跑。改了译文只重跑 `fonts` 之后的步骤即可。

## 字体与授权

**默认不随工具分发任何字体文件。** 工具在本地渲染贴图、生成字体补丁，
交付的是**产物**而不是字体本身。

自动下载仅限可再分发的字体（`OFL-1.1` / `Apache-2.0` / `MIT` / 公有领域）。
系统字体（微软雅黑、黑体、宋体等）**只在本机已安装时使用，绝不自动下载**。

`novaloc fonts list` 会显示每个字体的授权与 `bundle_ok` 标记。

## 已知限制

- **贴图文字必须是"能识别的印刷体"**。手写体、极度装饰化的美术字
  OCR 会失败；这种情况下工具会保留原图并在报告里标出来，不会乱画。
- **复杂背景的去字依赖 LaMa**（可选，需要 torch）。没装 torch 时
  退化为纯色填充 / Telea 修补，在渐变或照片背景上会留痕。
- **Unity `.assets` 字符串是"原地等长改写"**：文件大小与内部偏移不变、
  可逐字节还原，**但译文不能超过原文字节数**。超出的条目会保留原文并
  在报告里写明数量（实测抽样里约 20%~30% 的对白会遇到）。
  **绝不截断** —— 这是有意的取舍。
- **Unity 的 AssetBundle（`.bundle`/`.unity3d`）未解包**，其中的文本读不到，
  报告里会明确写出。可用 UABEA / AssetStudio 解包后走散装文件模式。
- **Unity 的候选清单精度有限，且刻意偏保守。** 实测 281 条里
  约七成是真实文案，其余是引擎符号（动画状态名、资源名），
  需要人工扫一眼。这是**有意的取舍**：从严会让
  `Options`/`Game Over` 这类最常见的菜单文案一起消失，
  而漏掉按钮文案比混进噪音代价大得多。
- **`Assembly-CSharp.dll` 里的字符串常量不支持** —— 那是编译产物，
  要改得反编译重打包，超出本工具范围。
- **只有 `.rpyc` 没有 `.rpy` 的 Ren'Py 发行版无法处理** —— 编译产物
  改了游戏也不认。工具会明确报告而不是假装成功。
- OCR 会把紧凑的英文标题切碎（例如 `NEW GAME` 可能被切成 `NEW` 和 `V GAME`）。
  译文长度与分块是按识别结果处理的，个别情况下需要人工在贴图审校页调整。
- **极少数条目翻译不了，会被明确标成 `failed` 而不是硬塞一个坏译文。**
  实测 29,792 条里剩 32 条（0.11%），成因是模型自身的行为而不是流水线：
  拒答、返回空响应、或**对多行原文只翻一部分**。
  `novaloc qa` 与文本审校页会把这些列出来供人工处理；
  **宁可少一句，也不给玩家看一句乱的。**
- **游戏内消息变量（RPG Maker 的 `%1` `%2`）模型保不住全部。**
  这两个记号运行时会被替换成**行动者名字**与**目标名字**，
  丢了它玩家就看到"攻击！"而不知道是谁在攻击。
  实测 357 条这类文本里模型能保住约 **2/3**（改写提示词、换模型都试过，
  见 `tests/README.md` 第 36、37 条）。
  **保不住的会被 `apply` 拒绝回写并标成 `failed`** ——
  宁可让这一句留在原文，也不让游戏里出现一句说不清的话。
  最终产物里 **357/357 全部变量齐全**（不合格的 113 条一条都没写进去）。
