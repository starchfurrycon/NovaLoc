### 6.2 逐文件备份核对（这是本节的核心结论）

用 `.scratch/_e2e_auto_verify.py` 做**逐文件**核对，而不是
"备份里存在某个同哈希文件就算过"（后者太弱：1 个匹配就能让断言通过，
即使另外 60 个被改的文件根本没备份）。写回是**不可逆**操作，
断言必须与实际改动**一一对应**：

```
=== 文件变化 ===
   未变 4058   改了 61   新增 4   删除 0
=== 备份核对（逐文件）===
   备份根下有 2 个目录
   被改文件 61 个：有备份 61，**无备份** 0
=== 判定 ===
   ✅ 就地写回生效（61 个文件），且每个都有可回滚备份
```

* **就地写回生效**：测试库里有 **65 个文件被就地改写**（61 个内容变化的
  `.json` + 字体等产物）；
* **每一个被改文件都能回滚**：备份里存在与"改动前 SHA256"**完全一致**的副本；
* rpgmaker 的 `.json` 大小**允许变化**（不是 Unity 那种等长约束），
  实测 61 个里有 61 个大小变了 —— 这是预期。

### 6.3 ★ 这一步先暴露的是**我自己验证脚本的 bug**

第一次跑核对时输出的是：

```
被改文件 61 个：有备份 0，**无备份** 61
   ✗ 有 61 个被改文件**没有**对应的改动前备份 —— 不可回滚
```

看着像**严重产品缺陷**（61 个文件全不可回滚）。但去翻备份目录：

```
[dir]  \www
[dir]  \www\data
[file] \www\data\Actors.json  7614B   ← 与改动前字节数一致
```

**备份一直都在，而且是对的。** 问题在路径拼接：

| | 路径形态 |
| --- | --- |
| 备份里的 | **游戏根相对**：`www\data\Actors.json` |
| 快照的 key | **库根相对**：`Dungeon And Darkness-Steam\www\data\Actors.json` |

脚本只试了后者，于是**每一个**文件都判成"无备份"。
修法是两种都试（先原样，再去掉库根那一段游戏名）。

教训：**"断言失败"和"产品有问题"是两件事** ——
一个全量失败的断言，先怀疑断言本身（这里是 61/61 全红，
"每个都错"本身就是断言写错的强信号）。


**注意 `已是中文 1` 与 `[1/1]`**：上一轮已经汉化过的
`Dungeon And Darkness-Steam` 这次**被识别为"已是中文"并跳过**，

1. **重跑是幂等的** —— 不会把已经汉化过的游戏再翻一遍（那样会

2. **`auto` 的"新加游戏"路径是真的** —— 它按**当前库内容**决定
   待处理集合，而不是靠一份需要手工维护的清单。

⚠️ 边界：这证明的是"跳过已完成的游戏"，**不是**"能正确处理
半个游戏被汉化过的情况"（那种情况本轮没构造）。

### 6.6 ★ 怎么判断一次 `auto` 是"在干活"还是"卡死了"

这一节是**踩坑换来的**，写给以后盯长跑的人（也是写给我自己）。

#### 6.6.1 只看 stdout 会把整段翻译误判成"卡死"

`auto` 的 stdout 在那 12 分钟里**一个字都没有**（翻译阶段只在
`stage_end` 才打印一行）。我第一次据此判断"卡死了"，**判断是错的** ——
同一时间的 stderr 里，翻译**正在持续重试**：

```
批 0（1 条）第 1 次失败：…
批 0（1 条）第 2 次失败：…
批 0（1 条）第 3 次失败：…
```

**静默 ≠ 无进展。** 异常走 stderr，进展走 stdout，**两条都要读**。

#### 6.6.2 那么什么才是"真卡死"的判据

一次**真卡死**同时满足下面几条（这是实测抓到的那次）：

| 观测 | 卡死时的值 | 正常翻译时的值 |
| --- | --- | --- |
| 被测进程 **ΔCPU**（10~15 秒窗口） | **0s** | 有小幅增长 |
| Ollama 进程 **ΔCPU** | **0s** | 明显增长 |
| 到 Ollama 的连接 | `Established` | `Established` |
| **stdout 与 stderr 的表观时间戳** | 都不动 | **至少有一个在动** |
| 模型在 Ollama 里的到期时间 | 逼近当前时刻（已空闲） | 被不断续期 |

**只看连接状态会误判**：两种情况都是 `Established`。

#### 6.6.3 不要拿中间产物的行数当进度

`entries.jsonl` 的行数我实测读到过：

```
1589/2669   →   1030/1421   →   1589/3043
```

看着像"分母在变、甚至变小"。**但那是口径错误**，不是文件怪异：

* `extracted/units.jsonl` = **3043 个单位**，21:51:20 一次写完，之后不变；
* `translations/entries.jsonl` = **条目**，在翻译过程中**逐批创建**，
  一直增长（实测 45 秒 +17）。

所以分母本来就该单调增长——它表示"**已产出**的条目数"，
**不是总条目数**。而 2669 → 1421 那种"变小"，是因为那是
**另一次运行**留下的文件（同一个游戏跑过好几轮，工作区目录不同），
我把不同工作区的数字当成了同一条时间线。

⚠️ 我一开始把这个现象解释成"文件由不同阶段先后写入"——
**那是我编的**（当时没去看工作区）。教训与 §3.5.1 那两个
凭印象的结论一样：**看起来合理 ≠ 量过**。

判活顺序应当是：**ΔCPU → 连接状态 → stdout 和 stderr → 最后才是中间产物**。

### 7.2 逐文件核对（**不只看报告，直接比文件**）

对备份目录里的**每一个**文件，与游戏目录里的同名文件比对：

| 判据 | 结果 |
| --- | --- |
| 备份里有、游戏目录里也有 | **126 / 126**（无缺失） |
| 内容**不同**（= 确实被就地改写） | **126** |
| 备份路径与游戏目录**一一对应** | ✅ 缺失 0 |
| 文本文件里**日文假名**：备份多于现文件 | **20** |
| 文本文件里日文假名：备份**少于**现文件 | **0** |

最后两行是关键：**"备份 `!=` 现文件"不能证明备份是原始内容**
（也可能两边都改了）。所以额外比了**日文假名数量** ——
备份里假名显著更多、现文件里汉字显著更多，双向都指向
"备份 = 改动前的原文，现文件 = 译后的中文"：

| 文件 | 备份（原始） | 现文件（已汉化） |
| --- | --- | --- |
| `data\Actors.json` | 汉字 44 / 假名 93 | 汉字 **102** / 假名 **10** |
| `data\Armors.json` | 汉字 774 / 假名 1183 | 汉字 **1262** / 假名 **135** |
| `data\CommonEvents.json` | 汉字 13356 / 假名 21942 | 汉字 **30639** / 假名 21522 |
| `data\Items.json` | 汉字 113 / 假名 279 | 汉字 **222** / 假名 **63** |

⇒ **目标 (3) 的"就地写回 + 备份可回滚"成立。**

⚠️ 数字口径：`auto` 报告 **129** 个文件，备份目录里可核对到 **126** 个。
差 **3** 个我**没有**解释清楚（可能是目录项、或清单与落盘口径不同）。
**不假装它们一致** —— 但 126 个全部通过上面的核对，
且没有"备份里有而游戏目录里没有"的情况。

### 7.3 ★ 同时必须说清的质量代价（不能只报好消息）

同一次运行里 **1480 / 3043 = 48.6% 的条目 `failed`**，其中
**1375 条集中在 `data\CommonEvents.json`**（剧情对话）。

看上面的表就能发现迹象：`CommonEvents.json` 的假名从 21942 只降到
21522 —— **绝大部分日文对话没被替换**。这不是"写得不好"，
而是**根本没写进去**（`failed` 条目 `target` 为空，回写时保留原文）。

机制与下一步见 `ROADMAP.md` #33 / #34 / #35（长多行条目；配对 A/B
已证明"逐行拆"在三条事先定好的判据上不更差，但**尚未落地**，
因为要先排除瞬态因素）。

⇒ **结论：流程通了，质量还不够。** 这一节证明的是**通路**，
不是**成品可用**。

## 八、本记录**没有**证明的事（诚实边界）

1. **没有启动游戏本体验证画面**。本次只做到"文件结构合法 + 内容正确"，

   **没有**在这份记录里验证。

   这类条目只有落在"槽位容量够"的位置才能写进去；
   容量不够时 `unity_patch` 的行为是**跳过并记录**，
   **绝不截断**（截断会造成静默内容损失）。
