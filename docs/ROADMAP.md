# 路线图与当前状态

本文档诚实记录 NovaLoc 新译**已经能做什么**、**还不能做什么**，以及每项缺口的态度
（规划中 / 调研中 / 不计划）。目的是让使用者不会误以为某个功能存在。

状态标记的含义：

| 标记 | 含义 |
|---|---|
| ✅ **已完成** | 代码在仓库里，可以跑通 |
| 🔜 **规划中** | 方向明确、工作量可估，但还没有代码 |
| 🔍 **调研中** | 技术路线或收益还不确定，需要先做验证 |
| ❌ **不计划** | 有意不做，理由见各项 |

### 1.4 贴图管线

`src/novaloc/images/` 全部模块可用：

- `ocr_ppocrv6.py` —— PP-OCRv6 三档（tiny/small/medium）、DirectML、
  四点规整（`order_quad`）、几何推算（`quad_geometry`）；
- `rec_models.py` —— **按语种路由识别模型**（见下），含按需下载 + SHA256 校验。

**PP-OCRv6 的识别器不含韩语与西里尔文字**（两侧官方文档都写明：
PaddleOCR 说识别支持 50 种语言 = 中/繁/英/日 + 46 种拉丁；RapidOCR 的
模型清单原话是"**不包括韩语**、阿拉伯语、藏语、彝族等语言"）。
对这类语言它不是"读得差"而是**读成空字符串** —— 与"这张图本来没有文字"
在结果上完全一样，流水线不报错、质检不报错，用户只会觉得"这游戏汉化不了"。
属于最难排查的一类问题。

实测（本机，DirectML），同一张写着 `게임 시작` 的图：

| 识别器 | 读到 |
| --- | --- |
| 默认 PP-OCRv6 multi | `''`（空） |
| 按韩语路由到 PP-OCRv5 korean | `'게임'`、`'시작'` ✅ |

修法：**检测不变**（始终 PP-OCRv6 medium，旋转文本 Hmean 93.8），
**识别按语种换模型**。中日英拉丁留在 v6 —— 特别注意**日文必须留在 v6**
（官方 90.5% vs v5 73.7%，差 16.8 个点），有测试守着不许改错方向。

| 语族 | 模型 | 大小 |
| --- | --- | --- |
| 中/日/英/拉丁 | PP-OCRv6 multi | 已含 |
| 韩语 | `korean_PP-OCRv5_rec_mobile` | 13.5 MB |
| 东斯拉夫（ru/be/uk） | `eslav_PP-OCRv5_rec_mobile` | 7.9 MB |
| 其他西里尔 | `cyrillic_PP-OCRv5_rec_mobile` | 8.1 MB |

**实现上两个坑**：

1. v5 模型**无法通过 RapidOCR 的常规配置路径到达**。读
   `rapidocr/utils/model_resolver.py` 才确认 `MODEL_ROUTES` **只注册了
   PPOCRV6**，所以传 `Rec.ocr_version=PPOCRV5` 会让 `resolve_model_key`
   返回 None，随后查不到 model_dict，直接抛 "Invalid OCR configuration."。
   解法：用 `Rec.model_path` 直接指到文件。
2. **不需要字典文件**：ONNX 内嵌了字符集（实测韩语模型 metadata
   `character` 有 23890 项，以谚文字母开头），RapidOCR 走 `have_key()`
   分支。若误以为需要字典，它会去下默认的 `ppocr_keys_v1.txt`（中文），
   结果是"识别出满屏乱码"而**不是**报错 —— 又一个静默失败。
- `textgroup.py` —— 相邻文字块聚合（避免把一句话逐块翻译）+ 译文按原始块数回切；
- `inpaint.py` —— 三档降级（纯色填充 / OpenCV Telea-NS / LaMa）；
- `render.py` —— 2-means 取前景背景色、描边色估计、字号二分收缩、CJK 混排折行、
  超采样 + BOX 降采样、单应变换贴回（支持旋转/透视）；
- `io.py` —— 非 ASCII 路径安全的图像读写；
- `annotate.py` —— 生成带文字框标注的可视化图，供 Web 审校页显示；
- `service.py` —— 整图编排（`process` / `process_many`）。

- Ollama 提供者（`ollama_provider.py`）与客户端（`ollama_client.py`：

  Python / shell / 反引号代码 / 具名尖括号；`⟦i⟧` 屏蔽 + 三层还原校验
  （多重集 / 剩余记号 / 出现顺序）；
- `prompts.py` —— 批量提示、单条提示、复核提示、术语表注入块；
- `json_parse.py` —— 宽容 JSON 解析（剥代码围栏、括号平衡提取、修复常见错误、
  定界符回退、索引对齐）；
- `guards.py` —— 清洗、占位符检查、长度检查、未翻译检测、假名/源语言残留检测、
  重复 n-gram 检测；
- `memory.py` —— 翻译记忆（完全匹配 + 模糊匹配，默认 `memory_similarity=0.97`）；
- `glossary.py` —— 术语匹配（大小写敏感 / 全词 / 正则）+ 术语候选挖掘 +
  64 条内置游戏术语表（**不默认注入**，理由见下）。

**两处实测教训**（都影响"译文质量"这类看不见的问题）：

1. **内置术语表不默认注入**。曾试过在流水线里自动并入 64 条游戏术语
   （修 `MP` → "魔法值"这类缩写误译）。实测是**净亏**：同一批 27 条
   真实游戏字符串跑 3 遍，漏译从 0 升到 2.67/遍，还出现
   `Load Game` → "重新开始"（应为"读档"）的污染 —— 提示词把
   `Restart`/`Save`/`Load` 一起注入，4B 模型在小批量里会串。而
   "过滤掉源词已在文本里的术语"这条安全规则会**正好**滤掉
   `HP`/`MP`/`Gold`，也就是唯一受益的条目，等于自己取消自己。
   现在 `builtin_entries()` 只作为用户可查可抄的起点。

2. **缩写误译改由质检兜住**。`MP` → "生命值" 这类错误，不是漏译、
   不是占位符丢失、源文也各不相同，传统规则**完全抓不到**。
   `qa.py` 因此新增"反向碰撞"检查：不同的**短标签**（无空格、≤4 字符）
   映射到同一译文 → 报 **ERROR**。只查短标签是因为长句撞词可能是
   合理的同义表述（"我明白了"/"原来如此"），用规则去压会伤害翻译自由度。

3. **尾部占位符被删除时不再丢弃整条译文**。实测
   `Gold: {gold}` 被模型译成 `'黄金'`（占位符被整段删掉）；
   `repair_dropped_masks()` 因纯汉字里没有词边界可用而放弃，导致整条
   `placeholder_broken`、**完全不产出译文**。现在若该记号是原文最后一个
   记号且其后无非空白内容，则确定性地补到译文末尾（不可能劈开中文词、
   也不会造成 `%dgold` 粘连）。

设计依据与实测数据见 [本地翻译层技术调研.md](../本地翻译层技术调研.md)，
本文档不重复。

## 1.8 字体合并的垂直度量必须按 UPEM 换算（已修，记录以备回归）

实测数据（`tests/test_font_real.py`）：

| 字体 | unitsPerEm | hhea.ascender | asc/upem |
| --- | --- | --- | --- |
| `simhei.ttf`（基准） | 256 | 220 | 0.86 |
| `lxgw-wenkai-screen.ttf`（补充） | 2048 | 1900 | 0.93 |
| 合并产物（**修复前**） | 256 | **2210** | **8.63** ← 错 |
| 合并产物（修复后） | 256 | 238 | 0.93 |

根因：`_snapshot_metrics()` 在补充字体**自己的 UPEM 坐标系**下抓度量，
随后被原样写进 UPEM=256 的合并字体；`fontTools` 的 `Merger` 会把字形
缩放到 `base_upem`，但度量没人管。

后果比缺字形更糟：Pillow 把文字排到 y=399（48px 画布之外），
游戏里表现为**文字彻底不可见**，而所有静态检查（cmap、轮廓数、
水平度量、FreeType 可加载）**全部通过** —— 也就是"QA 说没问题，
游戏里什么都看不到"。这正是本项目最想避免的那类假成功。

## 1.9 另外三类「覆盖率报 100% 却是空白」的假成功（v1.0 修，记录以备回归）

同上，这三条都是**实测**踩出来的，而且都属于"所有数字都说没问题"
那一类。详见 [ACCEPTANCE.md](ACCEPTANCE.md) 第四节。

### (a) base 的 cmap 里有码点，但字形是**空的**

合并的默认判据是 `needed = required - base.cmap` —— 它隐含假设
**"cmap 里有这个码点"等于"有字形"**。日文手写体不满足这个假设：

| 字体 | cmap 码点数 | 抽样 400 个常用汉字里**空字形** | 真实文本 3,596 字里**空字形** |
|---|---|---|---|
| `koin.ttf` | 21,363 | **39**（`到你而那之如没些她但只从`） | **2,164** |
| `koin_nocut.ttf` | — | — | **2,081** |

后果：合并"成功"、覆盖率 100%、QA 数出 **1,258 个空白**。

**修法（顺序很重要）**：先按原判据合 → QA **渲染**验证 → 只把验证失败的
那些字符强制覆盖、重合一次。不能一上来就强制覆盖**所有**字形 —— 那等于
把基础字体的字形全换掉，"保留原字体风格"（`merge` 策略存在的理由）就没了。

### (b) `fontTools.Merger` 对两边都有的码点**保留 base 那一条**

所以"把字符加进 `needed`"根本不生效。实测证据：强制与不强制产出的 `¢`
**字形名完全一样**（都是 base 的 `cent`，而不是补充字体重命名后的
`nvCJK0_…`），轮廓数也一样是 0。

修法：把强制字符**从 base 的 cmap 里摘掉**（`_drop_from_cmap`），
只动 cmap、不动 `glyf`（`subset_font` 刚用 `retain_gids=True` 固定了 GID）。
摘除必须遍历**所有** cmap 子表（`font["cmap"].tables`），不能用
`getBestCmap()` —— 后者只返回一张，而游戏引擎和 Pillow 各自会挑不同的子表。

### (c) 摘 cmap 之后，规划器当初选的字体不够用了

摘 cmap 会把那些字符从"基础字体已覆盖"里拿掉，于是它们**重新**需要补充
字体提供 —— 而规划器当初把它们算作"基础字体有"，`plan.source_paths` 里
可能根本没有能提供它们的字体。

实测：摘掉 2,217 个空字形后 `✔✕✖✘❤` 变成缺字，而规划器只选了
`lxgw-wenkai-screen.ttf`（没有这 5 个符号）⇒ 报"仍缺 5 个字符" ⇒
**整个重试被丢弃** ⇒ 第一次的 2,217 个空白原样保留。
换成**全部候选**后 `seguisym.ttf` 正好补上。

### (d) CFF（`.otf`）轮廓无法合并 ⇒ 退化为整体替换

`fontTools.Merger` 要求两边都有 `glyf`/`loca`（TrueType 轮廓），
CFF 字体的轮廓在 `CFF ` 表里 ⇒ 报
「表集合归一化失败：字体缺少合并必需的表：`['glyf','loca']`」。

原先的后果是这条字体**原样留着**：实测 `ship.otf` 只有 **77.2%** 中文覆盖
⇒ 游戏里凡用到它就是一片口口口。现在退化为**整体替换**成覆盖最好的中文字体。

**只有确实是 CFF 时才退化**（判据是错误信息里同时出现 `glyf` 和 `loca`），
别的合并失败原因照旧上报 —— 否则一个真正的规划错误会被"替换"悄悄掩盖。

> **另一条教训**：**"没被 CSS 引用"不等于"游戏不会用到"。**
> 这个游戏的 `FontLoad` 插件用 `Graphics.loadFont()` 动态加载字体，
> 不走 `@font-face`。所以按"宁可不缺字"处理。

现在的判据：`ascender / unitsPerEm` 的比值必须与基准字体同量级。
静态不变量查不出这类错误，必须**实际渲染并检查墨迹**。

## 2. 当前的缺口

### 2.1 Unity 序列化资源 / AssetBundle / IL2CPP —— 🔜 规划中

**现状**：不支持。`UnityAdapter` 只处理 `StreamingAssets` 与 `*_Data` 下的
**明文** json/csv/txt/xml/po/ini。

**缺口**：

| 文本形态 | 需要的技术 |
|---|---|
| `.assets` / `.unity3d` 序列化资源 | Unity 序列化格式解析（UnityPy 已提供） |
| AssetBundle | 同上 + bundle 容器格式与压缩 |
| IL2CPP（`global-metadata.dat`） | 元数据解析 + **定长字符串替换**（改长度要搬移所有偏移） |

**为什么不做成"先做最简版本"**：README 已明确表态 ——

> 我们不会去盲写这些二进制格式 —— 盲写几乎必然破坏资源，
> 而且失败时表现为"游戏打不开"，用户根本查不出原因。

**当前给用户的替代路径**：用 [UABEA](https://github.com/nesrak1/UABEA) 或
[AssetStudio](https://github.com/Perfare/AssetStudio) 导出 `TextAsset`，
再用散装文件模式处理。`UnityAdapter` 会在 evidence 里报告检测到的托管后端类型，
并在发现未处理的序列化资源时给出这个建议。

#### 2.1.1 实测：文本到底藏在哪（真实游戏 `UnityAliQ`，1.4GB）

> ⚠️ **本节末尾"所以要做就必须配一套回写后校验机制，工作量远超解析本身"
> 的判断已被 §2.1.2 修正**：实测证明**原地等长改写**（不改长度、不挪偏移）
> 是安全且可逆的，回写**已实现**。本节保留原样作为排查过程的记录，
> 其中"对白在 `.assets` 里"这条**是对的**（已复验：那句话确实在
> `sharedassets1.assets` 与 `level0` 中）。

为了判断"先做哪一块最值"，我对这个真实 Unity 游戏做了完整排查，结论
**支持"不要急着写 .assets 解析器"**，同时也**给出一块真正可做的收益**：

| 位置 | 实测结果 |
|---|---|
| 游戏根目录散装文本 | **只有 2 个无关文件**（`config.xml`、一个日志）—— 可翻文本为 0 |
| `*_Data/Managed/*.dll`（`#US` 堆） | `Assembly-CSharp.dll` 有 1,347 条字面量，但**绝大多数是内部噪声**：989 条标识符/字段名（`Puppet2D`、`_ProjInfo`、`Bone`）、9 条运行时报错（`[BUG:FIXME] FLIP failed`）、其余是 Poly2Tri / ImageEffect 的第三方库消息。**玩家可见文本几乎为零** |
| `*.assets` 序列化资源 | **对白在这里**：`sharedassets1.assets` 里能直接搜到明文 `"Activate the emergency destruction system."` |
| TextMeshPro | **完全没有**（全 Data 目录搜 `TMP_FontAsset` / `m_AtlasPopulationMode` / `TextMeshPro` 零命中；`Assembly-CSharp.dll` 用的是**传统 uGUI**，`UnityEngine.UI` 出现 1 次） |

**所以对这个游戏**：
* 它的 UI 文字走**传统 uGUI + 明文/序列化资源**，**没有 TMP 这道坎** ——
  §2.3 那条"必须重烘焙图集"的风险**在这个游戏上不存在**；
* 真正的缺口是**`.assets` 里的文本**，不是 TMP，也不是 DLL 里的字符串。

**据此新增的成果**（`novaloc/engines/dotnet_strings.py`）：
一个**只读**的 `#US` 堆解析器，能如实给出"这个游戏的托管程序集里有
多少字符串、其中多少像人话"。它的价值是**让用户看到真实数字**
（而不是被"支持 Unity"误导成"这游戏能翻"），并且用实测把上限
钉死在 196 条 —— 也就是**这个游戏靠 DLL 抽取最多只能翻 196 条**。

⚠️ **它刻意不接入回写**，原因写在模块文档里：`#US` 每条字面量前面是
长度前缀，改长度就要重算全部堆偏移与 RVA —— 那是重写 PE，错了的表现
是"游戏完全无法启动"，比口口口严重得多。所以它**只用于统计与导出**。

⚠️ 两级过滤（宽松 `translatable` / 严格 `dialogue_like`）都是**尽力而为**，
实测严格过滤仍会漏进未见过的日志形态。任何采用它的流程都必须**让人过一眼**。


**态度的理由**：这个功能的**风险收益比**很不对称 ——
做对了只是"多支持一类游戏"，做错了是"用户游戏打不开且不知道为什么"。
所以要做就必须配一套"回写后校验"机制（重新解析产物确认结构完好），
工作量远超解析本身。

#### 2.1.2 ✅ 已实现：`.assets` 的**原地等长改写**（推翻了 2.1.1 的结论）

**旧结论是"绝不改写 `.assets`"。实测证明它一半对、一半错** ——
关键在于**用哪种写法**：

| 写法 | 实测结果 | 结论 |
|---|---|---|
| 让资源库**重建**整个文件（UnityPy `save()`） | 66,240 字节的 `.assets` 存回去只剩 **5,888** 字节；写回原值也**无法还原**（第一处差异在偏移 5） | ❌ 否定 |
| **原地等长替换** | 36 MB 的文件改 1,874 处：大小不变、区间外改动 **0 字节**、写回原值后**逐字节相同** | ✅ 采用 |

原因是 Save 会重建整个文件、丢弃未被引用的对象、重算全部内部偏移；
而独立 `.assets` 的偏移是相对自身、且与配套 `.resS` 互相印证的。

**Unity 序列化字符串的格式**是 ``<4字节长度><UTF-8 字节><0..3 对齐零>``。
只要新串字节数 **≤** 原串，就能：保持文件总大小不变、保持所有内部偏移不变、
只改这 4+N 个字节，剩余空间补 0。

| 指标 | 数值 |
|---|---|

| 区间外改动字节 | **0** |
| 还原后 sha256 | 与原始**完全相同** |
| 改后资源可解析 | ✅ 6,807 个对象 |

##### 硬约束：装不下就**如实报告**，绝不截断

容量 = 原文英文字节数向上取 4 对齐，所以"装得下"等价于"中文不超过英文"。
实测 EN→ZH 的字节比通常在 0.35~0.46，**大部分装得下**，
但仍有一部分放不下（抽样 40 条中有 3 条、对白 35 条中有 8 条）。
这时：

* **绝不截断** —— 截断会静默丢内容（本项目最危险的失效形态）；
* 记为 `skipped_no_room` 并在报告里写明"**N 处因原文空间不足未改写**
  （保留原文，未被截断）"。

**"如实报告一部分没做到"远好于"看起来全做了、其实丢内容"。**

##### 这一轮被实测抓出的三个 bug（都不是读代码能发现的）

1. **`_workspace_dir()` 永远返回 None** —— `Context` 的真实字段是
   `workspace`（一个 `Workspace` 对象），不是 `workspace_dir` 字符串。
   第一版只按属性名找，于是清单不落盘、边车不生成、回写静默什么都不做，
   而抽取阶段照常报出几万条文本，**看起来一切正常**。
2. **改写不可逆** —— 写过一个更短的中文之后，长度前缀变小了；
   若再从文件里推导容量，推出来的比真实区间小，原文就再也写不回去。
   实测 38 处只还原 27 处、1,129 字节对不上。修法是让调用方
   把**抽取时记录的原始容量**一路传下去。
3. **`_last_units` 靠实例状态传偏移** —— `stage_apply` 拿到的适配器实例
   与 `stage_extract` 的**不是同一个对象**，于是它是空的，表现为
   "抽取 3 条、翻译 3 条、回写 0 条 → `没有任何文件被写入`"。
   **直接调用永远是对的**（复用同一对象），只有走完整流水线才暴露。
   修法是优先用 `apply()` 传进来的 `units`。

每个 bug 都配了针对性回归测试（`tests/test_unity_patch.py`，
其中 `test_adapter_apply_works_without_instance_state` 专门用
**没跑过 extract 的新适配器**调 `apply`）。

##### 还没做到的（如实列出）

* **AssetBundle（`.bundle`/`.unity3d`）未解包** —— 这类游戏里的文本读不到，

##### ★ AssetBundle 的最终结论：两种情况必须分开，且都不是"待办"

这一项从"计划做"变成"**有数据支撑的不做**"，过程记在这里以免被反复重开。

**情况 A —— 明文 UnityFS：投入产出比极低，不做**

三个真实游戏的实测（包内可翻文本 vs 同游戏 `.assets` 内的文本）：

| 游戏 | 包内 | `.assets` 内 | 占比 |
| --- | --- | --- | --- |
| （游戏一） | 4 | 11,817 | **0.03%** |
| （游戏二） | 4 | 127,693 | **0.003%** |
| （游戏三） | 1 | 83,578 | **0.001%** |

也就是说：**解包能力写完，也只能多翻千分之几的文本**，
却要引入一整套二进制容器解析 + 回写风险。**不投入。**

**情况 B —— 加密 Addressables（`IC 1.2`，全库唯一）：能力边界，不是 TODO**

`IC 1.2` 抽到 0 条。逐个查明：

* `_Data/` 里**没有任何** loose `.assets` / `level*`（0 条是结构性的）；
* 255 MB 的 `data.unity3d` 里只有 **8 个** `TextAsset`，全是 `*.physics3` 物理参数；
* 文本在 `StreamingAssets/StandaloneWindows64/` 的 **95 个文件（237 MB）**里，
  文件名是 CRC32；
* 其中 **93 个根本打不开**：`UnityPy` 返回 0 个对象、裸扫 0 个槽位、头部随机。

用**熵**做可证伪的判据（实测三档，分得很开）：

| 类别 | 熵 | 块熵极差 | 样本 |
| --- | --- | --- | --- |
| **加密** | **7.9999–8.0000** | 0.0005–0.0008 | `IC 1.2` ×3 |
| 压缩 | 7.28–7.35 | 0.14–0.42 | 真实 `.bundle` ×6 |
| 明文 | 5.5001 | 5.0853 | `.assets` |

`novaloc unity-strings` 现在会**明说**（真实输出）：

```
没有找到候选文案。
其中 93 个资源容器**经熵判定为加密**（熵 ≥ 7.99 且整文件处处均匀）。
加密资源无法读取，需要从 IL2CPP 元数据/主程序里逆出密钥。
这属于能力边界，不是用法问题。
```

**判据的固有局限（已钉成测试）**：把"一半可压、一半接近随机"的数据用
zlib 最高级别压，产物熵 **7.9997**、块极差 0.0015，**会被判成加密**。
熵判据无法区分"压到极限的数据"与"加密数据"。实际影响小
（真实容器离 7.99 很远），但如实记录。

**★ 造测试数据时我连错三次**：为了让"压缩不能判成加密"可测，我用了三种
合成方式，熵**全部贴满 7.99**（`(j*7+i)%251` → 7.9980、zlib 压"可压+随机"
→ 7.9985、字节限 `0..250` → 7.9715），一度**以为判据错了**。
去量真实样本才发现真实压缩流只有 7.28–7.35 —— 因为它的**字节频率不均匀**。
改用加权分布生成得 7.4284，落进真实区间。
教训：**造不出真实分布时，先量真实样本，别硬凑。**

* **纯图游戏**：实测 `AliQ`（613 MB 资源）里只有约 **13 句**英文，
  其余是动画/音效名 —— 这类游戏的文字是**画在贴图里**的，
  得走本工具的贴图汉化流程（但该游戏 `scan --images` 报 0 张贴图，
  说明它还用了非标准图集，需另行排查）。
* **Naninovel 的超大本地化 CSV**：一条记录上万字符、模型会把它当"多行文本"
  导致解析成空映射（实测 60 条里 12 条失败）。这类应走
  `unity_locale.py`（已实现解析与回填，但**故意不写回** ——
  整张 CSV 是**变长**记录，改它会挪动后续偏移）。
* **MonoBehaviour 类型树**：IL2CPP 游戏读不出类型树
  （实测 `AlienQuest-EVE`：26,738/26,986 失败），所以组件里存的文本够不着。
* **资源名噪声**：`Main Texture`、`Normal Map` 这类**会**通过文本筛选。
  已知取舍：宁可多收噪声，也不漏真台词。真正被挡住的是路径/代码式的
  （`Hidden/Universal...`、`_MainTex`、`UnityEngine.*`）。

### 2.2 视觉 VLM 兜底 —— ✅ 已完成（**只做内容纠错，不做检测**）

**现状**：已经接通。

- `translate/vision_ollama.py` 提供 `OllamaVisionEngine`，注册为
  `@register("vision", "ollama")`；实测 `registry_snapshot()` 里
  `'vision': ['ollama']`。
- `images/service.py::_vlm_rescue()` 在检测之后、翻译之前执行：
  挑出 `confidence < vlm_threshold`（默认 0.6）的块，按四边形做透视校正裁出正立区域
  （`_crop_quad`），交给 VLM 重读**内容**。
- `_vlm_reconsider()` 的 docstring 明确了边界：

  > **只用来纠正文字，绝不用来改框**：VLM 的定位精度比专用 OCR 差两个数量级
  > （实测旋转文本 Hmean 2.1 vs 93.8），一旦让它决定位置，排版就毁了。
  > 所以这里只取文本，四边形坐标原样保留。

- 替换条件很保守：**只在 VLM 给出非空、且归一化后与 OCR 原文不同的结果时才替换**，
  读不出来就保留 OCR 原结果（避免"兜底把好结果搞坏"）。
  被改过的块带上 `vlm_reread` 警告，并计入 `vlm_reads` / `vlm_fixes`。
- 关闭方式：`OcrConfig.vlm_fallback = False`，或者干脆不起 Ollama
  （`vlm` 属性会 `available()` 失败并返回 `None`，只打一行 info 日志）。

**仍然存在的边界 —— 这是最重要的一点**：

**检测永远不由 VLM 做。** 实测旋转文本检测的 Hmean：

| 方案 | 旋转文本 Hmean |
|---|---|
| PP-OCRv6 small | 93.7 |
| PP-OCRv6 medium | 93.8 |
| Qwen3-VL-235B | 2.1 |
| GPT-5.5 | 10.0 |

差一个数量级。VLM 能"读懂图里写了什么"，但不输出稳定的文字框。
所以如果 PP-OCRv6 **一个框都没检出来**，就没有低置信度的块可供兜底，
VLM 也不会被调用 —— 这时问题在检测能力，兜底帮不上。

> **注意**：上述四个数字不在 `本地翻译层技术调研.md` 里
> （那份报告讨论的是文档解析方向的 OCR，建议的是 PaddleOCR PP-OCRv5 + qwen3-vl 兜底）。
> 这组对比来自本项目自己的验证记录。

**剩余可做的事 —— 🔜 规划中**：

- 兜底**没有缓存**，同一段文字在不同贴图上重复出现会重复问模型；
  `_vlm_reconsider` 也没有按"已成功重读过的文字"做记忆。
  贴图里重复出现的 "OK" / "Cancel" 很常见，加一层缓存能省大量时间。
- `describe_style()` 已定义在 `VisionEngine` 协议里，但 `OllamaVisionEngine`
  是否实现了它、以及有没有被 `render.py` 用上，需要单独确认；
  **风格描述**（字重、是否艺术字、描边粗细）本可以用来改善重绘的观感。


### 2.3 TMP 静态图集 SDF 烘焙 —— 🔜 规划中

**现状**：不支持。这是 Unity 字体替换的**真正难点**。

**问题本质**：TextMeshPro 在运行时查的是 `TMP_FontAsset` 里的
`characterLookupTable` 与配套的 **SDF 图集纹理**。
**把 `.ttf` 拷进 `StreamingAssets` 对 TMP 完全无效** —— 它根本不读那个文件。

**要做的工作**：

1. 从 `TMP_FontAsset` 的序列化数据里读出图集尺寸、padding、`faceInfo` 等参数；
2. 用 FreeType 的 SDF 模式（或自己实现有符号距离场生成）为新增字符生成 SDF 位图；
3. 把新字形**塞进已有图集**（如果没有空位就要扩图集并更新所有 UV 矩形）；
4. 重建 `characterLookupTable` 与 `glyphTable`；
5. 重新序列化 `.asset` 并把图集 PNG 写回。

**为什么标注"规划中"而不是"调研中"**：技术路径是清楚的
（Unity_Font_Replacer 已经验证过可行性），只是工作量大且需要
Unity 序列化格式的读写能力 —— 而后者与第 2.1 节是同一块基础设施。
**所以这两项的优先级应该绑定：先做序列化格式读写，再做 SDF 烘焙。**

**相关法务提示**：Unity_Font_Replacer 是 GPL-3.0。本工具只借鉴"必须重新烘焙图集"
这个结论，**不会复制其代码**。见 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) 第 1.4 节。

### 2.4 归档解压与回写 —— ✅ 已完成（`src/novaloc/archives/`）

| `.zip` | ✅ | ✅ | `zipfile` |
| `.tar` / `.tar.gz` / `.tgz` / `.tar.bz2` / `.tar.xz` | ✅ | ✅ | `tarfile` |
| `.7z` | ✅ | ❌ **故意只读** | `py7zr`，退回 `7z`/`7za`/`7zr` CLI |

7z **不回写**是刻意的：写不回去时宁可明确拒绝，也不要产出一个半坏的归档。
`probe()` 会把它标成 `writable=False`，回写阶段据此拒绝并提示用户手工打包。

**工作方式**（这是设计上最容易出错的地方）：

```
unpack 阶段   解包到 <workspace>/unpacked/<归档名>/
各阶段        读的是「归档解包后的目录」（effective_source），不是归档文件
apply 阶段    把产物写到 out/，**不动**原目录与解包树（延续"原游戏只读"）
apply 末尾    repack(changes_from=out/) 把改动打回原归档，原文件备份为 *.novaloc.bak
```

注意 `changes_from=out/` 这个参数：流水线**不修改解包树**，如果 `repack`
去比对解包树，会得到"没有变化" → `repacked: 0` → 所有阶段都报 ok、
归档里却还是原文。这是本项目踩过的最阴的一类 bug（统计上完全成功、
产物是旧的），所以 `repack()` 的文档里把它写清楚了。

**安全三重**（读不可信归档时）：

1. 路径穿越 —— `safe_member_path()` 拒绝绝对路径、`..`、UNC、盘符、控制字符；
2. 解压炸弹 —— `MAX_ENTRY_BYTES` 256 MiB / `MAX_TOTAL_BYTES` 2 GiB /
   `MAX_ENTRIES` 20 万，**在读之前**按自报大小检查；
3. 恶意 pickle —— `.rpa` 索引是 pickle，用 `_RestrictedUnpickler` 白名单反序列化。
   白名单**必须**包含 `_codecs.encode`（pickle protocol 2 用它编码 bytes），
   否则所有带 XOR 前缀的正常归档都会被拒。

**还没做**：`.xp3`（KiriKiri）、Wolf RPG 的 `.wolf`、Unity `resources.assets`
的自定义容器 —— 见 2.1 与 2.5。加密/私有容器格式**明确不做**，那是无底洞。

2. **翻译阶段的异常只写 stderr**，stdout 那 12 分钟一个字都没有 ⇒
   我一度把整段翻译误判成"卡死"，而真实情况是**在持续重试**。

两件事的共同点：**"看起来正常/静默"和"脚本或观测面坏了"长得一样**。

所以现在的判活顺序是：

1. 主进程 **ΔCPU** 与 Ollama **ΔCPU**（都有动静 ⇒ 在干活）；
2. 到 Ollama 的连接状态（`Established` 且对端在算 ⇒ 正常）；
3. **stdout 与 stderr 都要读**；
4. 最后才看中间产物（`entries.jsonl`）—— 它由不同阶段先后写入，
   分母会变甚至一度变小，**不能当进度指标**（见 §3.6.3）。

## 3.5 翻译吞吐：一次把"到底慢在哪"量清楚（实测）

### 3.5.0 ★ 先修的是我**量数据的方式**：日志是 UTF-16

第一次量端到端日志，脚本报的是：

```
降级事件（'批 N 条里只回 M 条'）共 0 次
'Ollama 返回 500' 出现 0 次
```

而实际是 **48 次 / 14 次**。原因是**编码** —— 这个日志是 PowerShell 用
`*>` 重定向写出来的，格式是 **UTF-16LE（带 BOM）**，我却按 UTF-8 读，
`errors="replace"` 把中文全变成乱码，正则一条也匹配不上。

**一个返回 0 的统计最危险**：它看起来像"没有问题"，
而不是像"脚本读错了"。现在 `read_log()` 先看 BOM 再定编码，
并把判定结果打印出来，让"读错"这件事本身可见。


全库 **4,179,819** 条单位。这一节把吞吐的每个环节都用真实数据量了一遍，
因为**先后两次凭印象得出的结论都是错的**，必须留下可复核的数字。

### 3.5.1 先纠正两个我自己的错误结论

| 我说过的 | 实测 | 错在哪 |
| --- | --- | --- |
| "吞吐崩了，30 分钟只推进 34 条" | **31.1 条/分钟，0 停顿**（10 次采样） | 那两次读数之间**我自己在跑 Ollama 探针争 GPU**，而且只取了两点。**两点采样不叫测量** |
| "批量失败是主因"（据 `2/12` 日志） | 12 批 × 12 条真实内容：**144/144，0 失败，245.7 条/分钟** | 日志**只记异常**，分母（总批数）根本不在日志里，所以从日志算不出发生率 |

第一条的教训很直接：**采样间隔里有别的东西在动，就不能当成稳态速率**。
第二条的教训：**"日志里满是某个警告"不等于"这个警告很常见"** ——
先量分母。

### 3.5.2 各环节实测数字

### ⚠️ 3.5.2.1 一个我**必须收回**的推论

我先前写过"**模型只占端到端耗时的约 1/10**，所以换更快的模型没用"。
**这个推论有两个错误**：

1. **口径不对**：`0.18 秒/条` 是**纯模型往返**（单次 `/api/chat`），

2. **我没有任何按阶段拆分的时间数据**：日志里**没有每阶段耗时**，

能站得住的只有这些**直接观测**：

* 纯模型往返：批 40 时 **0.18 秒/条**，批 1 时 **0.76 秒/条**
  ⇒ **批越大越省往返**，这条支持 3.5.3 的改动；
* `translate` 阶段采样 **31 条/分钟**，而同样内容在探针里
  （批 12，`_batch_rate.py`）能到 **245.7 条/分钟** ⇒
  **两者之间确实有约 8 倍的未解释开销**，位置尚未确定。

**下一步（未做）**：给每个阶段加一条耗时日志，才能把 107 分钟
按阶段拆开。在那之前，**不要**再说"瓶颈在哪"。

### 3.5.3 找到并修掉写死的批大小

`pipeline/stages.py` 里写着：

```python
chunk_size = 12 if kind in ("dialogue", "narration") else 40
```

这个 12 **绕过了**提供者自己的 `_make_batches`（按 `max_batch_chars=3000` /
`max_batch_strings=40` / `max_batch_long_chars=200` 切）。而全库文本
**中位长度只有 9 字符** —— 12 条一批约 108 字符，离 3000 上限差得极远。

实测收益（`.scratch/_chunk_gain.py`，真实长度分布）：

| 游戏 | 写死 12 的批数 | 提供者切 | 降幅 |
| --- | --- | --- | --- |
| Dungeon And Darkness | 266 | 112 | **2.4×** |
| 072 Project | 800 | 371 | **2.2×** |

**改大批会不会掉质量？实测说不会**（`.scratch/_chunk_quality.py`，
同一批 120 条真实 dialogue，两种批大小各翻一遍，两边都 120/120 拿到译文）：

| 批大小 | 长度比中位 | 长度比 p90 | 最大 |
| --- | --- | --- | --- |
| 12 | 0.30 | 0.67 | 1.33 |
| 40 | 0.32 | **0.46** | 1.50 |

短句（原文 ≤10 字符）平均译文长：12 → 40 是 **−41%**，
**没有**"短句被长句带长"的迹象（那是代码注释里记着的真实事故）。

于是改成 `Pipeline._chunk_indices()`：**问提供者**要批次，
但加一条不可妥协的校验 —— 返回的下标必须**覆盖且不重复**，
否则退回固定块。漏译是**静默**的（条目根本不进 `out`，报告里看起来
像"这条不存在"），所以这条校验比速度重要得多。

## 3.6 一次"看起来卡死"：11 分钟静默，以及判据断在哪

### 3.6.1 观测到的现象（都是实测）

一次真实端到端跑（`Midnight Exhibitionist DX`）在 21:25:17 之后再无输出。
我 11.3 分钟后（21:36:37）去查，同时看到：

| 观测项 | 值 | 说明 |
| --- | --- | --- |
| `novaloc` 进程 ΔCPU（12 秒内） | **0s** | 一点没动 |
| 到 Ollama 的 TCP 连接 | **Established** | 连接还在，没断 |
| Ollama 进程 ΔCPU（8 秒内） | **0s** | 服务端没在算 |
| 模型 `translategemma:4b` 到期时间 | 只剩 3 秒 | 已空闲超 `keep_alive`，**没在生成** |
| `nvidia-smi` GPU 利用率 | 30~40% | 但这是**其他进程**的（见下） |

`nvidia-smi --query-compute-apps` 列出了一长串 PID，其中**只有** `63336`
（我们的进程）和 `33396`（ollama）。结论是：**客户端在等一个不会来的响应。**

### 3.6.2 ★ 判据断在哪：无法区分"一次卡死"和"两次超时"

`request_timeout_s = 300`，所以**单次**请求最多等 5 分钟。
静默是 11.3 分钟 ≈ **2 次超时**。但当时**没有任何办法**区分：

| 假设 | 后果 | 修法 |
| --- | --- | --- |
| 一次请求卡了 11 分钟 | 超时**失效** | 补一道自己的总时限 |
| 两次各 5 分钟的超时 | 超时**有效**，只是**沉默** | 把超时说出来 |

为什么区分不了：**日志里既没有时间戳、也没有任何请求耗时或超时记录**。

`_request()` 把 `httpx.TimeoutException` 转成 `OllamaError` 就交给重试层了，
**自己一个字不打**；而 `stage_translate` 的重试日志只记"第 N 次失败"，
不记等了多久。于是"等了 5 分钟"和"瞬间失败"在日志里长得**一模一样**。

**我没有在判据不足时改行为** —— 先补观测（`0cd0d45`）：

* `_log_request()`：每次请求都记耗时，**成功也记**（否则量不出基线）；
* `SLOW_REQUEST_S = 60`：超过就打 WARNING，写明**耗时**与**是哪个请求**；
* 超时分支也走它 —— 超时**必须留痕**。

基线参照（实测）：40 条一批约 7s、12 条约 3s，60s 足够宽松。

### 3.6.3 `entries.jsonl` 在跑的过程中会变大 —— 以及我**先给错了原因**

同一个游戏，我在不同时刻读到的是：

```
21:19   1589/2669
21:23   1030/1421
21:36   1589/3043
```

**分母在变**，而且一度**变小**（2669 → 1421）。

#### ★ 我当时的解释是错的

我把它记成了"这个文件由不同阶段先后写入（抽取/翻译各有自己的
进度快照），读到的取决于哪个阶段最后写的"。**这个解释是编的** ——
我当时**没有**去看阶段产物，只是看到一个不单调的数字就顺着
"多阶段各写一份"的直觉圆了过去。

#### 实测出来的真实原因

去看工作区就清楚了：

```
extracted/units.jsonl       3043 个单位   ← 21:51:20 一次写完，之后不再变
translations/entries.jsonl  1720 个条目   ← 一直在长（实测 45 秒 +17）
```

**条目是在翻译过程中被逐批创建出来的**，不是一开始就有 3043 条。
所以分母**本来就该单调增长**：它表示"已经产出的条目数"，
而不是"总条目数"。我把它当成总数，才觉得"分母在变"很怪。

读数不单调（2669 → 1421）是**另一次不同的运行**留下的文件
（同一个游戏我跑过好几轮，工作区目录不同），
我把**不同工作区**的数字当成同一条时间线了 —— 这是纯粹的口径错误。

#### 留下的教训（两条，都比原来的解释有用）

1. **拿"某个中间产物的行数"当进度指标要靠不住**，因为它可能是
   "已产出数"而不是"总数"。要判活，看**日志是否在增长**或
   **主进程的 ΔCPU**（见 3.6.2 的判据表）。
2. **更重要的**：我当时**有**能力去工作区看一眼（`extracted/` 与
   `translations/` 就在那里），却选择用"多阶段各写一份"这种
   **听起来合理**的说法补上。这与 §3.5.1 里那两个凭印象的结论
   是同一个毛病 —— **看起来合理 ≠ 量过**。

#### 正确的读法（Round 15 补）

总条目数**不在这两个文件里**，而在 `extracted/units.jsonl` 的行数
（本例 **3043**，一次写完后不再变）。所以正确的进度读法是：

```
已产出条目 / units.jsonl 行数      例：2674 / 3043
```

而 `entries.jsonl` 自己的分母**只表示"已写出多少条"**。
两者混用就会得出"分母在变"的错觉。

⚠️ **别在长跑期间对模型打额外请求。** 我在 Round 12/13 跑 A/B 探针时
和 `auto` **抢同一个模型槽位**（`max_loaded_models=1`），这会影响
被观测对象的 `failed` 数（本轮观察到 `failed` 从 39% 升到 51%）。
探针结论（配对对照）本身仍然成立，但**当时的绝对失败率不能用**。

## 4. 明确不计划做的事

写出来是为了节省沟通成本。

| 事项 | 理由 |
|---|---|
| **用生成式模型"画"贴图文字** | README 已经说明了取舍：生成模型不保证笔画正确、不需要字真的存在，结果是"看起来像中文但是错字"，而且尺寸字重描边每次都不同。**宁可风格略有差异，也不能画出错字**。这条不会变 |

| **修改只有 `.rpyc` 的 Ren'Py 发行版** | 编译产物改了游戏也不认，且这是作者明确的意图。工具明确报告失败而不是绕过 |

| **绕过游戏的反调试/反篡改** | 与本地化的目标无关 |
| **联网翻译 API（OpenAI / DeepL 等）** | 本工具的核心卖点之一是**完全离线** —— 不把游戏文本发到任何服务器。`registry` 的 `translate` 类别在架构上支持云 API 适配器，但**本仓库不会内置** |
| **为个别游戏写专用适配器** | 无法泛化。这类需求走散装文件模式 |

## 7. #41 ★★★ Ollama 500 会**中断整条游戏的翻译** —— 一个 `except` 写窄了的真 bug

**状态：已修 + 已红证 + 已实测（`ffe96e3`，v1.4.2）。**

### 7.1 怎么从"成功率低"追到一个"整轮中断"的 bug

游戏 2 跑完是 `translated 1563 / failed 1480`，failed 占 **48.6%**。
按 `warnings` 归因，**98.4%（1457/1480）带 `token repeat limit reached`**。
再按**源文行数**分档，形态非常刺眼：

| 源文行数 | 成功 | 失败 | 成功率 |
| --- | --- | --- | --- |
| 1 行 | 1112 | 29 | **97.5%** |
| 2 行 | 74 | 207 | 26.3% |
| 3 行 | 376 | 1244 | **23.2%** |

长度分档也有一处**反常**，正是它把人引向正确方向：

| 源长 | 成功率 |
| --- | --- |
| 0-50 | 92.8% |
| 50-100 | **14.3%** |
| 100-200 | **16.6%** |
| 200-400 | **92.0%** ← 更长的反而几乎全成功 |

**为什么 200-400 反而好**：`max_batch_long_chars = 200`，
超过 200 字符的条目被判为 `hard`、**独占一批**；50~200 的**成批**。

### 7.2 第一版假设被自己的实验否掉

我先假设"多行条目进批 ⇒ 复读 ⇒ 拖垮整批"，于是做三组对照
（`.scratch/_ab_repeat.py`，8 条真实失败源文）：

| 做法 | 成功 |
| --- | --- |
| A 整条屏蔽换行（现状） | 7/8 |
| B 拆行成批 | 8/8 |
| C 整条不屏蔽换行 | 8/8 |

**A 自己就有 7/8** ⇒ "拆行能修好"**不成立**（7 vs 8 分不开）。
这一步很有价值：它说明这些条目**当时失败、现在重跑就成功**，
于是问题从"内容形态"转向"当时到底发生了什么"。

### 7.3 决定性实验：0% 不可能是概率

24 条真实失败源文，用**产品自己的** `translate_batch`（`.scratch/_batch_poison.py`）：

| 条件 | 成功 |
| --- | --- |
| S 逐条（批大小 1） | 22/24 = 92% |
| **M 批量 第 1 次** | **0/24 = 0%** |
| **M 批量 第 2 次** | **0/24 = 0%** |

**0% 而不是 50%** ⇒ 一定有个**确定性**的东西在起作用，不是概率波动。

### 7.4 根因：`OllamaError` 不是 `ProviderError` 的子类

抓完整调用栈（`.scratch/_trace_abort.py`）：

```
translate_batch → ollama_provider.py:1283 → _call_single → _chat → client.chat → _request
OllamaError: Ollama 返回 500：{"error":"prediction aborted, token repeat limit reached"}
```

而

```python
class OllamaError(RuntimeError): ...   # ← MRO: OllamaError → RuntimeError → Exception
issubclass(OllamaError, ProviderError)  # False
```

两处**救援/重试**的 `except` 只写了 `ProviderError`：

* 块 3.5 的**标记重试**（就是 1283 那次调用外面）；
* 块 3.7 的**逐行救援**。

⇒ 500 **逃出整个 `translate_batch`**。后果不只是"那几条 FAILED"，
而是**上层那条游戏的整轮翻译提前中断** —— 比质量问题严重得多。

**修法**：两处改成 `except _RETRYABLE`（本就含 `ProviderError`，是**超集**，
不放松任何既有行为）。**没有**放宽到 `except Exception` ——
那会把真 bug 吞成"翻译失败"，正是本项目最怕的"看起来正常其实坏了"。

### 7.5 实测效果（同一 24 条、同一形态）

| | 修复前 | 修复后 |
| --- | --- | --- |

## 10. #44 ★★★ 「以原文为键」的合法返回被判成解析失败 —— 两处判据互相矛盾

**状态：v1.5.1 已修。** 现场来自真实游戏库实跑，不是构造用例。

### 10.1 现场

给 newlytransport 跑 `auto` 时 stderr 出现：

    批 0（1 条）第 1 次失败：单条翻译失败（所有解析策略均失败，
    原始输出前 200 字符：'{"vigilance requirements": "警戒要求"}'）
    ：解析得到空映射

译文 **完全正确**（"警戒要求"），却被判成失败，于是白跑一次重试。

### 10.2 根因：两个模块对**同一形态**的判断相反

* `to_translation_map` 的 docstring 明确写它**支持**
  ``{"原文": "译文"}``，理由是实测 `translategemma:4b` 真会这么回
  （要求按行给 ``编号<TAB>原文`` 时它回 ``{"HP": "生命值", …}``，
  完整且正确）；
* 但 `_looks_useful`（`parse_json_loose` 的门槛）**只认数字键**
  ⇒ 这段合法且正确的 JSON 被丢弃 ⇒ 空映射 ⇒ 报错 ⇒ 掉到单条重试。

⇒ **单看任一模块都自洽**，只有把"模型真实返回"喂进整条链路才暴露。
这是"同一判据分散在两处 ⇒ 必然互相矛盾"的典型例子。

### 10.3 修法与反例

`_looks_useful` 增加：键是**非平凡字符串**（长度 > 1）且**每个值都是
非空字符串** ⇒ 认为有用。

必须**继续被拒**的（都有测试钉住）：

| 形态 | 为什么必须拒 |
| --- | --- |
| ``{"t": "译文"}`` | "有译文但没索引"，收了会让调用方以为成功而**丢整批** |
| ``{}`` / ``{"原文": ""}`` | 解析"成功"但没内容 |
| ``{"a": 1}`` / ``{"a": None}`` | 值不是字符串，不适用新判据 |

### 10.4 ★ 写这批测试时我自己错了两次（都被测试立刻抓出）

1. 把 ``"0"`` 放进"单字符键必须被拒"的参数表 —— 但 ``"0"`` 是**数字键**，
   由数字键分支正常接受；
2. 断言独立的 ``{"i": 0, "t": "译文"}`` 为 `True` —— 实际是 `False`
   而且**是对的**（那里 `i` 被当数字键、值为 `0` ⇒"有键没译文"）。
   真实批条目**永远包在 list 里**，正确断言是
   ``_looks_useful([{"i": 0, "t": "译文"}]) is True``。

⇒ 两次都是"我凭印象写断言，而不是先确认数据形态"。
**先确认形态，再写断言。**

### 10.5 影响面（如实）

该形态在整轮里只出现 **1 次**（频率低），但**一旦命中就是该条目彻底丢失**
（走完三次重试仍失败 ⇒ 保留原文）。属于"低频、单次伤害大"。

## 11. #45 守望模式的三处安全加固（"后续新加游戏"必需）

用户需求是"自动对 newlytransport 翻译，**包括后续新加游戏**"。
"后续新加"就要求守望模式**能长期跑、能重启**，于是查出三个真问题。

**状态：v1.5.1 已修。**

### 11.1 守望状态原本只在内存里 ⇒ 重启即整库重跑

原来 `seen` 是个局部 set。重启一次，库里**所有**游戏都被当成"新出现"
而重跑一遍 —— 而全库跑一次要很久。

修：状态落盘到 ``D:\NovaLoc\watch-state.json``。
**先落盘再处理** —— 万一处理中崩了/断电，重启后不会把"已经看过的"
又当新游戏。

### 11.2 ★ 没有一份备份是"最初的原版"

`_unique_backup_dir` 保证"每次写回各有自己的目录"，于是第二次写回会
新建目录、又写一遍 ⇒ **每份备份备份的都是"上一次被改过的版本"**，
想回滚到出厂状态时**回不去**。

修：新增 `preserve_pristine_backup()`，写回**之后**立刻调用，
把该游戏**唯一**的未标记备份目录改名成 ``<名字>-orig-<时间戳>``。

⚠️ **这个函数我自己先写错了两版，都被测试抓出**：

| 版本 | 错在哪 | 后果 |
| --- | --- | --- |
| v1 | 标记"最早的未标记目录" | 第二次写回后又把 **V1 那份**标记成 orig —— **把改过的版本谎称成原版**，比没有备份更危险 |
| v2 | 裸 ``startswith(game_name)`` 匹配 | ``MyGame`` 会吃掉 ``MyGame2`` 的备份 |

最终判据：**仅当该游戏恰好只有一个未标记备份时**才标记；
有两个及以上就**什么都不做**（它们都不是原版）。
名字必须形如 ``<游戏名>-<纯数字/横线后缀>``。

⇒ 宁可**没有** orig，也不能给一个**错误的** orig ——
一个假的"原版备份"会让用户以为能回滚到出厂，实际回不去。

## 12. #46 ★★ 17% 失败率的**最终归因**（推翻了我自己两次猜测）

这一节记录的是"最大质量缺口"的定量归因。**我先后猜错两次**，所以把
每次猜测、判据、以及推翻它的数据都留下来。

**整个覆盖**。

```
源     'Lifia: I have something to say\n「I have to go.」'
模型   '莉菲娅：我有话要说。'        ← 第二行整段没了
补后   '莉菲娅：我有话要说。⟦0⟧'    ← 记号补上了
verify_restored(补后) → fatal=False  ❌ 它只数记号，看不见内容丢失
⇒ 条目被判"已翻译"，丢行静默写回游戏
```

`verify_restored` 看不见是**结构性**的：模型丢掉 `⟦n⟧` 后，还原函数
找不到记号可换，还原后文本里**一个记号都没有** ⇒ 计数 `0 == 0` 相等、
顺序校验也被跳过。"丢整行"只在**一种调用口径**下可见：

| `masked_source` 传什么 | 结果 |
| --- | --- |
| 掩码文本 | `fatal=True` ✅ 抓到 |
| 原文 | `fatal=False` ❌ 漏掉 |

**已修**（v1.6.0）：删掉无门槛的重复实现，只保留带门槛版本，门槛口径
定为结构性的"补后还原**文字量**必须多于模型原始输出"。

### 12.5 ★ 第三次归因：剩下的失败**不是**颜色码

修完之后还有约 **10.3%**（524/5099）失败。我一度以为主因是
"模型丢 `\c[2]`/`\c[0]` 颜色码"，因为 `#1947` 的实测很干净：

```
raw  = '{"0": "被动技能：…降低至一半。", "1": "所需等级：40"}'
取出 = '被动技能：…一半。\n所需等级：40'      ← 文字 + 换行**全对**
guard fatal=True  warnings=['placeholder_count:2->0']   ← 只因颜色码丢了
```

但**离线分类 471 条 failed 条目**（用缓存的 `raw_model_output`，不调模型）
得到的分布**推翻**了这个猜测：

| 类别 | 条数 | 占比 |
| --- | --- | --- |
| `placeholder+丢行`（**真丢内容**） | 401 | **85.1%** |
| `missing_content`（丢行） | 52 | 11.0% |
| `placeholder_only`（**只缺颜色码**，行数没丢） | **8** | **1.7%** |
| `ok_now`（按现在的解析器其实能过） | 6 | 1.3% |
| 无缓存 raw | 4 | 0.8% |

⇒ **"只缺颜色码"只有 8 条（1.7%）**。绝大多数失败是模型**真的丢了一行**，
典型形态是它把 `\c[2]【Passive】\c[0]` 这个"标签行"当成装饰**整行不译**：

```
src='\c[2]【Passive】\c[0]\nMaximum HP increases by 5%. Required LV:1.'
got='【被动效果】最大生命值增加 5%。 需要等级：1'          ← 内容其实完整
```

**如果只采纳这 8 条"仅缺颜色码"的译文，收益上限是 0.2 个百分点。**

> ### ⚠️ 本节结论已被 v1.6.1 部分推翻，请看补充
>
> 上面的 8 条 / 1.7% 量的是**整条路径**上"只缺颜色码就判死"的条目。
> 在整条路径上这个数字**确实很小**，因为 `repair_dropped_masks`
> 已经把它们救回来了（它按锚点/相对位置补回记号，位置确定时才补）。
>
> 但**逐行救援路径**（§3.7）当时**没有调用** `repair_dropped_masks`
> ⇒ 它救回的**每一条带颜色码的对话都在丢配色**。
> 多行对话几乎每行都带 `\c[0]`，所以影响面远大于 1.7%。
>
> 已修（v1.6.1）：逐行救援补上同一步，实测 `perline_style_repaired = 5`
> （12 条真实失败多行条目）。样例：`'男人：\n\c[0]嗯…♡'`。
>
> **教训**：报一个比例之前，必须说清**它量的是哪条路径**。
> 我上次量的是整条路径，却拿它给"所有路径都不用做"下了结论。

### 12.6 剩余缺口的取舍（**需要决策，不擅自改**）

剩下 ~10% 里，绝大多数是"模型把多行条目**压成一行**"。这里有一个
**真实的取舍**，两个选项都不是"全对"：

| 选项 | 玩家看到 | 代价 |
| --- | --- | --- |
| **A. 现状**：判死、保留原文 | 英文（颜色对，看不懂） | ~10% 条目不产出译文 |
| **B. 采纳译文**（内容齐但行数变了） | 中文（内容对，排版变了） | 排版与原文不同；且**无法区分**"压成一行"与"丢了一行" |

⚠️ 选 B 有一个**必须先解决**的技术障碍：`sentence_drop` 与
`length_ratio` 对"压成一行"和"丢内容"**都开火且区间重叠**
（实测：风格性合并在 0.28~0.56，真丢内容在 0.10~0.22 —— 部分重叠）。
项目里已有一次教训：`_is_acceptable_recovery` 就是因此被撤掉的
（比值**没有判别力**）。

⇒ 所以 B 不能靠调阈值实现，需要**结构性的**"内容是否齐全"判据。
在此之前保持 A（现状），并如实记录这 10% 不产出译文。

### 12.7 仍然可做的两件小事（收益已量过，都不大）

1. **`\c[N]` 位置还原**：实测颜色码相对位置偏差中位 **0.196**、P90 **0.640**
   ⇒ 按位置补会把颜色码插进词中间、套错色域。**不按位置补**。
   收益上限 1.7%（见 12.5）。
2. **`ok_now` 那 6 条**：按现在的解析器其实能过 —— 说明它们是**旧版本
   留下的失败记录**，重跑一遍就会变成成功。`--only-pending` 已覆盖。

## 13. #47 ★★★ "备份目录存在"**不能**证明写回发生过 —— 我的验收判据错了

这一节记录一个**方法论**错误，因为它的误导性很强：错误判据给出的
"通过"结论看起来完全可信，而实际什么都没验证。

### 13.1 我原本的判据（错）

`src/novaloc/cli.py` 的 `auto` 在写回后会调用 `preserve_pristine_backup`，
把"最初的原版"标记成 `*-orig-*`。我据此认为：

> "备份目录的存在 = 写回发生过的**硬证据**（文件系统事实，不靠日志）"

于是查了 `D:\NovaLoc\_novaloc_backup`，看到 **3 个备份目录、共 187 个文件**，
就准备把它当作"端到端写回已验证"。

### 13.2 实测把这个结论推翻了

用 sha256 逐文件比对"备份 vs 现盘"：

| 游戏 | 相同 | **不同** | 备份有而现盘无 |
| --- | --- | --- | --- |
| `Dungeon And Darkness-Steam` | 61 | **0** | 0 |
| `Midnight Exhibitionist DX` | 126 | **0** | 0 |

**187 个文件全部逐字节相同**。而现盘里
`Midnight Exhibitionist DX\data\CommonEvents.json` 有 **13356** 个中文字符。

⇒ 只有一个解释：**那个游戏本来就已经是中文**（别的工具/别人汉化的）。
`changed_files()` 返回空集 ⇒ `write_back` 在 line 408 直接 early-return
⇒ **一个字节都没写**，只留下一个**空的**备份目录。

三判据交叉验证（`.scratch/_who_translated.py`）：

1. 备份里的 `data/CommonEvents.json` **也是中文**（13356 个）⇒
   备份到的是**译文版**，不是原文；
2. 该文件的 mtime = `2026-03-20`，而备份目录建于 `2026-10-02`；
3. `workspaces/*/out` 里**没有**任何文件与现盘逐字节相同
   ⇒ 现盘的内容不是本工具产出的。

### 13.3 两个死胡同（都试过，都错）

* **拿"备份里是原文"当判据** —— 死循环：要判断备份里是不是原文，
  就得先知道原文是什么，而那正是待证的事。
* **拿 mtime 当判据** —— 无效：`batch.py` line 428 用的是
  `shutil.copy2`，它**会保留 mtime**。所以"mtime 没变"既可能意味着
  "没写"，也可能意味着"写了但 mtime 被原样带过来" ⇒ **没有判别力**。
  （我一度想用"备份 10-02、游戏文件 07-06"这个时间差下结论，幸好没写进文档。）

### 13.4 正确判据（已实现为 `.scratch/_e2e_writeback.py`）

必须在**可控环境**里制造"跑之前"的状态，然后比"跑之后"：

1. 把候选游戏复制进**临时库**，用**独立数据根**（`NOVALOC_DATA_ROOT`），
   不碰真实库；
2. 跑 `auto --limit 1`；
3. 三项判据**全中**才算通过：
   * **【1】现盘内容相对"跑之前"变了**（sha256 差异 > 0）——
     这一项是**唯一**能证明"写回发生"的；
   * **【2】备份里的文件与"跑之前"逐字节相同** —— 证明备份到的是**原文**
     （只有这一项 = 只备份没写回，正是 13.2 那个坑）；
   * **【3】现盘中文数显著增加** —— 证明写进去的是**译文**而不是别的改动。

### 13.5 顺带发现的第二个坑：验证用的游戏必须"文本在明文里"

第一次我挑了 `Sloppy_Fields_0.5.1.3_-_Subscribestar`（确实未汉化、49.8 MB），
结果：

* 被识别成 `loose`、只抽出 **3 个条目**；
* 改的却是 `options.ini`（**40 → 37 字节**，疑似动了行尾/尾空白）。

它的真实文本在 GameMaker 的 `data.win` 里，**本工具不解包那个格式**。
⇒ 拿它验证会得到**假阳性**："写回 1 个文件"这句话是真的，
但**该改的 `data.win` 一个字节都没动** —— 而"写回"对玩家的意义
恰恰是"译文进了游戏"。

**判据修正**：验证写回必须挑"文本在明文 JSON 里"的游戏（RPG Maker），
否则验的是"文件被碰过"，不是"译文进了游戏"。

> 另注：`options.ini` 40→37 字节这个**非预期改动**本身值得单独查 ——
> 它说明 `apply` 阶段会改写与文本无关的配置文件。已记为待查项。

### 13.6 ★ 那个 `options.ini` 改动已查清并修复（v1.6.2）

**根因是行尾被改，不是内容被改**（`.scratch/_ini_change_probe.py` 实测）：

    跑之前  b'[Windows]\r\nSleepMargin=10\r\nUsex64=True\r\n'   40 字节
    跑之后  b'[Windows]\nSleepMargin=10\nUsex64=True\n'        37 字节
                            ↑ 三个 \r 全没了

`Path.read_text()` 不传 `newline=` 时底层用 `newline=None`
⇒ **读进来时 `\r\n` 就被翻译成 `\n`**，之后
`write_text(newline="")` 忠实地把已经翻译过的行写出去
⇒ `\r` **在读取那一步就丢了**。修法是读、写**两侧成对**加 `newline=""`，
共修 5 处：`loose.py`、`unity.py`（`_apply_lines`/`_apply_po`/`_apply_kv`）、
`renpy.py`。修完实测 `options.ini: 未改（40 字节）`。

**影响面比 `.ini` 大**：`loose`/`unity`/`renpy` 的按行替换写回全都如此，
凡是原文用 CRLF 的 `.txt`/`.cfg`/`.xml`/`.rpy` 都在被静默改行尾。
它还制造"假阳性改动"（哈希变了、内容没变），排查时极易被带偏 ——
我自己就差点把"字节变了"当成"写回发生了"。

回归测试：`tests/test_writeback_newline_preservation.py`（10 例），
既有行为测试也有源码级守卫（防止以后新增写回路径再犯）。

### 13.7 ★ 端到端写回**已验证通过**（v1.6.2，最小夹具）

用 `.scratch/_e2e_min.py`（**最小确定性夹具**）跑出的结果：

    夹具  MinimalRPG（RPG Maker MV，2 个文件）
          data/CommonEvents.json   3 句英文台词
          data/System.json         currencyUnit = "G"

    auto --limit 1 → 退出码 0

    【1】现盘内容有变化 : 2 个文件被改写                 ✅
    【2】备份目录       : MinimalRPG-orig-20261003-162153 ✅（-orig- 标记有）
                          与"跑之前"逐字节相同 2/2       ✅ 备份是原文
    【3】现盘中文增加   : 0 → 20                          ✅

    实际写进去的译文：
      data/CommonEvents.json  "你好，旅行者。" "欢迎来到村庄。" "请帮我一下。"
      data/System.json        "currencyUnit": "金币"
    两个文件都与工作区 out/ 里的产物**逐字节相同**。

⇒ **"自动就地汉化 + 先备份 + 标记原版"这条链路是通的**，
而且是靠"现盘相对跑之前变了"这个判据证明的，不是靠日志。

⚠️ 但请连同 §13.1~13.6 一起读：这个结论**只对"文本在明文 JSON 里"的
引擎成立**。GameMaker（§14）那类仍然什么都没写进去。

## 15. #49 ★★★ 颜色码丢失被判"占位符崩掉" —— 一个游戏 **47% 的对话被丢成空白**

### 15.1 现象

工作区 `f4b03ca791a9`（9,777 条的游戏）失败记录：

| 项 | 值 |
| --- | --- |
| 失败 | 2,245 条 |
| 其中同一原因 | **2,239 条** |
| 原因 | `placeholder_broken: 丢失占位符：['\c[0]', '\c[2]', '⟦0⟧', '⟦1⟧', '⟦2⟧']` |

而模型输出是**完整可用的中文**，只是没保留颜色码：

    源    '\c[2]【Passive】\c[0]Chance to hold on when receiving fatal damage. \nRequired LV:30.'
    模型  '【被动】当受到致命伤害时，有几率保持防御。'

判死 ⇒ `target = ''` 写回 ⇒ **玩家看到空对话框**。
47% 的对话就这么没了 —— 而它们本可显示成"没有颜色的正常中文"。

### 15.2 根因：两处判据**完全相反**，错的那处更早生效

| 位置 | 对 `\c[n]` / `\i[n]` 的判定 |
| --- | --- |
| `guards._STYLE_ONLY_PLACEHOLDER_RE` | **样式** |
| `placeholders._is_style_only_mark` | **内容** |

`guards.py` 那里甚至**写明了**理由：

> `\c[0]`（颜色）、`\i[4]`（图标）、`\|`（停顿）—— 只是**配色/停顿**变了，
> 文字一个字不少 ⇒ **不该判死**

但 `placeholders` 的判定**更早生效**（`verify_restored(...).fatal`
在 `guards.guard()` **之前**）⇒ 那条宽容规则**永远没机会执行**。

⇒ 又一个"同一条判据在两个地方实现、结论相反、只有一个能生效"的坑
（与 §10 记的那两个同类）。

### 15.3 还有一层：同一个槽位被**判了两次、结论相反**

`verify_restored` 第 4 层校验算的是
`_is_droppable_mark(slots[i])`，**只对内容类**报缺失。
但它把结果写成 ``⟦i⟧`` 塞进 `check.missing`，
接着 `fatal_missing` 又拿 ``⟦i⟧`` 去问 `_is_droppable_mark`：
``⟦1⟧`` 既不在样式表里、也不匹配 `\[cCiI]\[\d+\]`
⇒ 被判成**内容类** ⇒ 致命。

直接后果：`repair_dropped_masks` 已把 `\c[2]` 和换行补回、
只剩 `⟦1⟧`（= `\c[0]`）没补 ⇒ 判死 ⇒ 对话变空白。

### 15.4 修法（三处，缺一不可）

1. `_is_style_only_mark` 认颜色/图标（`\c[n]` `\C[n]` `\i[n]` `\I[n]`），
   与 `guards` 对齐。⚠️ `\V[n]` `\N[n]` `\S[n]` `\P[n]` `\D` `\R` `\$` `\G`
   **仍判内容** —— 游戏会把它们替换成真实数据。
2. `fatal_missing` 改用 `_is_droppable_mark`（顺带放过 `%%`）；
   两处判据从此走**同一个函数**。
3. `PlaceholderCheck` 记住 `slots`，把 ``⟦i⟧`` 解回 `slots[i]` 再判；
   解不开或越界时**保守判死**。

### 15.5 验证：拿**真实失败条目**重放（`.scratch/_replay_failures.py`）

用每条失败记录里存下的 `meta.raw_model_output` 重放当前判定链：

    失败条目：2,035
    ✅ 可救回     : 1,960   （96.3%）
    ❌ 仍判死     : 70
    （没有 raw 输出、无法重放）：5

    ✅ 安全检查通过：救回的条目里**没有**一条丢内容类记号

★ **最后那条才是最要紧的。**"救回得多"不等于"修对了" ——
  如果救回的条目里混着"真的丢了 `\V[1]`"的，那就是把判据废掉了。
  所以这份统计里专门加了这一项，它必须是 **0**。

剩下 70 条逐条看过，属于**应该**判死的两类：

* 模型回了垃圾（源是长插件标签，输出就俩字 `'确认'`）；
* 真的丢了内容类记号，或 `order_changed`（`\mhp[3]`/`\atk[2]` 这组
  被剥掉后编号顺序乱了）。

## 17. #51 让守望服务跨重启活下来 —— 以及它在**验证**上有多难

### 17.1 需求

「自动对新建文件夹翻译」要真正常驻，就必须在**每次登录**后自己回来 ——
否则用户重启一次，整条自动化就静默失效了，而且**没有任何提示**。

### 17.2 为什么是「启动文件夹」而不是计划任务

`Register-ScheduledTask` 在这台机器上返回 `Access is denied`（需要管理员），
而本会话**审批提示是关闭的**，没有提权路径。启动文件夹不需要提权，
且正好匹配真实需求：**用户登录期间**守望服务在跑。
代价是不能在登录前运行 —— 对桌面汉化工具无所谓。

### 17.3 ★★ 这条路径上连续踩了三个坑，而且**两个都"看起来能用"**

| 写法 | 实测结果 |
| --- | --- |
| `.vbs` + `WScript.Shell.Run(cmd, 0, False)` | **弃用**。`cscript` 打印了 `PROBE_DONE`，但它本该写出的文件**根本不存在**；还对**已存在**的目录报"路径未找到"。排查成本远超收益。 |
| `start "NovaLoc Watch" /min launcher.cmd` | 前台**不返回**；守望随调用者一起死 |
| `start "" /b cmd.exe /c start … /min launcher.cmd` | 前台**立刻返回**、父进程链已断 —— **但守望仍然随调用者一起死** |
| `Start-Process -FilePath launcher.cmd -WindowStyle Hidden` | ✅ 用到现在 |

第三行是**最危险的那个**：它让"父进程已退出"成立，
而"父进程链断了"**不等于**"进程组断了"。

### 17.4 为什么这个坑特别难自动化验证

**本仓库的工具链在任务结束时杀掉整棵进程树。**
于是"从后台任务里测出守望存活"这件事**根本不成立** ——
你测到的永远是"被杀了"，无论实现对不对。

我因此**误判过一次**：看到父进程链断开就宣布"已脱离"，
下一轮真正的 teardown 又把它带走。

⇒ 结论：**这类"常驻进程能否独立存活"的问题，只能在真实登录
（或正常关闭控制台）下验证。** 不要用后台任务冒充。

### 17.5 为什么快捷方式用 `-EncodedCommand`

快捷方式的 `Arguments` 是一个**字符串**，而仓库路径含中文
（`D:\personal tasks\小工具\翻译工具`）。在
「cmd → powershell → 快捷方式 → powershell」这条链上手工拼引号必然翻车。
`-EncodedCommand` 收一个 base64（UTF-16LE）**整块**参数：
一个参数、零引号、零代码页参与。

⚠️ 顺带一个**观察假象**：把 base64 解码后打印到控制台会显示成
`С����` 之类的乱码，看着像"路径坏了"。实际是控制台用 GBK 渲染。
**验证时要解码后写文件再用 UTF-8 读**，别信终端。

### 17.6 交付物

| 文件 | 作用 |
| --- | --- |
| `scripts\launch-watch-hidden.ps1` | 隐藏窗口启动守望（唯一可信的 spawn 路径） |
| `scripts\install-autostart.cmd` | ASCII 包装（cmd.exe 按 OEM 代码页解析 `.cmd`） |
| `scripts\install-autostart.ps1` | install / remove / status，写快捷方式 |
| `scripts\fix-ps1-bom.ps1` | 新增 `.ps1` 后**必须**跑一次（PS 5.1 要 UTF-8 BOM） |

## 18. #52 反复失败的条目**永远重试**

### 18.1 现象

`stage_translate` 的跳过判据是

    prev is not None and prev.is_done and prev.target.strip()

而 `is_done` 只认 `TRANSLATED / REVIEWED / LOCKED`。`FAILED` **不满足**
⇒ 每跑一次 `translate` 就重试一次，**永远如此**。

### 18.2 代价不只是浪费

* 全库 **174** 个游戏、单条 **20~60 秒**；
* "后续新加游戏"的守望服务在等**同一个**热模型 ——
  实测两个进程并行会让 `POST /api/chat` 大面积 **300 秒超时**
  （`auto` 退出码 -1）。**串行比并行快。**

### 18.3 ★ 不能用 `entry.retries`

它看着像现成的计数器，但 provider 在每次重试时把它**重置**成 0/1
（`ollama_provider.py` 的 `entry.retries = 0` / `= 1`）。
实测 **1,140 条失败条目里全是 0** —— 根本累积不起来。

⇒ 计数放 `meta["fail_streak"]`（会落盘），上限 `_MAX_FAIL_STREAK = 2`。
用 2 而不是 1：`provider_error`（`空响应`、`编号不连续`）是**真会自愈**的
瞬时故障。跳过**必须报出来**，静默跳过等于把失败藏起来。

### 18.4 ★★ 差点又踩一次：计数必须在**合并之前**读旧值

第一版在合并**之后**读：

    merged = {**existing, **{e.uid: e for e in entries}}
    for e in entries:
        prior = merged[e.uid].meta["fail_streak"]   # ← 已经是**新**对象

合并后旧 `meta` 已被覆盖 ⇒ `prior` 永远是本轮自己的值
⇒ 计数**永远是 1** ⇒ 上限**永不触发**，而一切看起来都正常。

`tests/test_translate_fail_streak.py` 用**位置断言**钉住这一点
（自增语句的位置必须早于合并语句）。

### 18.5 给这台机器上现有工作区的一次性回填

计数器上线**之前**留下的失败条目，`meta` 里没有 `fail_streak`，
所以还要再浪费两轮才会被跳过。工作区 `f4b03ca791a9` 有 **1,140** 条这种。
（回填脚本见 `.scratch/`；必须在 `auto` 不在写该文件时跑。）

## 19. #53 ★★ "译文与原文讲的是两件事"——排查到底，结论是**对齐没坏**

### 19.1 现象

全库抽查译文质量（`.scratch/_quality_sample.py`，按 uid 哈希取 1/97 间隔）时，
出现一条看着**极严重**的：

```
源  'Overwhelmed by pleasure and exhaustion, Mashiro could no longer think.
     The office worker held her in his arms as she collapsed on the spot.

译  '前方可能导致游戏过关，取决于你的选择。\n我们建议你保存游戏。\n※存档菜单将打开。'
```

译文的**长度与形状都对**（三行中文），所以现成的守卫**全部放行**：
占位符完整、长度比正常、没有异种文字、没有重复。但它讲的是"存档提示"。

**如果这是成片的条目错位，那就是本项目最严重的缺陷** ——
所有对话都会对错人。所以必须查到底，不能"看着像幻觉就算了"。

### 19.2 我试错的两个判据（都废了，记录以免后人重走）

| # | 判据 | 结果 | 为什么错 |
|---|------|------|----------|
| 1 | 源文的**专有名词**在译文里找不到任何音译痕迹 | 报 **12.27%**（2981/24304） | `真实现手` / `真酱` / `真梨` **都是 `Mashiro` 的译名**，只是译法不统一。我的音译字表没收这几个字 ⇒ 几乎全是误报 |
| 2 | **A 的译文 ≈ B 的原文**（长度比 + 首字母音译） | 报 **907,835** 处 | 这个游戏**几乎每条都以 `Mashiro:` 开头**，而 `M` 在首字表里映射到"马玛米姆梅摩莫真"⇒ **任意两条都能"匹配"** |

> **教训**：凡是用"语义相似 / 音译"的判据，在角色名反复出现的语料上
> 都会被刷爆。**只有精确字符串的观察才可信。**

### 19.3 精确定位：那条样本的真实来源

用 `.scratch/_align_root.py` 按 uid 里的指针回到**原游戏 JSON** 取值：

```
条目 #1125  uid = CommonEvents.json:/13/list/331/parameters/0
  工作区记录的 source = 3 行合并（被快感淹没…/他抱住她…/他带她回自己家）
  原游戏 /13/list/331/parameters/0 的真值 = 只有第 1 行
```

再看原文件的结构：

```
[330] code=101  ''                                    ← 打开消息框
[331] code=401  'Overwhelmed by pleasure and exhaustion, ...'
[332] code=401  'The office worker held her in his arms ...'
[333] code=401  'He brought her straight to his home.'
```

⇒ `/331` `/332` `/333` 是**同一个消息框的三行**。
`siblings` 机制（`rpgmaker.py:738`）把它们**合成一条**翻译，
写回时由 `_split_across_slots` 拆回各槽位（`rpgmaker.py:1216`）。

**所以"合并"是设计，不是 bug。** 问题只可能是：
**拆分后的片段有没有写回各自的指针。**

### 19.4 为什么这里是对的（而且早有回归测试）

```python
pointers = [u.location.pointer, *u.location.siblings]
pieces = _split_across_slots(text, len(pointers), u.source)
for ptr, piece in zip(pointers, pieces, strict=True):
    self._set_pointer(obj, ptr, piece)      # ← 每片写各自的指针
```

`zip(..., strict=True)` 保证片数与指针数**必须相等**，不会静默错配。

而且这不是新代码 —— `tests/test_rpgmaker_command_format.py` 里
**早就有一对镜像用例**，正是钉这个失败方式：

* `test_apply_writes_split_translation_to_every_slot`：
  两格合并的译文必须**拆到两格**（只写第一格 ⇒ 玩家看到"一中文一英文"）；
* `test_apply_never_duplicates_text_across_slots`：
  反过来，**不能**把整段往每格都写一遍（消息框显示两遍，"每格都有中文"看着像成功）。

跑过：`16 passed`（`-k "split or apply or roundtrip"`）。

## 20. #54 四项流程优化：断点续跑 / 初筛 / 模型提速 / 动态资源占用

用户提的四条，逐条落地。**其中第 3 条（更快的模型）实测后结论是"做不到"**，
所以这一节的重点是"我试了什么、为什么不行、剩下的杠杆是什么"。

### 20.1 断点续跑（本来就有，只是没讲清）

用户问"随时关机开机不会过多影响翻译"。现状：

* **工作区复用**：`Workspace.find_for_game` 按游戏目录找已有工作区，
  不新建（早先无条件 `create` ⇒ 每次重启都从零开始，实测堆了 4 个工作区）；
* **增量落盘**：`_CHECKPOINT_INTERVAL_S = 15.0`，崩溃/断电最多丢 15 秒成果；
* **跳过已完成**：`stage_translate(only_pending=True)` 只处理没译好的条目。

⇒ 重启后是**接着跑**，不是重跑。**不需要改代码。**

### 20.2 ★ 真正需要改的是"别打扰正在玩的游戏"

这是我必须主动提出来的隐患 —— 用户说"我随时玩对应文件夹的游戏时不会影响"，
而当时的实现**在翻译完成后会覆盖原游戏文件**。

后果比"翻译出错"严重得多：

* 游戏正在读文件 ⇒ 读到写了一半的内容 ⇒ **崩溃**；
* 游戏退出时把内存里的旧数据写回存档 ⇒ 资源被换了、存档还是旧的
  ⇒ **存档损坏**，而这是**不可逆**的（备份只能退回原版，
  玩家那一刻的进度保不住）。

**修法**（`cli.py` 的 `process()`，写回之前）：

```python
running, who = _busy.is_game_running(ent.path)
if running:
    ent.status = "deferred"
    ent.message = "检测到游戏正在运行（…），**已跳过写回**以免破坏存档。"
    return
```

判据是**"游戏进程的 exe 在这个游戏目录下"**（`busy.is_game_running`），
这是结构性事实，不依赖游戏窗口标题怎么命名（很多 galgame 标题只有角色名）。

**前缀陷阱**：`C:\Games\Foo2` 的字符串以 `C:\Games\Foo` 开头。
用 `str.startswith` 会把玩 `Foo2` 判成"`Foo` 在运行"。
所以实现按**路径分量**比较（`p == gd or gd in p.parents`），
`tests/test_busy_gate.py::test_is_game_running_rejects_sibling_with_shared_prefix`
钉住这一点。

新状态 `deferred`（"游戏在运行，已缓写回"）单独出现在汇总表和报告里，
不再混进 `failed`。

### 20.3 初筛：三层，前两层在扫描期，第三层在抽取后

| 层 | 判据 | 在哪做的 | 省掉什么 |
|---|---|---|---|
| ① 已是中文 | `detect_already_chinese` | 扫描期（早就有） | 整个流水线 |
| ② 引擎不认识 / 被排除 | 注册表 + `--only/--skip/--max-size-mb` | 扫描期（**本轮新增**） | 整个流水线 |
| ③ 抽不到文本 | `ws.load_units()` 为空 | 抽取后（**本轮新增**） | 扫贴图/翻译/字体/质检/回写 |

第 ③ 层的真实浪费（改之前）：

* `stage_extract` 发现 0 条 ⇒ `ok=False` ⇒ 抛 `PipelineError` ⇒ 被记成 **`failed`**；
* 但在它之前 **`stage_images_scan` 已经跑完了** —— 要扫遍全部贴图，
  大游戏几分钟到十几分钟。**纯浪费。**
* 而且记成 `failed` 会让用户以为"工具坏了"，实际只是"文本不在明文里"。

改成在 `run_pipeline()` 里循环时检查：轮到 `images_scan` 而**还没有 units**
就直接 `break`，然后统一标成 `no_text`。

**实测效果**（`--dry-run`，不写任何文件）：

```
待处理 174　已是中文 19　识别失败 0
待处理引擎分布：unity 106　rpgmaker 39　loose 25　unknown 4
初筛 --skip ['loose']：174 → 149 个
初筛 --max-size-mb 600：149 → 31 个
```

`--skip loose` 的依据是实测：**loose 层 25 个游戏平均只抽出 26 条文本**
（见 `.scratch/_eta_sample.py`），基本没有收益。
`--max-size-mb` 的依据是"条目数与体积强相关"（1 GB 的游戏动辄上万条），
先跑小的能让用户**早点看到成果**，也便于小样本验收后再放开全量。

### 20.4 ★★ 更快的模型：实测**不存在**（试了 3 个，全部否决）

用户要求"快得多的模型"。我把库内已有的和能下载的都测了
（同一批 24 条真实未译文本，结果表见 `docs/ACCEPTANCE.md` §七之二）：

| 模型 | 参数量 | 成功 | 秒/条 | 结论 |
|---|---|---|---|---|
| `translategemma:4b` | 4.3B | 10/24 | **4.65** | 当前，最快可用 |
| `kaelri/qwen3.5-mt:2b` | 2.3B | **0/24** | ∞ | **不可用** |
| `demonbyron/HY-MT1.5-7B` | 7.5B | 13/24 | 8.80 | 慢一倍 |
| `hunyuan-mt-abliterated:7b` | 7.5B | 7/24 | 21.95 | 慢 4.7 倍 |

三个反直觉的结论，都值得记住：

1. **"翻译专用"不等于"更快"**。7.5B 混元翻译批次成功率**更高**
   （13/24 vs 10/24），但单次往返慢一倍 ⇒ 总 **秒/条更差**。
   参数量的物理成本压不过专用性的收益。
2. **2B 模型完全不可用**：它对"数字键 JSON 对象"协议返回**空内容**，
   三次重试全失败，白烧 **546 秒**。这是**协议兼容性**问题，不是速度问题
   ⇒ **不能靠"换更小的模型"提速。**
3. 之前一个会话已经量过**批次大小**（4/10/20）：批次 10 最优，
   但相对默认值只快约 10%，**量级上不解决问题**。

⇒ **单卡串行就是硬上限。** 两个翻译进程并行**更慢**（300 s 超时 +
`auto` 退出 `-1`），因为 `max_loaded_models=1` 把它们排成一队而各自带超时。

**剩下的杠杆只有三个，都需要用户决定**：
① 按体积先跑小的（`--max-size-mb`）；② 换更大的卡/多卡；
③ 接受跨月长跑，靠断点续跑 + 忙闲让路当常驻服务。

### 20.5 动态资源占用：协作式"让路闸门"

用户要求"机器空闲时占用多，有别的需要资源的时候释放出来"。

**为什么不能靠杀进程**：翻译跑到一半被 `taskkill`，正在写的那一条会丢；
更糟的是**回写阶段被杀** ⇒ 游戏目录半新半旧 ⇒ 存档可能损坏。
所以用**暂停闸门**：翻译循环每批之前问一次"该让路吗"，该让路就**睡**。

**信道用文件**（`<数据根>/_pause`），因为翻译进程和监视器是两个独立进程，
且监视器要跨重启存活 —— 文件是唯一不需要额外依赖、重启后依然有效的信道。
副作用但有意保留：**用户可以手动 `New-Item _pause` 立刻让路。**

**判据用三个信号的组合**（`src/novaloc/translate/busy.py`）：

| 信号 | 单独用会怎样 |
|---|---|
| CPU > 50% | 打游戏时 CPU 可能只有 20%（游戏靠 GPU）⇒ 漏判 |
| GPU > 55% **且**前台是外部程序 | 只用 GPU 会把 **Ollama 自己**判成忙 ⇒ 死锁 |
| 有游戏进程在跑 | 最硬的一条，**必须无条件让路** |

#### ★ 实测踩到的坑：`llama-server` 漏网

Ollama 0.35 把推理放在**独立的 `llama-server.exe`** 里，路径
`...\ollama\bin\lib\ollama\llama-server.exe` —— **进程名里既没有
"ollama" 也没有 "python"**。我最初的正则 `ollama|novaloc|python`
匹配不到它，于是实测出现：

```
gpu_percent(exclude_own=True)  -> 82.0   ← 没排掉 llama-server
gpu_percent(exclude_own=False) -> 74.3
```

**"排除自家后反而更大"在逻辑上不可能** —— 这个反常就是线索。
修好后（pid 65456 = `llama-server.exe` 被正确识别）：

```
GPU 排除自家:    7.3     7.3     8.0      ← 真实的外部占用
GPU 不排除:     82.4    81.9    83.5      ← 其中约 74 点是 Ollama 自己
```

⇒ 教训：**判"谁在用 GPU"必须把推理服务进程也算成"自家"**，
否则会自己把自己永久暂停。`tests/test_busy_gate.py` 里
`test_own_process_names_are_recognised` 与
`test_high_gpu_from_our_own_foreground_does_not_pause` 两条镜像用例钉住它。

#### 闸门的真实效果（决定性验证，`.scratch/_gate_verify.py`）

**先说清楚：我在这件事上连续测错过三次**，所以最后把口径写死了。

| 次数 | 做法 | 我当时的结论 | 为什么错 |
|---|---|---|---|
| 1 | 对**旧进程**放闸门，看 30 秒 | "闸门生效" | 旧进程代码里**根本没有** `_pause` 逻辑（grep 全仓库确认）。那 30 秒的 0 只是**批次之间的空档** |
| 2 | 对**新进程**放闸门，看 75 秒 | "闸门无效" | 那是在飞的批次跑完了 |
| 3 | 无闸门看 60 秒当基准 | "基准 0，比较无意义" | 这个判断本身是对的 |

**根因**：这个模型**有时一批要算 2~3 分钟**（实测 `entries.jsonl`
2.5 分钟没动，而 `llama-server` 的 CPU 时间在涨）。
用 60~75 秒的窗口去测"有没有新译文"，**噪声比信号还大**。

⇒ 最终口径：三段各 **180 秒**（是实测最慢批次约 150 秒的 1.2 倍以上），
而且放闸门后**先等 180 秒**让在飞批次落地再开始计。

结果：

```
无闸门: 96 条 / 180s = 32.0 条/分钟
有闸门:  0 条 / 180s =  0.0 条/分钟     ← 完全停住
恢复后: 97 条 / 180s = 32.3 条/分钟     ← 完整恢复
```

⇒ **能停住、也能恢复**，且闸门本身没有性能损失（32.0 vs 32.3）。

#### 闸门放在**批次边界**的理由

不放在"随时打断"，因为一批就是一次 Ollama 往返，
打断它会浪费已经算出来的 token。代价是最多**延迟一批**（实测 2~3 分钟），
对"让路给用户打游戏"这个场景完全可以接受。

#### `_pause` 文件的编码坑

一开始写纯 `utf-8`，用户用 **PowerShell 5.1 的 `Get-Content`** 看是乱码：

```
文件内容: 浜哄伐娴嬭瘯锛氭ā鎷熸満鍣ㄥ繖
```

PS 5.1 默认按 **ANSI(GBK)** 解码无 BOM 的文件。改成 **`utf-8-sig`** 后正常。
（另一种做法是"只写 ASCII"，但那样就没法在文件里说明**为什么**暂停，
理由里必然有中文 ⇒ 排查更难。）

#### 监视器的部署

* `src/novaloc/translate/busy.py` —— 判定与闸门（可 `python -m` 直接跑）；
* `scripts/watch-busy.ps1`（UTF-8 **BOM**）+ `scripts/watch-busy.cmd`（**纯 ASCII**）；
* `scripts/install-autostart.ps1` 改成**表驱动**，一次装两个快捷方式：
  `NovaLoc 守望服务.lnk` 与 `NovaLoc 忙闲监视器.lnk`。

⚠️ **两个自启服务都还没在"真实登录"下验证过** ——
和 ROADMAP §17.3 同一个问题：从后台任务里无法证明进程能否活过会话拆除。
`-EncodedCommand` 的内容已经**解码核对**过（不要信任终端里显示的乱码）。

### 20.6 ★★ Windows 脚本的三条编码/解析硬要求（本轮全部踩了一遍）

这一节独立出来，因为这三个坑**每条都花了很久才定位**，而且表现都像
"文件损坏"或"进程没起来"，完全联想不到真正原因。
现在有 `scripts/check-script-encoding.py` 自动检查（进了仓库）。

#### ① `.cmd` 必须 **CRLF** 行尾

我用编辑器写出 LF-only 的 `.cmd` 后，cmd.exe **按字节偏移错位地读每一行**，
把行首几个字符吃掉：

```
REM NovaLoc busy-watcher launcher (ASCII ONLY).
  -> 'sy-watcher' is not recognized as an internal or external command
setlocal
  -> 'use' is not recognized ...
```

**看起来像文件损坏**，实际只是行尾。定位过程：先怀疑中文路径、再怀疑
`%~dp0`、再怀疑变量展开，最后用 Python 数了字节才看到
`CRLF 行数=0  仅LF 行数=19`。

#### ② `.cmd` 必须是**纯 ASCII**（中文只放 `.ps1`）

cmd.exe 按 OEM 代码页（本机 GBK）解析 `.cmd`。UTF-8 中文会被当 GBK 解，
容易在字符串中间拼出 `"` 或 `&` ⇒ 语法崩。
我第一版 `watch-busy.cmd` 里有 552 个非 ASCII 字节（大段中文注释），
另外一处中文在 `start "..."` 的窗口标题里把命令行切断了。

⇒ 规则：**`.cmd` 写 ASCII，注释用英文；中文解释放 `.ps1` 或 Python。**

#### ③ `.ps1` 必须 **UTF-8 with BOM**，且**注释里也不能出现「$名:」**

两条不同的问题：

* **BOM**：PowerShell 5.1 读无 BOM 文件时按 ANSI(GBK) 解码，中文乱码。
  本轮我在编辑 `watch-busy.ps1` 时把 BOM 弄丢了，导致中文全部乱码。
* **`$名:` 形状**：`"$round:"` 会被当成**驱动器引用**（`$drive:` 语法）：

      Variable reference is not valid. ':' was not followed by a valid
      variable name character.

  修法是写 `${round}:`。**但真正的教训是**：我改完之后，
  为了解释原因在**注释里**原样写了 `"$round:"` ——
  **注释不是安全区**，照样触发同一个 ParserError。
  文件里连注释都不能出现那个形状。

#### 附带发现：`>>` 重定向出来的是 **UTF-16LE**

`cmd /c "powershell.exe ... >> log"` 写出的文件开头是 `ff fe`（UTF-16LE BOM）。
之后所有按 UTF-8 读的工具看到的都是乱码。

⇒ 结论：**不要用 shell 重定向收集 PowerShell 的输出**，
让 Python 侧用显式 `encoding="utf-8"` 自己写日志。

（这与早先记下的"只有 `cmd /c ... >> out` 是字节透明的"并不矛盾：
那条讲的是 **cmd 自己**输出时的行为；这里是 **powershell.exe** 在写，
它选了 UTF-16。）

#### 工具化：`scripts/check-script-encoding.py`

```
python scripts/check-script-encoding.py          # 只检查
python scripts/check-script-encoding.py --fix    # 检查并修 BOM / 行尾
```

它做三件事，每件都对应上面一个坑：

1. 数 CRLF / LF-only（`.cmd`）；
2. 找非 ASCII 行（`.cmd`）；
3. 查 BOM **并用 PowerShell 自己的 `Parser` 做语法校验**（`.ps1`）——
   语法这一项必须用真 Parser，正则判断会漏（`$名:` 这种就是）。

它上线后立刻抓出两个我自己没发现的错：
`watch-busy.ps1` 丢了 BOM，以及一处 `}` 不匹配的语法错误。

#### 日志可证伪：「活着但空闲」与「压根没起来」不能长得一样

监视器最初只在**状态发生变化**时写日志，于是它正常跑着、日志却是**空的**。
这两件事的表现完全一样，我自己都被骗过一次（以为是进程没起）。

⇒ 加了**启动横幅**（无条件写一行当前判定）。
`test` 之外也留了 `--once` 子命令，便于手工确认。

### 20.7 ★★ "关机开机不影响翻译" —— 在修之前答案是**会**

用户直接问过："我关机开机，玩游戏啥的都不会影响翻译吧？"
我核实后发现**两个缺口**，其中一个让翻译会在重启后**永久停住且不报错**。

#### 缺口 1（严重）：自启的服务**拒绝碰积压**，于是重启后翻译就停在半路

* 自启清单里只有**守望服务**，它跑的是 `--watch-only`；
* `--watch-only` 的语义就是"**不重跑库里现有游戏**，只等新游戏"；
* 而全库翻译进程（唯一的 auto）是**手工起的，不在自启清单里**。

⇒ 关机 → 开机之后：

1. 全库翻译进程没了；
2. 唯一自启的守望服务**明确拒绝**处理那 170 多个积压；
3. **而且完全没有任何报错** —— 守望日志一切正常（"已记住 193 个游戏"）。

这正是"静默失效"里最难查的一类：**服务活着、日志正常、活儿没干**。

**修法**：新增 `--backlog`，语义是"配合 `--watch-only`，
**先补完库里积压的待处理游戏**，再进守望循环"。

* 语义上必须显式分开，不能直接改 `--watch-only` 的默认行为 ——
  那个选项是用户可用的，有人确实只想要"只守望"；
* 守望服务改为 `--watch-only --backlog`，于是**一份自启服务同时覆盖
  「积压」和「新游戏」**；
* 代价可接受：每个游戏靠 `only_pending=True` 续跑，已完成的会很快过去，
  所以"重启一次"不会重翻。

⚠️ 诚实的限定：这个修复我**没有在真实重启下验证过**（和 §17.3 同一个
原因 —— 从后台任务里无法证明进程能否活过会话拆除）。
已验证的是：`--backlog` 选项存在且能解析、守望脚本的命令行里确实是
`--watch-only --backlog`、脚本语法与编码自检通过。

#### 缺口 2：写回过程中**游戏被启动**的窗口

原来的保护是"**进入写回之前**查一次游戏在不在跑"。这不够：

写回是**逐个文件** `copy2`（`batch.write_back` 里就是一个
`for rel in rels`）。上千文件的游戏要好几秒，上万文件的要几十秒。
用户完全可能**恰好在这段时间里**双击启动游戏 —— 那一刻游戏开始读的
正是被替换到一半的资源目录：

* 读到新旧混合文件 ⇒ **崩溃**；
* 退出时把内存里的旧数据写回存档 ⇒ 与刚替换的资源不匹配 ⇒
  **存档损坏**，而且**不可逆**（备份只保证能退回原版，
  玩家那一刻的进度保不住）。

**修法**：给 `write_back` 加 `should_stop` 回调，**每个文件之前**重新确认：

```python
def _game_started() -> str:
    run, who = _busy.is_game_running(ent.path)
    return f"游戏被启动（{who}）" if run else ""

rep = write_back(..., should_stop=_game_started)
if rep.aborted:
    ent.status = "deferred"     # 不假装成功
    ent.message = (... "已立即停止（备份完整，可恢复）" ...)
```

两个刻意的设计决定，都写进了 docstring：

1. **已经写了的不回滚** —— 回滚本身要再写一遍文件，
   在"游戏正在读"的时刻做这个**反而更危险**。
   此时目录是"部分新部分旧"，但**备份是完整的**，可以据此恢复。
2. **必须显式报告** `rep.aborted`，不能默默当成功 ——
   否则用户以为游戏是完整的，实际是半新半旧。

`tests/test_writeback_stop.py` 有 9 个用例钉住这些（含
"中间叫停后已写的不回滚、备份覆盖刹车点之前的所有文件"）。

#### 剩下的残余风险（说清楚，不掩盖）

两道检查之间**仍有微秒级窗口**：`is_game_running` 返回"没跑"之后、
`copy2` 真正落盘之前，游戏可能启动。要做成零窗口就得在写回期间
独占文件锁（Windows 上 `LockFileEx`），代价是可能让游戏**打不开**，
比"读到旧文件"更糟。所以这里选择"窗口极小 + 备份完整"，
而不是"锁死文件"。

#### 初轮跑完之后会不会长期空占资源

用户问："初轮翻译结束后也不会长期空占资源吧？" 实测常驻开销：

| 常驻部件 | 内存 | 说明 |
|---|---|---|
| 守望服务（`novaloc.exe` + python 子进程） | 约 5 MB + 38 MB | 每轮 `--interval 60` 秒才醒一次 |
| 忙闲监视器（守护 + python） | 约 83 MB + 21 MB | 每 20 秒查一次，一次约 1~2 秒 CPU |
| **合计** | **约 150 MB** | 不推理时 CPU 接近 0 |

关键一条：**Ollama 的模型会自己卸载**（`keep_alive: 10m`）。
翻译停下来 10 分钟后，`llama-server` 会释放它占的
**约 9 GB 显存/内存** —— 实测该进程的 RSS 会从 8.9 GB 掉下去。
所以"跑完之后"的资源占用是"约 150 MB + 0 显存"，不会长期占着 GPU。

⚠️ 但**初轮本身**会长时间占 GPU —— 那是"正在干活"，不是"空占"。
用户打游戏时靠 §20.5 的闸门让路（实测 32.0 → 0.0 条/分钟）。

#### 附带修掉：`--backlog` 每轮会**重扫全库**（实测 1~3 小时/轮）

`--backlog` 是"大锤"式修法：每轮先遍历所有待办。但原来的
`run_pipeline` 会**无条件** `stage_extract()`，于是每个待办游戏每轮都重抽一遍。

抽取实测不便宜（`.scratch/_eta_sample.py`，12 个游戏真抽）：

    Alien maze                        39.7 s
    amusement parklust                59.1 s
    [WaterRing] ZZZ_Game (2025.01)   339.9 s
    rpgmaker 层                        0.5 ~ 6 s

⇒ 174 个游戏重扫一轮要 **1~3 小时**，而**已经抽好的完全没必要再抽**
（产物就在 `extracted/units.jsonl`）。

**修法**：`run_pipeline(..., skip_extract_if_cached=...)`，
且**只**在 `--backlog` 路径上开 True。手工 `novaloc auto` 不开 ——
那时用户的意图可能就是"源文件变了，重抽一遍"，静默跳过属于
"优化吃掉功能"。

**实测 A/B**（同一个游戏 `[WaterRing] ZZZ_Game`，2025 条文本）：

| | 抽取 | 该游戏总耗时 |
|---|---|---|
| 第 1 轮（无缓存，**真抽取**） | 340 s | **9 分 39 秒** |
| 第 2 轮（`--backlog`，**跳过抽取**） | 跳过 | **10.2 秒** |

⇒ **57 倍**。而且用 `extracted/units.jsonl` 的 mtime 交叉验证过：
第 2 轮跑完后它仍是第 1 轮的时间戳（7.5 分钟没动），
说明是真跳过，不是别处的缓存命中。

⚠️ 残余代价：每轮开头的"引擎识别"仍会扫 193 个目录
（实测整轮 121.7 秒里绝大部分是它）。这个可以接受 ——
它不写文件、不占 GPU，而且每轮只跑一次。

## 21. #55 ★★★ "支持中文的游戏被我重翻了一遍" —— 用户指正的漏判

### 21.1 用户的原话

> 有可能很多支持中文的游戏被你误处理了，因为支持中文的同时支持别的语言，
> 导致游戏里有别的语言的资产，而你就进行了多余操作。
> 比如 Alice in Cradle 就支持中文，可是你依旧在翻译。
> 支持中文的游戏只需要将其换为其自带的中文就行了（比如在其设置里）。

**用户说对了。** 这是本轮最严重的一处浪费。

### 21.2 实测确认

`AliceInCradle_ver029` 的实际结构：

```
AliceInCradle_Data\StreamingAssets\localization\
    en/     68 文件   0.71 MB
    ko-kr/  76 文件   2.32 MB
    th/     44 文件   0.35 MB
    zh-cn/  70 文件   0.88 MB   ← 官方简体中文
    zh-tc/  69 文件   0.81 MB   ← 官方繁体中文
    _/      69 文件   0.95 MB
    __AdditionalFonts/ 16 文件 40.99 MB
```

`zh-cn\ev_book.txt` 的内容：

```
「好痛……」
诺艾儿用手捂着肿胀的皮肤。
```

**官方中文一直在那里**，玩家在设置里选一下就有。
而我给这个游戏翻了 **127,693 条**（已译 68,743 条、跑了几个小时 GPU），
纯粹是白做。

### 21.3 为什么原来的判据看不见这件事

`detect_already_chinese` 原来只查两样：

1. RPG Maker 的 `www/data/System.json` 里 `terms` 的汉字占比；
2. 游戏目录里有没有**中文字体文件**（`*zh*`/`*sc*`/`*cn*` 的 ttf/otf）。

**"每种语言一个目录"这种形态它完全看不见** —— Unity 游戏把每种语言
放进独立子目录，主配置里一个中文都没有，字体还往往是共用/自定义的。
于是"支持中文"这个**客观事实在判据里根本不存在**。

> 这是本项目反复出现的同一类错误：**判据只覆盖了已知的形态**，
> 而真实世界还有别的形态。上一次同类的例子是
> GameMaker 的 `data.win`（§14）和嵌套 Unity 工程（§16）。

### 21.4 修法与判据

新增 `detect_builtin_chinese_assets()`，两个条件**都要**满足：

1. **目录名是语言码** —— `zh`/`zh-cn`/`zh_cn`/`zh-Hans`/`zh-tw`/`chinese`/
   `chs`/`cht`/`sc`/`tc`/`cn`/`简体`/`繁体`/`中文`…（大小写无关）；
2. **该目录里确有一批文件含汉字**（默认 ≥3 个）。

第 2 条不能省：只看目录名会把**"预留了但没填内容"的空壳**误判成有中文，
后果是**漏翻一个本来该翻的游戏**。

然后把它接进 `detect_already_chinese`（这一步最关键 ——
只写一个独立函数、忘了在主管线里调用，是典型的"看着修好了、实际没生效"，
所以有一条专门的测试钉住它）。

**门槛松紧的不对称**决定了判据该宽还是该紧：

| | 代价 |
|---|---|
| **漏判**（真有中文没认出来） | 白烧几小时 GPU + 把好好的中文游戏改掉 |
| **误判**（没中文却认成有） | 少翻一个游戏（用户还能 `--force` 强制翻） |

⇒ 显然该往"宽"的一侧偏，所以语言目录名列表写得很全。

### 21.5 全库扫描结果：4 个游戏自带中文

`.scratch/_find_builtin_zh.py` 扫了全部 193 个目录：

| 游戏 | 中文资产位置 |
|---|---|
| `AliceInCradle_ver029` | `AliceInCradle_Data\StreamingAssets\localization\zh-cn`（40+ 个含汉字文件） |
| `Inari v1.5.12` | `LocalizeData\cn`（23 个） |
| `Night_of_Revenge_HELLGATE...` | `BepInEx\plugins\HellGateJson\CN`（21 个）+ 两处子目录 |
| `path-to-the-occult-1.0.3-windows` | `locales\zh`（9 个） |

修好并重启后的实际效果：

```
修之前:  待处理 174   已是中文 19
修之后:  待处理 170   已是中文 23     ← +4，正是上面这 4 个
         引擎分布 unity 106→103、rpgmaker 39→38
```

### 21.6 Alice in Cradle 的处置：**中止在造成损害之前**

关键的时间点判断（这是我这次做对的地方）：

* 工作区 `e7bff9b76a6e` 的 `out/` 里 **0 个文件**；
* `_novaloc_backup` 里**没有** Alice 的备份目录。

⇒ 说明它还在**翻译阶段**，`stage_apply` 与 `write_back` 都还没跑，
**游戏现盘一个字都没被改**。所以：

1. 先放闸门让它停在批次边界（避免正在写的文件被截断）；
2. 精确 PID 终止旧进程；
3. 删掉那个白做的工作区（81.5 MB，`out/` 为空 ⇒ 丢弃无损失）；
4. 重启，新代码把它归入"已是中文"直接跳过。

事后复核游戏现盘：

```
zh-cn 目录        存在，70 个文件完好
*novaloc* 文件    0 个   ← 从未被本工具改过
```

⚠️ 如果我发现时**已经写回**了，就得靠备份回滚 —— 而这次备份还不存在。
**"检查 out/ 与备份目录是否存在"** 是判断"有没有造成不可逆改动"的
两个可靠信号（ROADMAP §13 的判据在这里第二次派上用场）。

### 21.7 这一处漏判省下了多少

`--backlog` 让每轮都重扫全库，所以这个 bug 的代价是**每轮都重复**：

* `AliceInCradle` 127,693 条 × 每个 backlog 轮 ≈ 10 小时 GPU / 轮；
* `Inari` 6,078 条、`Night_of_Revenge`、`path-to-the-occult` 也会各来一遍。

## 22. #56 ★★ `out/` 是**整个游戏的副本** —— 结构性浪费 11.5 GB（还会涨到几十 GB）

### 22.1 怎么发现的

用户问"看看现在情况呢"。我查了常驻进程、进度和磁盘，发现 **D 盘掉了 39 GB**
（352.9 → 312.9），远超预期。顺着查下去：

```
D:\NovaLoc\workspaces    14,437 MB   ← 问题在这
  out/                   11,511 MB   ← 占 80%
  extracted/                 86 MB
  translations/              46 MB
  images/                   208 MB
  fonts/                     54 MB
```

`out/` 一个目录就 11.5 GB。

### 22.2 根因：`prepare_out` 是整目录复制

`engines/base.py`：

```python
def prepare_out(game_dir, out_dir, *, overwrite=True):
    """把游戏目录复制到输出目录。

    默认整目录复制而不是"只复制要改的文件"：游戏运行时可能依赖
    大量未被修改的资源，少复制一个就可能启动失败。
    """
    shutil.copytree(game_dir, out_dir, symlinks=True)
```

**这个决定本身是对的**（我也认同它的理由）。问题在于**回写成功后没人回收它**。

对比一下两边的量级，差距很说明问题：

| 游戏 | `out/` | 备份 | 备份覆盖 `out` 的文件 |
|---|---|---|---|
| Academy Love Saga | 1235 文件 / 1955 MB | 66 文件 | **65 / 1050** |
| ButtKnight | 368 文件 / 2386 MB | — | — |
| AliQ | 49 文件 / 1403 MB | 8 文件 | 8 / 9 |

`out/` 里全是 `.resS`(2022 MB)、`.png`(1226 MB)、`.dll`、`.ogg` —— 那些
**从来不会被翻译**的资源。而备份是**稀疏**的，只存被改过的文件
（`changed_files()` 用大小+哈希判定），所以 1.7 GB vs 11.5 GB 的 30 倍差距。

按全库 170 个游戏外推，`out/` 会累积到**几十 GB**。

### 22.3 ★ 我先猜错了一次：以为"没进 `written` 的文件要保留"

我最初写的回收逻辑是**逐文件**的，判据是"在 `written` 里 且 备份里有原件"。
理由是：没写回的文件可能是**被拦下的新版本**（`should_stop` 中止、
占位符不合格被拒），那可能是唯一副本。

按这个逻辑算出来只能回收 **1.48 GB**（而不是 11.5 GB），因为备份很小，
"同时有备份"的文件没几个。这个数字与预期差太多，于是我**去实测**：

```
抽 ButtKnight 的 40 个文件逐字节比对现盘:
    与现盘完全相同: 40 / 40
    与现盘不同    :  0 / 40
```

⇒ **假设被推翻了**。原因很清楚：`changed_files()` 用**大小 + 哈希**判定
"变了没"，所以进了 `written` 的就是"内容真的不同"的那些；
**其余文件在 `out/` 里就是原样副本，与现盘逐字节相同** ⇒ 删了无损失。

所以"写回**完全成功**"时，整目录清空是安全的。修法：

* `safe_to_clear=True`（写回**零失败、零中止**时传）⇒ 整目录清空；
* `safe_to_clear=False`（有失败/中止时传）⇒ 退化成逐文件，
  这时 `out/` 里可能真有"没能写回的新版本"，必须留着。

**默认值是保守的那个** —— 危险行为不能是默认值（有测试钉住）。

### 22.4 实测效果

一次性回收已有工作区（只动"`out/` 非空"的，即 `stage_apply` 已跑过的
完成态；正在翻译的游戏 `out/` 是空的 ⇒ 天然排除，不会打断活）：

```
10 个游戏，12,453 个文件
D: 312.84 GB → 324.10 GB   （+11.24 GB）
备份目录 1510 个文件未动    （回滚依据完好）
翻译进程未中断
```

### 22.5 安全护栏（逐条对应一个真实风险）

`.scratch/_reclaim_out.py` 与代码里的回收逻辑都遵守：

| 护栏 | 防的是什么 |
|---|---|
| 只动"`out/` 非空"的 | 正在翻译的游戏 `out/` 为空 ⇒ 不打断活 |
| 绝不碰备份目录 | 备份是唯一回滚依据 |
| 保留 `out/` 目录本身 | 用户仍能看出它的位置 |
| 默认 dry-run | 误删是删不回来的 |
| 报告**实际**释放量 | 预计值经常与实际不符（占用/权限） |
| 默认走保守模式 | 危险行为不能是默认值 |

### 22.6 教训

这是本轮第二个"**我的假设被自己的实测推翻**"的例子
（前一个是 §21 里"没进 written 的文件要保留"）。

两次的形态一样：**我先根据代码逻辑推断出一个结论，然后去测，
发现数字与推断差一个数量级，于是回头查，发现推断的前提是错的。**

> 数字差一个数量级时，**不要调参去凑**，要去查前提。
> 1.48 GB vs 11.5 GB 的差距就是那个信号。

## 23. #57 ★★「失败 24,049 条」的真身：**引擎 API 文档被当成游戏文本抽了出来**

### 23.1 起因

我报告"失败 24,049 条（11.7%）"时，按 `warnings` 归类得到
**23,700 条（98.5%）是 `placeholder_broken`**，即"丢了占位符"。
看着像一类机械问题，值得修。于是去查。

### 23.2 第一版分类给出的信号（样本一看就不对）

我按"丢的是什么记号"分类，得到"混合：换行+未分类 63.9%"。
但抽出来的样本**根本不是游戏对话**：

<name>UnityEngine.AccessibilityModule</name>
<para>A class containing methods to assist with accessibility for user
<param name="palette">An array of colors to populate with a palette.
<SG説明:Cabbage is way too expensive,\nso I want you to go and procure me
PRJ_RogueDeck/Content/PRJ_RogueDeck/Texture/UI/Status/DeBuff/T_Executi
```

⇒ 所以"丢占位符"只是**表象**。真身是**抽取阶段把不该翻的东西收进来了**。

### 23.3 重新归类：61.2% 是"抽错东西"

| 类别 | 条数 | 占比 |
|---|---|---|
| **Unity API 文档 XML**（`<para>`/`<param>`/`<name>`） | **13,889** | **58.4%** |
| Unity 内置命名空间 | 494 | 2.1% |
| 泛 XML 标签 | 91 | 0.4% |
| 插件标签 `<SG…>` | 44 | 0.2% |
| 纯 ASCII 标识符 | 18 | 0.1% |
| **小计（不是翻译问题）** | **14,536** | **61.2%** |

剩下 9,234 条里，大头是插件 DSL（`<Set Sts Data>`、`<PsensorL:4 Ld>`、
`<random:40>`）和真正的 `\n` 掩码丢失。

### 23.4 为什么 `Managed` 目录的排除规则没生效

`_UNITY_SKIP_DIRS` **本来就有 `Managed`** —— 但它只在
"**找 `*_Data` 目录**"那一步用；进入抽取阶段后是
`rglob("*")` 从 `*_Data` 根扫起，**不再过滤目录**。
所以 `*_Data/Managed/*.xml` 照样被抽。

> 又一处"规则写了但没在正确的层次生效"。与 §21 的
> "只写独立函数、忘了在主管线调用"是同一类。

### 23.5 修法：两道判据（都不能省）

1. **路径形态** `*_Data/Managed/UnityEngine*.xml`；
2. **内容标签** `<member>`/`<summary>`/`<param>`/`<typeparam>`/`<returns>`…。

判据 1 不能省 —— 实测 `Arena Story` 里有几个文档**已被旧版本翻译写坏**：

```
UnityEngine.VideoModule.xml:  '中文译文 已完成<doc> ...
                                {"t":<members> "中文译文"}'
UnityEngine.InputModule.xml:  '中文译文 已完成<doc> ...'
```

原本的 `<summary>`/`<param>` 标签被译文**替换掉了**，判据 2 对它们漏判。
这类文件更该被排除（继续翻只会越改越乱）。

### 23.6 ★ 我第一版判据过宽，被自己的反面用例抓到

第一版把 `para`/`list`/`item`/`term` 也算成文档标签。测试立刻红了：

```
tests/test_api_doc_filter.py::test_plain_game_xml_without_doc_tags
  <items><item id='1'>Potion</item></items>   ← 游戏数据，必须保留
```

⇒ 收紧到**只收文档专属标签**。这正是"先写反面用例"的价值：

> **误排游戏数据的代价（玩家看到没翻的文本）比多抽几条文档严重得多。**
> 所以判据宁可窄，不可宽 —— 与 §21「自带中文」判据宁可宽的方向**相反**，
> 因为那一次漏判的代价是白烧 GPU，而这次漏抽的代价是玩家体验。

### 23.7 实测效果

| 游戏 | 修改前抽取 | 修改后抽取 | 说明 |
|---|---|---|---|
| `Arena Story` | **83,585 条** | **545 条** | 排除 60 个文档 XML，**残留 0** |
| `ButtKnight` | 34,650 条 | 34,650 条 | **完全不变** ⇒ 无误伤 |

`Arena Story` 剩下的是真游戏文本（`Telegram@quzimingyue`、
`本游戏为Tg频道quzimingyue自购分享`）。

意义：这个游戏以后**不会再重译 8 万多条文档**（它单轮跑了
7 小时 43 分，其中大部分是这个）。

### 23.8 还没做的两件事（留待收尾）

1. **已有工作区里的旧 units 不会自动重抽** ——
   `Arena Story` 的 83,585 条还躺在 `units.jsonl` 里，
   而 `--backlog` 会跳过抽取。需要一次显式的重抽。
2. **插件 DSL**（`<Set Sts Data>`、`<PsensorL:…>`）**仍是该讨论的** ——
   它们是真游戏逻辑，但**不该整条翻译**（模型只能回"确认"）。
   正确处理是"只翻标签外的文字"，那是另一个中等规模的改动。

n= 40  ✅ 40/40 10.6s
```

**所有批大小都回满。** 那些"只回少数"（`auto9.err` 里 1,067 次）
是**病态少数**，不是主因。

▲ 这里差点得出错误结论：我的**探针第一版**用
`to_translation_map(raw)`（传原始 JSON 文本）而不是
`parse_translations(raw)`（会先剥代码围栏），只认出 1 个键，
看起来像"模型只回 1 条"。**是探针自己的 bug。**

### 24.3 用进程 CPU 时间找真瓶颈

`.scratch/_find_bottleneck.py`（按进程采 CPU 增量）：

```
python.exe（主流水线）  CPU 0.89 核
llama-server            CPU 0.01 核      ← 推理几乎闲置
合计 1.06 核 / 32 核
GPU 13%
```

⇒ 时间**不在推理上**。两个独立原因：

1. `llama-server` 启动参数是 **`-np 1`**（Ollama 一次只跑一个请求）；
2. `Config.ollama.concurrency` **从未被使用**（死配置）——
   批是 `for bi, batch in enumerate(batches)` **串行发**的。

### 24.4 已修的三处（都有实测与回归测试）

| 提交 | 内容 | 实测 |
| --- | --- | --- |
| `37d5658` `962116c` | 并发派发（**窗口式**，带背压） | 289 → 655（探针） |
| `c6b72a9` | 批大小上限 **25 → 8** | 308 → **548**（热态，`/api/chat`） |
| `96331d0` | 忙闲阈值 **50/55 → 75/90** | 消除"自己把自己判成忙"的自锁 |

**批大小为什么是 8**（热态实测，走生产同一条 `/api/chat`）：

| 批大小 | 并发1 | 并发2 | 并发3 | 并发4 |
| --- | --- | --- | --- | --- |
| **8** | 170 | 332 | 461 | **548** |
| 16 | 165 | 327 | 486 | 476 |
| 25（原值） | 148 | 309 | 324 | **308** |

批越大每条越慢（提示词变长后注意力开销超线性）——
**"25 + 并发 4"恰好是表里最差的一格**。

**背压为什么必须**：并发派发第一版是"一次性 submit 全部批次"，
而**每个请求的 300 秒超时从提交时刻算**，Ollama 只有 `-np N` 个槽
⇒ 排队尾的请求**必然超时**（实测 `批 0（1 条）用了 300.0s（失败）`、
worker 攒到 **102 个线程**）。改成"最多 N 个在飞、回来一个补一个"。

### 24.5 ★ 吞吐上限：每条 **11.0 token**、生成 **57.4 tok/s**

`.scratch/_probe_tokens.py`：

| 批大小 | 输出 token | 每条输出 | tok/s | 理论上限(条/分) |
| --- | --- | --- | --- | --- |
| 4 | 46 | 11.5 | 57.0 | 298 |
| 8 | 84 | 10.5 | 58.1 | 332 |
| 16 | 171 | 10.7 | 63.3 | 356 |
| 25 | 279 | 11.2 | 61.3 | 330 |

⇒ **理论上限 ≈ 313 条/分钟**（57.4 / 11.0 × 60），目标 **327**
⇒ **差 4%**；而**实测最好 229**（差 30%）。

**换更快的模型这条路已堵死**：`kaelri/qwen3.5-mt:2b` 实测
生成 **93.1 tok/s**（快 62%），但**回满率 0%**（0/48 条）
—— 对当前"行号作键"格式**完全不回**（与早前 0/24 一致）。

**并发只能给 2.8 倍**（`.scratch/_probe_parallel_real.py`，4 个不同批同时发）：

```
并发   各请求耗时        总耗    单请求均   GPU均   llama核
  1          2.5        2.5s     2.5s    86%     1.14
  4  6.0 2.8 4.4 7.7    7.7s     5.2s    81%     1.10
```

⇒ 真并行但只有 2.8 倍，GPU 81~86%、llama 1.1 核 —— 已接近这块
8 GB 卡的算力上限。**`-np` 从 1 加到 4 不可能得到 4 倍。**

### 24.6 ❌ 未解开：**隔离稳定、生产挂死**

用**独立端口的 Ollama 实例**（不干扰生产）跑稳定性矩阵
（`.scratch/_stability_matrix.py`，每格 8 分钟）：

| -np | num_ctx | 状态 | 吞吐(条/分) | 峰值显存 |
| --- | --- | --- | --- | --- |
| 1 | 8192 | 稳定 | **81** | 7770MB |
| 4 | 4096 | 稳定 | **229** | 7746MB |

**但生产上 `-np 2/4` 跑一段就"请求不再返回"**，两种表现：

1. `-np 4`：`Ollama 请求过慢：POST /api/chat 用了 300.0s（失败）超时`
   + worker 攒到 102 线程 + `llama-server` CPU 很低；
2. `-np 2`（**已加背压之后**）：**没有超时**，但 worker 停在 205s CPU、
   24 线程、**队列不再推进**。

⇒ 都是"请求不再返回"。已排除的原因：

* ~~`num_ctx=4096`~~ —— 按日志段核对（`.scratch/_verify_stability.py`），
  `-np 4 + num_ctx=4096` 那段其实跑了 **11 个游戏、0 超时**；
* ~~单纯的 `-np 4`~~ —— 隔离实测稳定。

**现在的判断**：与**生产特有**的东西有关（RapidOCR 的 DirectML 抢 GPU？
长时运行？`--bundles --depth 2` 阶段？）。**这是唯一挡住
2.8 倍提升的问题。**

### 24.7 当前决定：**保留稳定配置**（挂死比慢严重）

```
OLLAMA_NUM_PARALLEL = 1
Config.ollama.concurrency = 1     # 与之一致
Config.ollama.num_ctx = 8192
```

实测约 **226 条/分钟**（相对最初的 20~45 提升 **5~11 倍**）。

理由：**挂死会让整个游戏失败、需要人工介入重启**，
而 `-np 1` 是**已验证数小时稳定**的。

### 24.8 下一步：把实验变成无人值守

`.scratch/_ollama_channel.py`（本轮新增）—— 带**健康监控 + 自愈**的
Ollama 通道：独立端口、持续发请求、每 15 秒采
（`llama-server` 是否在 / 最近 60 秒完成数 / GPU / CPU），
**判挂后记录现场并自动降级重试**，结果追加到 JSONL。

⇒ 这样"哪种配置能撑多久"可以无人值守地跑出曲线，
而不是像本轮这样手动重启十几次。

### 24.9 ★ 补记：靠提高并发到 327 在**算术上不可能**

后续用 `.scratch/_ollama_channel.py`（带健康监控 + 自愈）测出更长时长的结果：

| -np | 时长 | 完成 | 吞吐 | 结果 |
| --- | --- | --- | --- | --- |
| 4 | 186s | 87 批 | 223.9 | 稳定 |
| 4 | 355s | 199 批 | 269.3 | 稳定 |
| **4** | **822s（13.7 分）** | **419 批** | **244.6** | **稳定** |

隔离环境下 `-np 4` 累计跑了 **22.7 分钟、705 批、0 超时**。
另测「主动卸载再重载」4 轮（`.scratch/_probe_reload.py`）全部 `HTTP 200`
（8.5~24.3s）—— 排除"重新加载"这个候选。

**于是可以算清天花板了**：

```
生成速度        55~70 tok/s   （实测，全 GPU）
每条输出 token  11.0          （实测，各批大小稳定）
327 条/分 × 11 token = 3597 token/分 = 60 tok/s
```

⇒ **「327 条/分钟」要求模型以接近单请求峰值（57~63 tok/s）持续产出。**
而实测**有效产出**：

| 配置 | 有效产出 | 吞吐 |
| --- | --- | --- |
| `-np 1` | 约 15 tok/s | 81 条/分 |
| `-np 4`（隔离稳定） | **约 45 tok/s** | **244.6 条/分** |
| 单请求峰值 | 57~63 tok/s | 对应 313~343 条/分（**不可持续**） |

⇒ **244.6 已达单请求峰值的 75%**，是可持续并发下的好结果。

### 结论：本机「一周跑完」达不到

* 需要 **327 条/分钟**；
* 本机**可持续**上限约 **244.6**（隔离）/ **226**（生产）；
* 理论天花板 **313** 需要「单请求峰值持续」，不现实。

差了 **35%~45%**。**这不是调参问题** —— 4B 模型的 57~63 tok/s
决定了天花板，而唯一更快的可用候选（2B，93.1 tok/s）
**回满率 0%**（质量不可用）。

出路都需要本机之外的投入：

1. 换更快的 GPU（生成速度线性影响吞吐）；
2. 重新评测出「可翻中文且更省 token 或更快」的模型
   （且必须验证回满率 —— 2B 那个就是栽在这条）；
3. 接受现实：按 226 条/分钟，全库约需 **10~12 天**而不是 7 天。

### 剩下的两个未测候选（挂死原因）

1. **RapidOCR 的 DirectML 与 Ollama 争 GPU** —— 生产里两者都用 GPU
   （扫图/汉化阶段 vs 翻译阶段），而隔离测试只有 Ollama；
2. **超长连续运行** —— 生产单个游戏可跑 25 分钟以上，
   隔离测试最长 13.7 分钟。
