# 测试套件

## 怎么跑

```powershell
# 全量（约 3 分钟；字体合并那几组比较慢）
.\.venv\Scripts\python.exe -m pytest tests -q

# 单个套件
.\.venv\Scripts\python.exe -m pytest tests/test_font_real.py -q

# 每个套件也能独立当脚本跑，输出的是带实测数字的分节报告
.\.venv\Scripts\python.exe tests/test_font_real.py
```

## 为什么测试长得像脚本

每个 `test_*.py` 主体是一个 `main()`，内部用 `check()` 汇总断言并打印
**实测数据**（覆盖率百分比、耗时、具体缺哪些字），末尾既有
`test_suite()`（给 pytest）也有 `if __name__ == "__main__"`（给人）。

保留这种形态是刻意的：这个项目的核心承诺是"绝不出口口口"，
而验证它靠的是**数字**——"最好的单字体只有 98.33%"、
"合并后 ascender/upem 从 8.63 回到 0.93"。重写成纯 `assert`
会让这些证据从输出里消失，而它们才是判断"改对了没有"的依据。

## 外部前提与跳过策略

有些测试需要本机资源，**缺失时 skip 而不是失败**——否则新克隆仓库的人
会看到一片红，却不知道只是没准备素材。

| 前提 | 影响的套件 | 怎么补 |
| --- | --- | --- |
| 中文字体 fixture | `test_font_service.py`、`test_charset_merge.py` | 把 OFL 中文字体（如 LXGW WenKai）放进 `tests/fixtures/fonts/` |
| **本机装有中文字体** | `test_api_e2e.py`、`test_pipeline_e2e.py`、`test_vlm_fallback.py`（标了 `needs_fonts`） | Windows/macOS 自带；Linux 装 `fonts-noto-cjk`。这几套要真的把中文渲染进贴图，没有字体就会 `RuntimeError: 找不到可用的中文字体` |
| Windows 系统字体 | `test_font_real.py`、`test_merge.py` | Windows 自带；其它平台跳过 |
| DirectML / ONNX Runtime | OCR 相关断言 | 装 `pip install -e ".[dml]"`；无 GPU 时退化到 CPU（慢约 84 倍） |
| PP-OCRv6 模型 | 贴图识别 | 首次运行自动下载到 `<data_root>/models/rapidocr` |
| Ollama | 只影响真机端到端；测试用假服务端 | 见 README 的 Ollama 一节 |

注意区分两种"要字体"：

* **要一个能用的字体把字画上去** → 用 `tests/_minimal_font.py` 自己造，
  不该依赖本机（`test_engine_rpgmaker.py` 就属于这种，它标 **不需要**
  `needs_fonts`）；
* **要真中文字体**（因为要画汉字、要跑 OCR 认中文）→ 标 `needs_fonts`。

`_minimal_font.py` 的字形轮廓是**从 Pillow 内置字体里抽出来重新组装**的
（Aileron，随 Pillow 分发），所以是真字母形状、OCR 能认，而仓库里
**不需要放任何字体文件**。

> ⚠️ 早先那版最小字体给每个字符都画同一个**方块**：PIL 能加载、能画上
> 墨迹、静态检查全绿，但 OCR 完全认不出来（`NEW GAME` 40px 时"墨迹"
> 占 88% 像素，就是一整块实心矩形），导致贴图汉化报告"0 处文字"。
> 这正是本项目最怕的失败模式：**看起来成功，其实什么都没做**。

## 一处"指标本身写错了"的教训

`test_texture_overlap.py` 要断言"产物上没有残留的原始外文"，但机器
**看不见图**，只能靠像素统计。第一版我写的是"原文字区域里亮像素占比
小于 5%" —— 听着合理，实际**正确产物也过不了**：译文自己的笔画就占
11%。这种阈值等于没测，而且方向是错的（它会惩罚正确的输出）。

改成"墨迹可解释度"：把译文用**产品同一个渲染器、同一套内边距**渲染出来，
取其 alpha 掩码对齐到原文字的包围盒，再看产物的亮像素有多少能落在
掩码内。落在掩码之外的越多，说明越可能有残留外文。

关键是**先量再定阈值**（`.scratch/_calib_leftover.py`）：

| 状态 | extra（无法由译文解释的墨迹占比） |
| --- | --- |
| 修复后 | 0.031 |
| 修复前（模拟） | 0.710 |

20 倍差距，阈值取 0.15 —— 两边都稳。**任何"目测像合理"的阈值，
在写下之前都该先量一遍它在正确/错误两种状态下分别是多少。**

**字体文件不入库**：`tests/fixtures/fonts/` 在 `.gitignore` 里。原因是体积
（两个 CJK TTF 就有 21 MB）和许可证（LXGW Neo XiHei 是 IPA-1.0，
不允许再分发）。详见 `docs/FONTS.md`。

## 拿真实游戏跑出来的四个 bug（合成样例全都测不出来）

合成工程按"我们以为的格式"写，所以**结构性的错**它一定发现不了。
把 `E:\lush\1\newlytransport` 里一个真实的 558 MB RPG Maker MV 游戏
跑完整流水线，暴露出四个问题，其中**两个是静默失效**：

| # | 症状 | 为什么合成样例测不出 |
| --- | --- | --- |
| 1 | 资源在 `www/` 下的游戏被认成"散装文件"25%，11 张贴图全部"源文件不存在"**而阶段报 ok** | 合成的 MV 工程资源直接在根下（我们以为只有这一种布局）；NW.js 打包是另一种真实且常见的布局 |
| 2 | `apply` 把 CSS 改写成**原文件名**，新字体从未被引用 | 合成样例的补丁字体与原文**同名**，同名覆盖正好掩盖了它；真实流水线产出的叫 `<原名>.zh.ttf`，**不同名** |
| 3 | 翻译跑到 **27 分钟**时被 `UnicodeEncodeError: '\uddd1'` 打断，整轮作废 | 合成样例的文本是我们编的，不会有孤立代理项；它是**运行期从模型回复里进来的** |
| 4 | 人物立绘被读出单字符 `'2'/'S'/'0'` 并"翻译"，其中 `'0'` → `'VS'` 被**重绘进画面** | 合成样例的"贴图"是干净的矩形+规整文字，不会让 OCR 在插画上产生幻觉 |

四条教训，按可复用的程度排：

1. **"阶段报 ok" 不等于"事情做了"**。1 和 2 都属于这一类：计数为 0 或
   路径算错时，阶段照样返回成功，报告里写着"0/11 张贴图已汉化"，
   看起来像"这些图本来没字"。所以断言要打在**产物**上
   （`out/www/data/Map001.json` 里有中文、CSS 指向新字体名），
   而不是打在状态上。
2. **测试数据要用"真实流水线自己会造出来的那对命名"**。2 的教训最贵：
   我第一版测试用了同名补丁字体，测试通过，bug 还在。
3. **一个词的失败不能结束整轮**。3 里重试层只捕了自定义异常，
   `UnicodeEncodeError`（继承 `ValueError`）从旁边溜过去了。
   单一文本触发的问题必须只让那一批失败。
4. **没有视觉能力时，用像素统计代替"看一眼"**。4 是靠量
   "识别区域占整图比例"（幻觉块占 17%–48%）和"单字符"这两条判据
   定出来的，而不是靠看图。注意其中一条判据**必须放宽**
   （`Loading.png` 的真文字也占 44%），否则会误杀真文字 ——
   判据的阈值要拿真实的正例校准。

### 两条配套教训

**（1）判据的"分母"必须是玩家真正看到的东西。**
第 29 条两个坑都是分母问题：组合记号被 `isalpha()` 漏掉、
富文本标签被算进可见字符。凡是比例类判据，
先问一句"分母里有没有玩家看不到的东西"。

**（2）失败计数器会掩盖截然不同的原因。**
第 26、27 条在计数器上都和"正常的失败"长得一样
（`prompt_leak`、`placeholder_broken`），
所以**必须把失败条目摊开看**。第 26 条是"误杀好译文"、
第 27 条是"可以救的坏译文"，而第 27 条如果不打开看，
就会以为是模型不行 —— 实际只是多了一个垃圾记号。

### 五条 bug 是同一个根因：**规则的作用域搞错了**

第 22、23、24、25、26 条看起来无关，都栽在"**规则该作用在哪个范围**"上：

| # | 规则 | 错误作用域 | 应该的作用域 |
| --- | --- | --- | --- |
| 22 | 插件配置不翻 | 无（根本没这条规则） | `note` 字段 |
| 23 | 插件配置不翻 | **所有字段** | 只 `note`（`name` 里的 `<right>` 是排版） |
| 24 | 属性缩写固定译法 | 交给模型猜 | 确定性查表 |
| 25 | 校验与优先级 | 只管模型结果 | **所有来源**（查表 / 缓存 / 模型） |
| 26 | "模型在道歉"的判据 | 匹配**词**（`抱歉`） | 匹配**形状**（抱歉 + 无法） |

共同教训：**新加一条规则时，先问"它的作用域是什么"** ——
是某个字段、某个来源、某个词、还是全局。第 23 条就是漏了这一步，
代价是 7034 个说话人；第 25 条则是"校验只管了一条路径"。

另外第 24/25 组合出了一个很隐蔽的失败模式：
**改了代码、重跑了、日志说成功、结果一模一样** ——
因为旧结果被当成缓存又喂了回来。遇到这种情况，
第一件事是查"这个值从哪来"，而不是继续改规则。

### 一次"把自己的探测当成基准"的教训

第 21 条在排查时我还额外错了一次，比 bug 本身更值得记：

我用 httpx 直接测"25 条一批要多久"，得到 **124 秒**，
于是判定"prompt 处理是瓶颈"。可同一份配置后来又测出 **8.2 秒** ——
因为**翻译任务正在跑，我的探测在跟它抢同一块 GPU**
（本机单卡，Ollama 又是串行处理请求）。

停掉任务、GPU 空下来再测：**7.7～8.3 秒**，完全正常。
拿被污染的数字去优化，方向一定是错的，而且会得出
"prompt 太长"这种看似合理、实则无关的结论。

后来改成**纯文件读取**监控（只看 `entries.jsonl` 的行数与修改时间），
不碰 GPU —— 修复后的真实速率 **213 条/分钟**，
而污染状态下测出来是 8 条/分钟，差 26 倍。

### 第 21 条的"修法"也错了两次

1. **不设上限** → 个别批次 384 秒；
2. **一刀切 `48 × 条数`** → 跑飞那批降到 17.6 秒，但另一些批次
   涨到 **153～183 秒**：上限太紧，正常 JSON 被**截断**，
   解析失败后走"重试 → 逐条降级"（12 条 = 12 次调用），比不管还慢；
3. **按内容算**（`字符数 × 2.2`，再加保险丝）→ 全部回到 6～15 秒。

所以 `test_translate_output_cap.py` 里**一半的测试在钉"不能一刀切"**，
而不只是钉"必须有上限"。教训是：**上限类参数要按内容定，
而且"截断"的代价常常比"跑飞"更高**（因为会触发重试放大）。

## 第 30～32 条：三个"看起来完全正常"的失败

这三条放在一起，因为它们共享同一个特征：
**程序在跑、日志是绿的、文件也在、但结果是错的**。
没有任何异常，没有非零退出码，没有告警。

### 第 30 条：旧坏译文永远不被重查

翻译阶段加好 `foreign_script` 守卫之后，`entries.jsonl` 里**仍然**
留着夹泰文/阿拉伯文/西里尔的乱码句，而**告警分布里一条
`foreign_script` 都没有** —— 说明守卫根本没经手它们。

根因是 `stage_translate` 的跳过条件：

```python
if only_pending and prev is not None and prev.is_done and prev.target.strip():
    continue
```

「状态=已翻译 **且** 译文非空」就跳过。那些坏条目恰好**完全符合**
（它们是守卫上线**之前**写的），于是永远不被重新校验。
而"跳过"是**正常路径，不是错误路径**，所以什么错都不报。

> 注意：把 `foreign_script` 加进 `_BAD_WARNINGS` **救不了历史数据** ——
> 那个集合管的是"要不要进翻译记忆"，
> 而这些旧条目的 `warnings` 里根本没有 `foreign_script`。

这和**第 25 条**（贴图缓存抢先命中）是**同一类失败、完全不同的成因**：
那次是"来源优先级"，这次是"跳过条件"。
两次的表现一模一样：**改了代码、重跑了、日志说成功、结果不变。**

所以遇到这个表现，第一件事永远是问
**「这条数据是从哪来的、谁会重新看它一眼？」**

修法是三道闸门：翻译阶段过守卫（已有）、跳过逻辑对跑偏条目
**强制重译但限次数**（`meta.drift_retry` ≤ 2）、
`apply` **独立再查一遍**并**作废**坏条目
（清空译文 + 标 `failed`）让下一轮自动重译 ——
不必手工删 `entries.jsonl`，也不必整轮重翻。

### 第 31 条：21 个字符让**全部**中文字形注入失败

字体阶段因 21 个**永远补不上**的字符（阿拉伯/泰/马拉雅拉姆）整体失败。
后果比报错看起来严重得多：

```
out/fonts/mplus-1m-regular.woff      1007484 B   与源文件逐字节相同
out/fonts/mplus-2p-bold-sub.woff        7020 B   与源文件逐字节相同
```

补丁失败后 `apply` 没有字体可回写，就把**原字体原样拷**过去了，
而原字体中文覆盖只有 **3.4%** ——
**玩家进游戏满屏口口口，而流水线报"成功"。**

文件在、格式对（`wOFF` 头）、大小也"正常"。
所有"文件存在性 / 格式"检查全绿，
**只有逐字节比对才看得出来它根本没改。**

修法迭代了三版，每版都是"判据本身不对"：

1. 从报错里解析字符 → 写成"按冒号切、去掉 ASCII 和空白"，
   把前缀里的 `font`/`is` 也当字符了。更糟的是**外来文字的
   `isalpha()` 也是真**，按"是不是字母"根本分不出来。
   改成**认结构**：取**最后一个**冒号之后的全部内容。
2. 只剔"**只在源文侧**"的字符 → 漏了真实情况：
   实测 **11 条译文本身**混进了外来文字，于是它们进了「必需字符」，
   一个都剔不掉。
3. 按"**影响多少条文本**"剔 + **迭代**（规划器是贪心集合覆盖，
   剔掉一批后候选字体选择变了，原本被顺带覆盖的字符会跟着缺）。
   阈值 `max(3, 条数 × 0.5%)` —— **必须有比例项**：
   实测 `'กี้'` 出现在 **7 条**里，绝对阈值 3 挡不住，
   于是"剔了 18 个还剩 3 个"、合并**还是失败**；而 7 条只占 2 万条的 0.03%。

效果：`M+ 1m 69.8% → 100.0%`、`M+ 2p bold 3.1% → 100.0%`。

### 第 32 条：我把自己跑了 50 分钟的翻译搞崩了

翻译跑到第 50 分钟（21655 条）时，我在另一个终端并发跑了 `apply`
（它也要写 `entries.jsonl`）：

```
[WinError 32] 另一个程序正在使用此文件，进程无法访问：
'…\translations\entries.jsonl.tmp' -> '…\translations\entries.jsonl'
```

**更糟的是**：事后校验发现 `entries.jsonl` **中间**有 1 行截断
（读到一半被替换）—— 说明"先写 tmp 再原子改名"在并发时序下
**并不安全**，不只是"最后一步报错"那么简单。

两个根因，两个修法都要：独有 tmp 名（`os.getpid()`+线程 id，底层保险）
+ `Workspace.lock()` 工作区互斥（根因）。

真正的教训是**这个丢失没有任何报错**：两个进程各自读到旧文件、
各自写回自己的版本，**后写的把先写的抹掉**。
用户只会发现"莫名其妙少了一批译文"。

### 这三条共同的教训：判据 / 生命周期的错，不在"计算"里

第 30 条错在**跳过条件**（谁会重新看这条数据）；
第 31 条错在**剔除判据**（哪个字符算"真需求"）；
第 32 条错在**写入生命周期**（谁有权同时写）。

它们都不在"翻译得对不对""字体合得对不对"这些**计算**环节里。
所以**光测计算结果永远测不出来** —— 必须测
**"数据从哪来、谁在看它、谁在写它"**。

## 第 33 条：判据落在边界上，就说明判据选错了

`foreign_script` 守卫换了**两次**判据，第二次的教训比第一次更值钱。

### 第一次修（bug #27）：把"分母口径"搞对了

从 `isalpha()` 改成数**原始字符**（泰文的组合记号被漏掉了），
分母从"所有字母"改成 `visible_text()` 后的**玩家可见字符**
（`<right>` 标签把分母撑大了 2.4 倍）。这一层是对的。

### 第二次修（bug #33）：比例判据**本身**选错了

改完分母之后，拿真实的 **24,882 条译文**一跑，发现大量真跑偏
**恰好落在 25.0%** 这个阈值上：

    '而且你竟然饶了它们 ജീവ'          3/12 = 25.0%  → 放过
    '你…？我 دیگه不用说了，对吧？'     4/16 = 25.0%  → 放过

**判据落在边界上，就说明判据本身选错了。**
继续调数字只是把边界挪到别处，下一批数据还会落在新边界上 ——
而且**永远不会有测试报错**，因为"刚好没过线"是合法结果。

真正的区分是**形态**，不是**比例**：
把真实译文里"最长连续外来段"的长度统计出来，是清清楚楚的两堆 ——
**长度 3/4/5，而且这 7 条全部是跑偏**；
正常译文里"成串的外来词"**一个都没有**，只有单个 `π`/`β`/`Ω`。

改成"有没有混进来一个**外文词**"（连续 >= 3 个外来字符）之后：

    旧判据（比例 > 25%）              命中 3   误报 0
    新判据（连续外来段 >= 3）          命中 7   误报 0
    新判据 + 比例兜底                  命中 9   误报 0

### 从这条抽象出来的判据设计规则

1. **阈值落在真实数据上就叫停，去换判据。**
   如果一个阈值附近**堆着真样本**，那不是"阈值再调 5% 就行"，
   是判据的**形状**不对。
2. **判据要匹配"形态"，不只是"数量"。**
   "一个 4 字的外文词出现在中文句子里"是一种**形态**；
   "外来字符占 27%"不是。
3. **旧判据别删，降级成兜底。**
   两条判据各自管一种形态：段判据管"混进来一个词"，
   比例兜底管"被空格/拆字打散"（真实样本
   `'<right>د ه گ ی</right>'` —— 模型把词拆成单字符加空格，
   段判据完全失效）。**任一命中即判坏。**
4. **兜底判据也要和主判据口径一致。**
   主判据排除了"源文里本来就有"的外来词，
   兜底一开始没排除 —— 于是 `'падеж means case'` → `'падеж 是格的意思'`
   这种**正确**译文被判坏（比例 50%，远超阈值）。
   两条判据口径不一致，就会在"主判据没命中、兜底命中"的缝隙里误杀。

### 一个"复用正则"的静默失效

段正则原先想省事，用 `_FOREIGN_SCRIPT_RE.pattern.strip("[]")` 拼出来。
`strip` 会把字符类里的 **`-`** 一起切掉，于是段正则
**静默匹配不到任何东西** —— 判据等于没写，而且**不报错**、
测试也全绿（因为"抓不到坏样本"和"样本都是好的"看起来一样）。

改法：抽一个 `_FOREIGN_SCRIPT_RANGES` 常量给两个正则共用。
并且加了一条测试直接钉住"同一字符重复 3 次必须能被段正则认出"。

### 三次都是同一个根因：夹具比真实数据"乖"

第 18、17、20 条 bug 表面无关，根因完全一样：

| # | 夹具长什么样 | 真实数据长什么样 | 漏掉了什么 |
| --- | --- | --- | --- |
| 20 | 指令是数组 `[401,0,[...]]` | 指令是字典 `{"code":401,...}` | **20,065 句台词一个字没翻** |
| 17 | 假 VLM 返回像样的词 `"Restore"` | 真模型返回 `'? ? ? ? ? ? ?'`，每次 4～48 秒 | 整个阶段从 2 分钟变成 5 小时 |
| 18 | 干净矩形 + 规整文字 | 图标表/行走图，OCR 产生大量噪声 | 47% 像素被涂改；元话被画进游戏 |

**抽象出来的规矩**：

1. 如果一段代码要处理"外部数据"，测试必须**至少有一条直接读真实样本**的断言
   （没有样本就 `skip`，但断言要写在那里）；
2. 把真实数据里的**具体取值**抄进测试当固定用例 ——
   垃圾答案的原文、噪声块的原文、指令的两种形式；
3. 警惕"局部正确"：`gameTitle='穿过传送门'`、`terms.basic` 是中文、
   质检 3299 条通过 —— 这些全是真的，但剧情一个字没翻。
   **报告全绿不等于功能做完了**，必须把产物摊开看。
   这条 bug 是在"验证翻译效果"时把 `Map028.json` 的 401 命令打出来才发现的。

新增的教训（接着上面四条）：

5. **"默认设置"是最容易被忽略的变量**。#5 的根因是引擎的**默认开启**选项
   （资源加密），我们从没想过要处理 —— 文档里也不会强调"默认值"。
   做适配器时要把"引擎默认开启什么"当成一等公民去查。
6. **默认值 / 扩展名 / 版本号这类"元信息"必须实测**。#5 里我把 `RPGMV`
   当成 4 字节 magic（实际 **5** 字节，那个 `V` 就是第 5 字节），
   于是比对永远不成立 —— 真实文件**全都判不出是加密文件**。
   我第一版算法还错成"整个文件异或"，只有前 16 字节对得上，
   解出来的 IHDR 尺寸是 `3558706419x2399187502` 这种离谱值。
   **是真实文件把它戳穿的**：自造的夹具配错算法照样能通过。
7. **"格式变了但还能用"比"格式错了不能用"更危险**。#13 那种情况
   （裸 sfnt 顶着 `.woff` 扩展名）浏览器通常仍能加载，
   所以不会报错、不会崩，只是在别的加载器/工具链上偶发失败。
   代价为零的保真（`fontTools` 写回 woff）没有理由不做。
8. **通道/尺寸这类"形状"问题要用形状断言，别用像素断言**。#13 的
   检测就是一句 `shape[2] == 4` —— 比任何像素统计都可靠。
9. **一个 0 字节的"可能相关文件"值得追**。#12 的突破口是
   `fonts/gamefont.css` 存在但**是空的** —— 顺着它查下去才发现
   **MZ 根本不加载这个文件**（它走 `FontManager.load` + `FontFace`，
   文件名来自 `System.json` 的 `mainFontFilename`；只有 MV 在
   `index.html` 里 `<link>` 它）。这一条顺带避免了一个错误修法：
   如果按"MV 的思路"去改 CSS，MZ 上一点用都没有。

### 一个"假替身太善良"的教训

#17 是最值得记的一条。`test_vlm_fallback.py` 里那个假 VLM 一直返回

1. 把**真模型的实际回答**抄进测试，作为准入判据的固定用例

2. 用**真实游戏资产**跑一遍统计预算（"60 张图里 73 个低置信块 × 20 秒
   ≈ 5 小时"），而不是只看单次结果对不对。

### 一个"夹具退化"的教训

## 第 34 条：跑完一轮真实翻译之后，剩下的 55 条才是真信息

29,792 条里剩 55 条空译文（0.18%）。**这个数字本身没有信息量** ——
信息在"按根因归类"之后。

第一版统计只按**告警前缀**分类，得到"37 条 provider_error、
18 条 placeholder_broken"。这个分类**没有用**，因为同一个前缀下
混着完全不同的成因、修法天差地别。按**根因**重新归类才看清：

    37 条  空响应（网络抖动，重跑就好 —— 不是 bug）
    18 条  占位符：模型**丢了整行**（真信息丢失，补记号救不回来）
     7 条  占位符：`\|` 换行（可救，且落点会劈开中文词 → 有 bug）
     2 条  插件定义代码（`<JS On Expire State>` 里的 JS 不该翻）
     1 条  提示词逃逸

### 教训一：先归类，再动手

"18 条 placeholder_broken" 听起来是一个 bug。
实际是**三种**：丢整行（不可救）、停顿落点错（可救但有 bug）、
插件标签（**本来就不该翻**）—— 只有中间那种该改代码。

分类的粒度决定了能不能看清问题。**按告警文案分类几乎总是错的**，
因为告警文案是"哪个闸门拦下的"，不是"为什么坏"。

### 教训二：改好了 A，可能把 B 撑漏

这一轮最值得记的事：

修好"停顿类记号补回"之后，`tests/test_translate_integration.py`
的"完全不是 JSON"场景**变红了**。它原本是全绿的。

原因是补回会把 `<color=#ff0000></color>` 插进拒答判据的窗口里：

    模型回复: '抱歉，我无法完成这个请求。'            → 拦住 ✅
    补回标签: '抱歉，<color=#ff0000></color>我无法…'  → 漏掉 ❌

拒答判据是"道歉 + 做不到**隔得不远**"，中间窗口 `{0,12}` ——
给 `请稍等，我现在无法确定` 这类写法留的余地。
而一个 25 字符的颜色标签就把窗口撑爆了。

**两道闸门之间有"窗口"这种软约束时，前面那道闸门的输出会改变后面的判定。**
补回逻辑插进去的是**玩家看不见**的记号，所以正确做法是让判据看
"玩家读到的文本"，而不是把窗口调宽（调宽会放进真拒答的同义词）。

### 教训三：放宽一个判据时，必须同时说清"放宽的依据是什么、边界在哪"

`_snap_to_boundary` 的半径从 6 放宽到 24。这不是拍脑袋，依据是：

* `\n` / `%d` 的**绝对位置**有意义 → 半径必须窄；
* `\|` / `\.` 是**停顿**，绝对位置不必精确，但**必须落在词缝里**。

所以放宽**只对停顿类生效**。如果一刀切放宽到 24，
"纯汉字无任何标点"的换行会被补到句子中间 —— 那正是
`test_placeholder_repair.py` 里三条"应拒绝"用例钉住的行为。

**放宽判据的测试，一半要测"该放行的放行了"，另一半要测"不该放行的仍然拒绝"。**

## 第 35 条：ERROR 级判据在真实数据上误报 59 组 —— 那比没有判据更糟

质检跑完报 786 个问题，其中**唯一的一个 `error`** 是"反向碰撞"那条：

    59 个译文被多个不同的短标签共用（缩写很可能译错）

判据本身有来历（`MP` 被译成"生命值"，应为"魔法值"），
但它在真实数据上命中的 59 组**没有一组是真问题**：

    '操…' / '等等…'                     → '喂…'
    'Eh?/为什么？/什么事？/什么？/啊？'    → '怎么了？'
    '*脸红*' / '*臉紅*'                  → '脸红'
    '你是誰？' / '你是谁？'                → '你是谁？'

两类天然误报：**语气词一对多**（`Eh?`/`Hm?`/`啊？` 译成"怎么了？"完全正确）
和**简繁/全半角变体**（`你是誰？` 与 `你是谁？` 是**同一条目**的两种写法）。

### 教训一：`error` 级判据会卡住整条流水线

`qa` 的 `ok` 定义为 `error 数 == 0`。所以这一个误报
**直接让 `apply` 没跑成**（`✗ 阶段「质检」失败`）。

`warn` 级误报只是噪音，`error` 级误报会**挡住交付**。
反过来说：判据的级别定得越高，越要先拿真实数据量一遍误报率。

### 教训二：一个永远在误报的判据，比没有判据更糟

它同时消耗"报告的可信度"和"人的注意力"。
一旦人学会"这条不用管"，**真正报出来的那次也会被忽略**。

所以这里不是"接受 59 组误报、写进已知限制"，而是**收紧到 0 组**。

### 教训三：收紧要改**形状**，不是改**数字**

第一反应是把 `_COLLIDE_MAX_LEN` 从 4 调到 3。不行 ——
`Eh?` 长度 3、`Hm?` 长度 3，照样命中。

**又一次"判据落在边界上"**（见第 33 条）。真正的区别是**形状**：

| | 语气词 / 短句 / 变体 | UI 缩写 |
|---|---|---|
| 例子 | `Eh?` `Hm?` `啊？` `你是誰？` | `HP` `MP` `EXP` `HP%` |
| 形状 | 含问号/波浪号/星号/**汉字** | **纯 ASCII 字母数字** |
| 该报吗 | ❌ 一对多很正常 | ✅ 一定译错 |

判据从"长度 ≤ 4"改成"长度 ≤ 4 **且形如缩写**"
（`^[A-Za-z0-9][A-Za-z0-9_+\-./%]*$`），59 → 0。

**代价是刻意接受的**：`Hm` 与 `MP` 撞词这种"一个是缩写、一个是语气词"
的情况不再报。换来的是判据真正可用了。

### 教训四：放宽判据必须配一半"不许放宽"的测试

`test_real_data_false_positives_are_not_flagged` 把真实数据里
误报过的 22 组钉下来（**这批数据是从 59 组里挑的代表，
不是编出来的**），而
`test_ascii_abbreviations_are_still_flagged` 守住另一半：
`HP`/`MP` 与 `ATK`/`DEF` 仍然必须报。

只测"不报了"会掩盖"判据被彻底关掉"这种最省事的假修复。

## 第 36 条：换"更大的模型"之前，先量清楚现在这个错在哪

用户要求"用最好的开源模型"。花了一轮把候选模型真装下来、拿**真实游戏
文本**量，结论是**不换**。记录这个过程，因为结论反直觉。

### 量出来的三件事

**一、7B 翻译专精模型（Hunyuan-MT / HY-MT1.5）在真实数据上不如 4B 的 `translategemma`**

| 模型 | 空译文 | 占位符坏 | 丢 `%n` 变量 | 提示词回显 | 平均秒 |
|---|---|---|---|---|---|
| `translategemma:4b`（现用） | 0 | 8 | **3** | **0%** | 0.69 |
| `huihui_ai/hunyuan-mt-abliterated:7b` | 0 | 8 | — | 幻觉元话 | 1.03 |
| `demonbyron/HY-MT1.5-7B` | 0 | 8 | 2 | **13%** | **0.60** |

`abliterated`（去审查）那一版会**把源文当成一段需要说明的对话**，
输出 `'这是角色之间的对话。请保留说话者的口气…'` ——
**去审查顺带把指令跟随能力也去掉了**，这本身是一条经验。

`HY-MT1.5` 更快（0.60s vs 0.69s）、变量保住略好，但**13% 的条目
把提示词当成译文吐出来**：

    'Una herramienta versátil…'  →  '这是一份物品/技能说明。请完整保留…'
    'eventos CG'                 →  '中文译文'
    '[Magic Equipment] A robe…'  →  '这是一件蕴含魔力的长袍。完整保留其中的数值与单位…'

一局游戏里每 8 条就有一条是这种"看着像中文、其实是提示词"的垃圾。

### 教训一：**替换文本**和**追加文本**的失败模式完全不同

第 9 条（`prompt_leak`）防的是模型**复述要求**。但那个判据对
`HY-MT1.5` 的这种回显**一条都没拦住**（实测 `check_leak` 命中 0/54）。
它输出的是一句通顺的、**和提示词不一样**的中文 ——
判据靠"和提示词像不像"抓不到它。

**一条判据只对它有样本的那一类失败有效。** 换模型等于换了一整个
失败模式集合，旧判据的命中率必须**重新量**，不能假设它还有用。

### 教训二：先看 **Modelfile**，再看模型本身

`HY-MT1.5` 的回显不是模型能力问题，是**打包问题**：

    TEMPLATE  … <|startoftext|>{{ .System }}<|extra_4|> … <|extra_0|>
    PARAMETER temperature 0.7
    PARAMETER top_k 20

Hunyuan-MT 的 prompt 里 `extra_0`/`extra_4` 两个槽位本该填**目标语言**，
这个 Modelfile 让它们**空着**；同时把 `temperature` 硬定成 0.7
（我们的配置是 0.2，**被 Modelfile 覆盖了**）。

所以"换模型"之前该先问：**这是模型不行，还是这个量化包不行？**
两者要修的完全是两件事。

### 教训三：真正提升质量的往往是**判据和提示词**，不是参数量

这一轮最后**没有换模型**，但拿到了两个真实收益：

1. 发现 `%1` 这种**消息变量根本没被保护** ——
   真实游戏 357 条里 **189 条（53%）丢了行动者名字**（见第 37 条）；
2. 发现**屏蔽反而让模型更容易丢它** —— 不屏蔽保住约 50%，
   屏蔽之后只有 0～14%（这个反直觉的结论花了 6 种记号 × 4 版提示词
   才量清楚）。

**"用更好的模型"是个很贵的假设；"先把当前模型的错误量清楚"通常更便宜，
而且往往能直接指出真正的瓶颈在哪里。**

## 第 37 条：`%1` 不是标点，是数据 —— 而且**屏蔽它会让它更容易被丢**

`Database → 用语` 里的战斗消息写 `%1` `%2`，游戏运行时替换成
**行动者名字**与**目标名字**。真实游戏实测：

    357 条含 %n 的条目中，189 条（53%）译文丢了变量
      1→0  74 条     '%1 attacks!'  →  '攻击！'
      2→1  96 条     '%1 casts %2!' →  '%1 施法！'
      3→1  13 条
      3→2   5 条

玩家看到 `'攻击！'` —— **谁攻击、攻击谁，全没了。**
而这 189 条**静默通过了所有检查**：不是漏译、不是复读、
占位符校验也不管（它压根不认识 `%n`）。

### 教训一：判据漏了一个形态，就整类漏掉

原来的 printf 规则是 `%\d*(?:\.\d+)?[sdfxXeEgGoc]` —— 要求**转换字符**
（`%s` `%d`）。RPG Maker 写的是**裸数字**，一条都不匹配：

    mask('%1 attacks!')  →  槽位 []      # 零个占位符

**判据只覆盖了"标准形态"，而游戏引擎经常用"简写形态"。**
这和前面 `\D` / `\R` 裸字母转义是同一类事故
（见 `lang.py` 里 `plugin_letter_escape` 的注释）。

### ★ 教训二：**屏蔽一个记号，可能让它更容易被丢掉**

最直觉的修法是"把 `%1` 屏蔽成 `⟦0⟧` 保护起来"。**实测这是反的。**

拿 14 条**真实丢过变量**的源文做 A/B：

| 做法 | `%n` 保住 |
|---|---|
| 屏蔽成 `⟦0⟧` + 基线提示词 | **0 / 14** |
| 屏蔽成 `⟦0⟧` + "必须保留" | **0 / 14** |
| 屏蔽成 `⟦0⟧` + "这是名字" | **1 / 14** |
| 屏蔽成 `⟦0⟧` + 说清语义 + 反面例子 | **1 / 14** |
| 6 种别的记号长相（`{{0}}` `<ph0/>` `${0}` `[[0]]` `<0>`…） | 最好不到一半 |
| **不屏蔽**，让模型直接看到 `%1` | **约 7 / 14** |

原因：`⟦0⟧` 是无语义的**装饰符**，而 `%1` 在训练数据里是
**有含义的格式串**（printf 家族）。
**把语义换成装饰，模型就把它当噪音清掉了。**

### 教训三：保护一个记号有**两条**路，别默认选"藏起来"

| 路线 | 做法 | 适用 |
|---|---|---|
| **藏起来** | 屏蔽 → 校验还原后的多重集 | 模型**不知道**它是什么（`\C[29]` `<right>`） |
| **让它可见** | 不屏蔽 → 出站比对数量 | 模型**知道**它是什么（`%1` 是格式串） |

选错的代价很具体：藏起来那条路让保住率从 ~50% 掉到 ~7%。
**判断依据是"模型认不认识这个记号"，不是"它重不重要"。**

出站判据取"**数量 + 内容**"而不是"位置"：中文语序本来就活
（`'%1 攻击！'` 与 `'攻击！%1'` 都不算错），
但数量少一个、或者 `%1` 变成 `%2`（把行动者显示成目标），
都是确定无疑的损坏。宁可判失败，也不写一句坏话进游戏。

## 第 38 条：**"产出少"不一定是缺陷** —— 先量出分母是什么

贴图阶段报 `69/750 张贴图已汉化`。这个数字**看着像失败**：
只有 9% 的贴图产出了。第一反应是"OCR 漏检了 681 张"。

**量过之后，69/750 是正确结果。** 681 张里绝大多数本来就没文字
（战斗背景、立绘、地图装饰、行走图、CG）。RPG Maker 的
`img/battlebacks1|2`、`img/titles1|2`、`img/pictures` 主要是纯美术。

### 怎么量"漏了多少"

**再跑一遍同一个 OCR 引擎毫无意义** —— 同一个模型给同一个答案。
需要**正交的第二种证据**：

| 证据 | 独立性 | 结论 |
|---|---|---|
| 强边缘像素占比 | 与 OCR 完全无关（纯图像统计） | 全部 < 27%，无"文字墙"特征 |
| **VLM 独立读图** | 不同模型、不同机制 | **24 张抽查：0 张有文字** |
| 目录语义 | 人工常识 | 全是背景/立绘/标题画 |

抽的 24 张是**按可疑度排序取最可疑的一半 + 分层随机一半**，
不是随便抽的 —— 偏高可疑度取样会**高估**漏检率，
是保守方向的偏差。结果 0 命中，所以"这些图真的没有文字"是可靠的。

### 教训一：**分母不可信时，比例没有意义**

`69/750` 里的 `750` 是"扫到的图片数"，不是"含文字的图片数"。
拿它当分母会得出"只完成 9%"这个**错误**结论，
然后去修一个**不存在**的 bug。

**先问"这个分母是什么"，再问"这个比例好不好"。**

### 教训二：VLM 的正确用途是**离线评估**，不是在线兜底

同一个 VLM，两种用法结论相反：

| 用法 | 代价 | 结论 |
|---|---|---|
| **在线兜底**（逐块重读低置信块） | 750 张图 +5 小时 | ❌ 实测 0 更好、2 更差 |
| **离线抽样评估**（看几十张图回答"有没有字"） | 107 秒覆盖 68% 的图 | ✅ 直接定量了漏检率 |

原因是**调用次数的量级不同**：兜底是 O(块数)（上百个/张图），
评估是 O(图数)（一张图一次）。同一个模型，
**按"每图一次"用是划算的，按"每块一次"用是灾难**。

`qwen3-vl:4b` 实测 4.5～9 秒/张。它的超时不是模型慢，
而是**我们在问一个不该问那么多次的问题**。

## 第 39 条：判据"看起来对"不等于"会生效" —— 三个静默失效的判据

Unity 那条线上一次撞到 **三个判据形态错误**，共同点是
**都不报错、只是静默地给出错误结果**。这类 bug 比崩溃难查得多。

### ① 路径匹配被分隔符打败

`_in_runtime_infra` 最初写 `"/".join(p.parts)`。Windows 上
`Path("Mono/etc/x").parts` 拼出来**仍是反斜杠**，
于是 `"/mono/etc/" in low` **永远为假** —— 排除规则一条没生效。
改完之后数字**一条没变**，才发现是这个。

**修法**：统一 `path.as_posix().lower()`。

### ② 正则用了 raw bytes 前缀

`rb"\x00{64,}"` 里的 `\x00` 是**字面四个字符**（`\`、`x`、`0`、`0`），
不是零字节。它在正则里**碰巧也能用**（正则引擎会把 `\x00`
再解释成零字节），所以两个写法都"能跑"—— 于是更难发现。
但配合 `match(data, pos)` 的字节匹配语义就出现了偏差。

**教训**：字节级正则不要用 `rb`，用 `b` 让转义先展开。

### ③ 长度前缀比了**字符数**而不是**字节数**

```python
if s and len(s) == ln:      # ❌ ln 是字节长度，len(s) 是字符数
```

对纯 ASCII 两者相等，所以**英文测试全过**；
而 `你确定要保存吗？` 是 **24 字节 / 8 字符**，
`len(s) == ln` 永远为假 ⇒ **所有中文文案被静默丢掉**。

这个 bug 的可怕之处：这份功能的用户**就是要翻中文**，
所以它把最该收的漏光了，而英文路径完全正常 ——
**用英文样本测永远发现不了**。

**修法**：`len(raw) == ln`（比字节）。

### 教训：判据必须用**目标语言**的样本验证

③ 是本次唯一一个"测试全绿但功能对目标用户完全无效"的 bug。
原因是所有测试数据都是英文的。

**"测过了"不等于"对目标场景测过了"。**
以后凡是涉及长度/编码/大小写的判据，
**必须至少有一条 CJK 样本**，否则等于没测。

## 第 40 条：噪音滤除的三次翻车 —— "判据落在边界上"

给 Unity 序列化资源做只读文案提取时，噪音滤除改了**五轮**，
每轮都是**判据形态**错，不是阈值错。

| 轮次 | 判据 | 后果 | 为什么错 |
|---|---|---|---|
| 1 | 只排除文件名 | 抽出 **530,507** 条（33 MB 播放器日志） | 判据按"后缀像不像文本"，不按"是不是游戏内容" |
| 2 | 加运行时目录 | 还剩 **9,586** 条（`Mono/etc/`） | 同上的变体 |
| 3 | 加"全大写首词 = 音效名" | 拦掉 **`THANK YOU FOR YOUR SUPPORT!`** | 全大写文案在游戏里**非常常见** |
| 4 | 加 SQL 关键词（`IGNORECASE`） | 拦掉 **`Select Location to Teleport.`** | SQL 关键字是**全大写**惯例，`Select` 恰恰是句子写法 |
| 5 | 单词一律拒 | 漏掉 **`Options`/`Continue`/`Settings`** | 单字菜单项是最常见的 UI 文案 |

最终 **28 条去重候选**（从 716 MB 里），真实文案全在内。

### 规律：判据的**形态**错了，调阈值救不回来

* 第 1、2 轮错在**分类轴**（"像不像文本" vs "是不是游戏内容"）；
* 第 3、4 轮错在**过度泛化**（一个特征被当成充分条件）；
* 第 5 轮错在**把"常见"当成"必然"**。

三次都是**换判据**解决的，没有一次是调数字解决的。
**判据落在边界上，就说明判据选错了。**

### 反向代价不对称

宁可多收几条资源名（人工扫一眼就能剔），
也不能漏掉按钮文案 —— 漏掉会让用户以为"工具没找到东西"。
**代价不对称时，判据要往代价大的那一侧偏。**

## 第 41 条：跳过优化的"正确性"必须**可证明**，不能靠经验

617 MB 的资源里逐字节扫太慢，于是写了跳过优化：

```python
# ❌ 第一版：连续 4096 次未命中 ⇒ 前跳 64 KB
if since_hit >= 4096: i += 64 * 1024
```

理由听着很合理："那段区间本来就没有候选"。
**实测数据直接否掉它**：

* `level0` 有 **13** 条真实候选，加上跳过后**只剩 1 条**；
* 相邻候选的间隔是 **10,681 / 17,585 / 33,553 / 49,353 字节** ——
  和 64 KB 是**同一量级**。

也就是说，"连续未命中"**推不出**"接下来没有候选"。

### 改成可证明的版本

现在只跳**连续 ≥ 64 个零字节**的区域：

> 长度前缀 `≥ MIN_LEN(4)` ⇒ 字符串起点的**首字节非零**
> ⇒ 连续零字节里**不可能**有起点。

这个结论**不依赖任何经验阈值**，跳跃范围有严格上界，
而且速度一样够（10 MB 零区从 0.40 秒降到毫秒级）。

### 顺带：找零区结尾也不能用 Python 循环

`while data[e] == 0: e += 1` 在 10 MB 零区上要 **0.40 秒**
（就是 Python 逐字节解释开销）。
改成正则 `\x00{64,}` 的 `match(data, pos)` 拿 `m.end()`，
C 实现一次到位。

**"优化"如果依赖一个没被验证的经验假设，它就是在**静默**丢数据。**

## 第 42 条：大文件"跳过"是**更隐蔽**的丢数据

早先版本给序列化资源扫描设了 `max_bytes = 400 MB`，超过就跳过并报一句
"已跳过以免吃光内存"。于是那个游戏的**主资源正好是 613 MB** ——
**最可能藏文本的文件根本没被扫**，而报告显示"扫描成功"。

用户拿到的是**一份不全的清单**，且**看不出来不全**。

改成**分块流式扫描**（8 MB 块 + 4 MB 重叠）后：
内存占用与文件大小无关，**没有任何文件因为"太大"被跳过**。

### 教训

**"因为太大而跳过"必须同时做到两件事**，否则不许写：

1. 让用户**看得出来**跳过了什么（不是一句"已跳过"）；
2. 确认这个跳过**不影响结论的正确性**。

做不到就改成流式/分块 —— 内存是工程问题，**数据完整性不是**。

## 第 43 条：**"重试"跑不起来，比"不重试"更糟** —— 两个叠加的静默失效

Ren'Py 的成对文本标签（`{color=#ffd700}…{/color}`）会被
`translategemma:4b` **整条丢掉**：

```
源文  {color=#ffd700}The lamp was lit at dawn.{/color}
掩码  ⟦0⟧The lamp was lit at dawn.⟦1⟧
首译  '灯在黎明时被点亮了。'          ← 两个记号都消失了
```

`repair_dropped_masks` 会把成对标签**补回一个位置**（实测把 `{/color}`
补到句末）。这个位置是**猜**的 —— 但接受这个猜测，理由见下面"已知取舍"。
真正拦住坏译文的是写回闸门 `is_unsafe_writeback`。

所以加了**定向重试**：只对已经失败的条目、用点明记号的提示重问一次。
逻辑写好了、日志加了、测试也过了 —— 然后实测 **27/28 没变**。

**因为它一次都没跑起来。** 两个独立的原因叠加：

### 原因一：`mapping[0]` 不保证是字符串

```python
mapping, res = parse_translations(raw, expect_indices=[0])
if 0 in mapping:
    return mapping[0]              # ❌ 可能是个 list
```

模型对单条请求回了 `{"t": ["清晨，油灯被点亮了。", ""]}` ——
把单条当成了数组。于是 `mapping[0]` 是个 **list**。

这个 list 一路带到 `verify_restored`，在那里对 list 调用字符串方法
抛异常；而重试逻辑写的是 `except ProviderError: continue`，
异常类型不匹配就直接冒到外层被吞掉 —— **重试静默失效**。

> **判据**：`_call_single` 的契约是"返回 `str`"。
> 违反契约的值必须在**边界处**拦住，不能指望下游每个人做类型检查。
> 现在 `_call_batch` 出口也会把非 `str` 的值**丢掉并记日志**。

### 原因二：纠正提示里的 Markdown 把模型带偏了

第一版重试提示写成了带 `⚠️` 和 `**加粗**` 的排版。实测模型输出：

```
{"t": ["清晨，油灯被点亮了。", ""]}     ← JSON 结构都变了
```

**追加到提示词末尾的"纠正指令"越朴素越好。** 改成编号 + 短句
（且**不用 emoji / Markdown**）之后，模型恢复正常结构。

### 但即使两个都修好，这条仍然没救回来

修好以后重试**确实跑起来了**，模型也**确实重新回答了** —— 但它
还是把两个记号丢掉了。所以最终仍是 27/28。

**这不是 bug，这是判据在正确工作**：

* 守卫拒绝回写 ⇒ 游戏里这一行**保持英文原文**；
* 假使当初"宽容"地写回 ⇒ 游戏里出现**没有被染色的句子**
  （或者更糟：把颜色标到错的字上）。

**宁可留一句英文，也不给玩家一句颜色标错的台词。**
失败条目在 `qa` 与文本审校页里列出来供人工处理。

### 教训

1. **"加了重试" ≠ "重试会跑"**。必须有办法**数出来重试触发了几次**
   （`stats["marker_retry_recovered"]`），否则"没效果"和"没运行"
   从外面看完全一样。
2. **静默失效最爱藏在 `except` 的类型不匹配里**：`except ProviderError`
   抓不住 `AttributeError`，而异常被外层吞掉 ⇒ 什么都不报。
3. **喂给模型的"纠正指令"要朴素**。Markdown/emoji 会改变输出的**结构**，
   不只是风格。
4. **救不回来时，坚持拒绝写回**才是正确行为。
   重试是提高成功率的**优化**，不是正确性的**依靠**。

### 已知取舍：成对标签的补回位置是"猜"的

我一开始想加一条"一个记号都没剩时不许补回"，理由是"信息已经丢了，
补就是猜"。写完立刻有 **12 个用例变红** —— 全是 RPG Maker 的
单侧转义（`\C[6]标题` 整条被模型删掉记号），而**那些是真能救回来的**。

所以这条一刀切的规则**退回去了**。现在接受的取舍是：

| | 单侧转义（`\C[6]`/`\n`/`%1`） | 成对标签（`{color}…{/color}`） |
|---|---|---|
| 补回位置 | **确定**（只能在开头/中间/末尾） | **猜**（锚点映射，可能偏） |
| 最坏后果 | 无（位置唯一） | 某几个字颜色和原文不完全一致 |
| 是否接受 | 接受 | **也接受** |

接受成对标签猜测的前提是三条**都已成立**：

1. 补回**只插记号、不改正文**（有测试逐字校验）；
2. 补完仍要过 `verify_restored`（数量与内容齐全）；
3. 最终还要过 `is_unsafe_writeback` 写回闸门。

最坏后果是"配色不完全一致"，而不是崩溃、乱码或变量丢失 ——
对"整条不翻、玩家看到一句英文"而言，用户更倾向要中文。

> 如果将来发现某类标签猜错代价很高（例如**控制排版**而非配色，
> 猜错会让文字重叠），应当按**标签类型**分别决定，
> 而不是保持现在的一刀切"都可以猜"。

## 第 44 条：Ren'Py 回写要**逐行**验证，不能抽查

`.rpy` 是**可执行代码**。伤到 `python:` 块、`$` 行、缩进或转义引号，
游戏**直接报错起不来** —— 而"起不来"和"翻译没做完"是两种完全不同的
故障，用户必须能区分。

合成工程（83 行，28 条文本单元）端到端验证结果：

| 检查项 | 结果 |
|---|---|
| 行数一致 | 83 = 83 ✅ |
| 变化的行是否都在文本单元内 | 27 行全在，**越界 0 行** ✅ |
| `python:` 块 / `$` 行 / 文档字符串 | 逐行 `==` 一致 ✅ |
| `[player_name]` 插值 | 保留 ✅ |
| 转义引号 `\"…\"` | 输出改用中文引号 `“…”`（等价且更正确） |

### 有意思的一处

`"She said: \"Meet me at the pier, and bring the key.\""`
译成 `"她说：“在码头上见我，带上钥匙。”"` —— 产物里**没有** `\"` 了。

这个**不是缺陷**：中文引号 `“”` 是普通字符，在 Ren'Py 字符串里
不需要转义。**照抄 `\"` 反而是错的**（会让游戏里显示出反斜杠）。
我的验证脚本一开始把"产物里必须有 `\"`"写成断言，于是报了假失败
—— 和 `tests/README.md` 开头那条"指标写错比没有指标更糟"同一个毛病。

> **判据**：验证"转义语义是否保住"，而不是"转义**字符**是否还在"。
> 前者需要理解语法，后者只需要字符串比较 —— 后者会骗你。

## 第 45 条：**一整个文件被静默跳过** —— 34,151 条剧情对白

真实 MV 游戏的 `data/Scenario.json` 是 **11 MB、981 个场景**的剧本文件，
里面有 **37,146 条 `code 401`（显示文字）** —— 这个游戏的**主要剧情对白**。

而 `extract_text` 的派发链里**根本没有它的分支**：

```python
if f.name == "MapInfos.json": ...
elif f.name == "System.json": ...
elif f.name.startswith("Map") ...: ...
elif f.name == "CommonEvents.json": ...
elif f.name in DATABASE_FIELDS: ...
elif f.name == "Tilesets.json": ...
# ← 没有 else，Scenario.json 静默掉队
```

于是：

* 工具报"抽取 **29,174** 条文本"，**看着很正常**；
* 实际 **34,151 条去重剧情对白一个字都没抽到**；
* 玩家打开游戏：**菜单是中文，剧情全是英文**。

### 为什么这个 bug 特别难发现

1. **报告全绿**。"少抽了一整个文件"不会让任何断言失败 ——
   数字只是"小一点"，而没人知道正确数字是多少。
2. **一半是好的**。同一个游戏的 `CommonEvents.json` **是被处理的**，
   所以会呈现"支线事件翻了、主线剧情没翻"的半成品状态。
   这比"什么都翻不动"更难判断 —— 用户会以为是自己看错了。
3. **跳过的文件不可见**。循环末尾那段"统计被跳过的原因"是个**空壳**：

   ```python
   # 统计被跳过的原因
   for _ in range(0):
       pass
   ```

   **没有任何输出**告诉用户有文件被跳过。

### 修法

1. 加 `Scenario.json` 具名分支（结构是 `场景名 → 指令列表`，
   与 `CommonEvents.json` 的 `list[dict]` 不同，要自己包一层再交给
   同一套指令解析）；
2. 加 `else` **结构兜底**：像剧本的抽一遍，不像的记进 `skipped`
   让用户**看得见**；
3. 场景名（`'1'`/`'EV22'`/`'00boheA_deai1'`）**不抽** —— 是内部标识；
4. `code 356`（**88,048 条**插件指令）与 `355/655`（脚本）照旧不碰。

**抽取量 29,174 → 65,570。**

### 教训

> **"少抽了一整个文件"是静默失效里最隐蔽的一种。**
> 别的静默失效至少还留下"某条译文不对"的痕迹，
> 而它只让**数字变小** —— 没有任何东西是"错"的。

所以**没有 `else` 的派发链本身就是 bug**：
只要格式是"按文件名分支"，就必须有一条兜底，
让**没被认领的文件**出现在报告里。

## 第 46 条：抽取器写好了，**不等于它会跑**

这是第 45 条的下半段，单独列出来因为它是**测试设计**上的教训。

我写完 `_extract_scenarios` 之后，测试直接调它：


## 第 47 条：复读判据的假阳性 —— "掩码原文" vs "还原译文"

`check_repetition` 的运行时机很微妙。在 provider 里被调用时：

* **原文还是掩码状态**（`⟦0⟧`）；
* **译文已经还原**（引擎转义码回来了）。

```
掩码原文  '…Weapon Type: ⟦0⟧⟦1⟧   Armor Type:⟦2⟧⟦3⟧⟦4⟧'
还原译文  '…武器类型：\I[96]\I[97]   护甲类型：\I[129]\I[135]\I[139]'
```

`strip_placeholders` 认引擎转义码（`\I[96]`、`%1`），
但**不认掩码记号** `⟦0⟧`。而早先只对 `source` 调用它：

* 原文里的重复 → 减掉了；
* 译文里**还原出来的同一批图标码** → 没减掉 ⇒
  n-gram `']\I['`、`'\I[1'` 命中 ≥3 次 ⇒ **误报复读** ⇒
  整条判致命、**译文被清空**。

实测误报 **13 条**，全部是 `Actors.json` 的角色 profile，
**译文完全正确**（含武器/护甲图标码）。

修法：两侧都过一遍"掩码记号 + 引擎转义码"的归一化，只比较**真实文字**。

### 为什么之前的测试没抓到

因为这个形态**只在"掩码翻译 + 占位符还原"同时开启时**出现。
用不带占位符的样本测，两侧都是裸文本，看不出问题。

所以新的测试**必须成对**给出"掩码原文 + 还原译文"，
而且**真阳性用例要和假阳性用例放在一起** ——
把判据削到"什么都不报"，假阳性测试也会全绿：

| 用例 | 期望 |
|---|---|
| 掩码原文 vs 还原译文（图标码相同） | **不报** |
| 干净源文 + `你好你好你好…` | **要报** |
| 干净源文 + `yes yes yes…` | **要报** |
| 原文自己就重复（`no no no`） | 不报 |
| 普通长句 / 带 `%1` 的正常译文 | 不报 |

> **判据**：修假阳性时，真阳性用例**必须**同批增加。
> 只减不增的"修复"很容易变成"把判据废掉"。

## 第 48 条：单条请求收到**批格式**回答 —— 静默丢掉后半句

模型把**原文里的换行**当成"两条独立文本"，于是对单条请求
按**批**的格式编号回答：

```
源文  '…Bohelos. Not very athletic.\nWeapon Type: \C[6]Sword\C[0]'
输出  {"t": [{"i": 0, "t": "来自博赫洛斯王国的女孩。并不擅长运动。"},
             {"i": 1, "t": "武器类型：剑"}]}
```

`parse_translations` 摊成 `{0: …, 1: …}`，于是：

* `mapping[0]` 是**合法字符串** ⇒ 类型检查抓不到 ⇒
  只取它 = **静默丢掉第二行**（译文看着完全正常，只是少一半）；
* 而更早的写法 `return mapping[0]` 在值真是 `list` 时会把 list 带下去，
  在 `verify_restored` 对 list 调字符串方法时抛 `AttributeError`；
  重试逻辑写的是 `except ProviderError`，**类型不匹配**，
  异常冒到外层被吞掉 ⇒ **重试静默失效**。

### 修法：按**编号顺序**接起来

编号是模型自己给的顺序信息，比字典插入顺序可靠，
而且**不丢任何内容** —— 比"只取第一段"和"整条拒收"都好。

⚠️ 但**只在编号连续、都从 0 开始时**才敢接：
编号有洞（`{0:…, 2:…}`）说明模型自己都没弄清段落边界，照旧拒收。

### 附带发现的**越界编号**问题

模型会在批响应里给出本批不存在的编号（本批 2 条却回 `{"0":…, "2":…}`）。
早先只做：

```python
missing = [i for i in expect if i not in mapping]
```

越界编号**不参与判断、又占着一个键**，于是真正缺的那条
**不会被发现** ⇒ 补漏逻辑静默跳过。现在越界编号直接剔除。

> **判据**：解析层的输出必须做**完整校验**
> （类型 + 编号连续 + 编号在范围内），不能只查"有没有"。
> "有一个合法字符串"和"这个字符串是对的"是两件事。

## 第 49 条：判死之后**没把垃圾清掉** —— 三条坏译文差点让整个游戏满屏口口口

这是本项目见过**链条最长**的一次静默失效。每一环单独看都没问题：

| # | 环节 | 单独看 |
|---|---|---|
| 1 | `foreign_script` 守卫判坏 3 条跑偏译文 | ✅ 判据正确 |
| 2 | provider 里 `entry.target = res.text` **无条件赋值** | ❓ 看着无害 |
| 3 | `fonts` 阶段 `_collect_texts()` 只看"target 非空" | ❓ 看着合理 |
| 4 | 那几个外文字符本机任何 CJK 字体都没有 | — 事实 |
| 5 | 字符集缺字**硬失败** | ✅ 契约正确 |
| 6 | 字体适配中止 ⇒ `apply` 把原字体**原样拷**过去 | ❓ |
| 7 | 原字体中文覆盖只有 4.6%~77% ⇒ **满屏口口口**，而流水线报"成功" | 💥 |

被拒绝的译文：

```
'приходится долго ждать动画，真是让人受不了。'   ← 俄文
'等等！？你要去打შინ纳王？这不可能！'              ← 格鲁吉亚文
```

**判据没错，错在拒绝之后没把垃圾清掉。**

### 两处修，缺一不可

1. **源头**：`entry.target = "" if res.fatal else res.text`。
   `FAILED` 的语义本来就是"没有可用的译文"——
   `_invalidate_entries()` 一直是"清空 + 标 FAILED"，只有 provider 漏了。
2. **下游**：`_collect_texts()` 按 **status** 过滤，而不是按"target 非空"。

只修源头 ⇒ 重跑之前写坏的条目**仍然**污染字符集；
只修下游 ⇒ 垃圾继续在文件里堆积、翻译记忆与审校页都要各自防一遍。

> **判据**：**"拒绝"必须是一个原子动作** ——
> 标记状态和清除内容要一起做。
> 只标状态不清内容，等于把垃圾留在管道里，
> 而下游每多一处"只看内容非空"的判断，就多一个引爆点。

## 第 50 条：**猜测**的字符不该和**真实文本**的字符共用一条硬失败判据

`UI_SAFE_CHARS` 是一张"游戏界面**一定**会渲染到的字符"清单，
列了几百个装饰符号。它默认整个并进所需字符集，
而字符集缺字触发**硬失败**：

```
❌ ok=False  错误=字符集里有 4 个字符没有任何候选字体能提供：※‥′″
```

问题在于这几个符号**本机任何一个 CJK 字体都没有**
（`lxgw-*`、`simhei`、`msyh`、`Deng`、`simsun`、`seguisym` 全试过），
而它们在 **65570 条真实文本里出现 0 次**（981 个场景，一次都没有）。

**一句都用不到的装饰符号，把整个字体阶段拦死了。**

### 原有的补救路径对，但判据是猜的

代码里已经有一条补救：补不上时，把"影响条目数 ≤ 3"的字符剔掉重试。
它的**结论**对（那几个符号确实只影响 0~1 条），但：

* 一个**真需要**的生僻字（人名用字）如果碰巧只出现在 1 条文本里，
  会被同一个判据剔掉 ⇒ 那一行照样口口口；
* 阈值 `≤ 3` 是拍的，换项目规模就未必合适。

而我们其实**知道**答案 —— `build_charset_tiers()` 就是按
"这个字符来自真实文本还是来自猜测清单"算出来的。
**用知道的事实，不用猜的启发式。**

### 契约

| 层 | 来源 | 缺字后果 |
|---|---|---|
| `required` | 译文 + 原文 + `extra` | **硬失败** |
| `optional` | `UI_SAFE_CHARS` | 只记警告 |

⚠️ **严格层仍然必须硬失败。** 修假阳性最容易犯的错就是把判据削到
什么都不报 —— 那等于把"保证不出现口口口"的核心契约废掉。
所以测试里真字符缺失必须照样报错（见
`test_strict_missing_still_fails`）。

### 实测效果

```
不过滤：严格层 2604 个字符
过滤后：严格层 2580 个字符        ← 少 24 个
少的正好是：'абгдежзиклмнопрстухьяინშ'（全部来自坏译文）
```

### 为什么**不是**去调 `max_ratio`

格鲁吉亚那条只占 16%（3/19），低于 25% 的兜底阈值。
但**不能**调低阈值：`'伤害 3π'` 里希腊字母 `π` 的比值**恰好是 0.25**，
而那是一条**正确**的译文（希腊字母在数值和术语里很常见，玩家认得）。

真跑偏靠的是**段判据**（连续 ≥3 个外来字符 = 混进来一个词），
格鲁吉亚那条正是被段判据抓住的。判据在正确工作 ——
漏的只是"判死之后没清理"（第 49 条）。

> **判据**：遇到"某个判据没抓住"时，先分清是
> **判据选错了**还是**下游没消费判据的结论**。
> 前者要改阈值/换判据，后者改阈值只会误杀。


## 第 51 条：提示词里的**输出格式示例**会成为模型要产出的那一个对象

### 症状与误判

真实吞吐卡在 **1.2~2.8 tok/s**、每批耗时 200 秒以上。第一反应是
"显卡被游戏占了"（确实还有别的问题），第二反应是"`num_ctx` 太大"
（**错的** —— 那个相关性来自 Ollama 每次改 `num_ctx` 都重载模型）。

真正把它揪出来的是**去读原始返回**：模型只生成了 **26 个 token**。
"卡死"不会只生成 26 token —— 是**模型认为自己答完了**。

### 根因：数组示例被当成"那一个对象"

提示词要求：

```
输出格式固定为对象数组，每一项都必须带索引：
[{"i": 0, "t": "译文"}, {"i": 1, "t": "译文"}]
```

同一批 40 条真实文本，只改这一段：

| 要求模型输出 | 生成 token | 返回条数 | `done_reason` |
|---|---|---|---|
| `[{"i": 0, "t": "…"}, …]` 数组 | 26 | **1** | `stop` |
| `{"0": "…", "1": "…"}` 对象 | 613 | **40** | `stop` |

模型把示例里的 `{"i": 0, "t": "…"}` 当成了"要产出的**那一个**对象"，
输出完就正常结束。**批大小无关**：4/8/16/24/40 条都只回 1 条。

### 为什么难发现：它靠**降级路径**把自己藏起来了

`_call_batch` 发现缺 39 条后走"逐条降级补漏"，于是每批发 `1 + 39` 次请求。
结果：

* 流水线一切"正常"，**译文质量甚至更好**（逐条翻译上下文更干净）；
* 只是慢 —— 慢到看起来像卡死。

**有降级路径是好事，但它会把"系统性失效"伪装成"偶发慢"。**

### 修法与护栏

* 格式改成**以行号为键的对象** `{"0": "…", "1": "…"}`，
  解析层本来就支持（`to_translation_map` 认数字键 dict）；
* **旧数组形态仍然兼容** —— 模型有时会自己换回去；
* 新增 `batch_mostly_missing` 计数 + WARNING：一批缺一半以上就单独记一笔，
  日志直接点出"先查 prompts 里的输出格式说明"。

`single_fallbacks` 这个数字**一直存在**，但"每批都 +1"和"偶尔 +1"
在汇总里看不出区别 —— 这正是它藏了这么久的原因。

> **判据**：一个"慢"的问题，先去数**模型生成了多少 token**。
> token 少 = 模型答完了 = 问题在提示词；
> token 多而耗时久 = 真的算力不够。
> 另外：**降级路径必须有计数**，否则它会掩盖触发降级的那个 bug。
> 吞吐 14000 条/小时 → 修复后实测，旧路径约 6300 条/小时。


## 第 52 条：护栏阈值定小了会**反向**工作（60 字符不是"长文本"）

`_make_batches` 里硬编码 `long_text = len(text) > 60`，超过就单独成批。
读代码时它很像"小心为上"，但真实 MV 游戏（剩余 34357 条）量出来是：

```
长度：中位 50  均值 43  90 分位 67  最大 159
超过 60 字符的：11966 条 = 34.8%
```

**90 分位才 67 字符** —— 绝大多数"长文本"只比中位数长一点点。
而"逐条"的代价是实打实的：一条 67 字符的对白和一条 20 字符的
都占满一次模型往返。

| 门槛 | 批数 | 单条批 | 平均每批 | 总请求 |
|---|---|---|---|---|
| 60（旧） | 20709 | 16027 | 1.7 条 | **20709** |
| 200（新） | 1449 | 51 | 23.7 条 | **1449** |

**请求数降到 1/14.3。**

### 关键：两个"别混批"规则防的不是一回事

* **短标签不与非短标签混批** —— 防的是长句的语言风格传染过去，
  让按钮文字变长到**溢出 UI 框**。真实会出问题，**必须保留**。
* **长文本单独成批** —— 只是"少塞点"，在 60 字符这个量级上
  没有质量收益，纯粹在浪费请求。

门槛调大**不影响质量**：它只决定"和谁一起发"，不决定怎么翻。

> **判据**：看到一个"保守"的阈值，去真实数据上量一下它命中多少条。
> 命中率高到不合理（三分之一）时，它就不是护栏而是瓶颈。
> 顺便：这个阈值要**可配置**（`max_batch_long_chars`），
> 因为"多长算长"取决于语言和游戏，不该写死在代码里。


## 第 53 条：引擎把一句话拆成多条指令 —— 逐条翻译只能拿到半句话

### 事故

RPG Maker MV 的 `code 401`（显示文字）会把一句话**按显示宽度拆开**：

```
[39] code=401  "…the suffering of the slaves in the "
[40] code=401  "Kingdom of Bohelos, where they are treated…"
```

早先把**每条 401 都当成一句独立台词**，模型只看到半句话就去翻译。
真实游戏实测：

```
连续 401 组共 23858 组
   1 条: 12406 组 (52.0%)
   2 条:  9621 组 (40.3%)
   3 条:  1826 组 ( 7.7%)
⇒ 11452 组（48.0%）是被拆开的
```

对玩家来说不是"质量稍差"：消息框第一行中文、第二行莫名其妙的补语。

### 发现它的路径（值得记）

先做的是**译文质量体检**，看到 13943 条"译文比原文短得多"，
第一反应是"模型偷懒丢内容"。去查原始 `Scenario.json` 才发现
**原文本身就是半句话** —— 问题在提取，不在翻译。

> 顺带纠正一个我自己差点写进判据的错误：中英文长度比天然偏小，
> **"译文短"本身不能作为丢内容的判据**。真正的问题是断句。

### 修法

* 连续的 401 合成一条 `TextUnit`（各片用 `\n` 连接），
  其余位置记在新的 `TextLocation.siblings`；
* 回写时 `_split_across_slots` 按行拆回各槽位；
* **`\r` 开头的是插件注释**（`//メッセージバックを黒く`），不是文案，跳过。

拆分策略里踩到的坑（测试抓出来的）：行数多于槽位时一开始用
`"\n".join(...)` 合并，把换行**留在参数里**。MV 把参数原样显示，
一个多余的 `\n` 就是消息框里一个空行、版面撑坏。
现在多格时**一律吃掉换行**；`n == 1` 原样返回。

> **判据**：处理"按显示宽度/长度切块"的引擎时，**第一件事**是确认
> "相邻的同码指令是独立语义还是同一段的碎片"。
> 判断方法：把相邻几条拼起来，看是不是一个完整句子。
> 另外：**拆回去的不变量必须是"拼起来等于原文"** —— 写一条
> 遍历"任意行数 × 任意槽位数"的不变量测试，它立刻抓到了换行泄漏。


## 第 54 条：指针与真实结构不匹配 ⇒ 回写"成功 0 个文件"（最严重的静默失效）

### 事故

`_extract_scenarios` 包了一层以便复用 `_commands_text`：

```python
self._commands_text({"list": cmds}, fname, f"/{key}/list")
```

于是每条指针都带上 `/list/`：`/1/list/0/parameters/0`。
但 `Scenario.json` 的真实结构里**没有 `list` 这个键**：

```javascript
{"1": [ {"code": 401, ...}, ... ]}      // 指令直接在数组里
```

`_set_pointer` 走到 `list` 就找不到键、返回 `False`。
**23159 条剧情对白一条都写不回去。**

### 为什么它不报错（最坏的部分）

```python
if n:
    target.write_text(...)
    res.files_written += 1
```

`files_written` **只在 `n > 0` 时**才自增，所以
"一条都没定位上"和"本来就没有要写的东西"在结果对象上**长得一样** ——
都是 `files_written == 0`。后者正常，前者灾难。阶段照样报成功。

玩家打开游戏：**菜单是中文，剧情全是原文。**

### 它是怎么被炸出来的

本来只是在给"连续 401 合并"写**回写**测试，夹具里 `apply` 直接返回
"没有任何文件被写入"。查下去才发现指针和真实结构不匹配 ——
**是给新功能写测试时顺带炸出来的一个更早、更严重的老 bug**。

如果没写这条测试，它会一路活到发布：所有单测全绿、
MZ 项目的验收数据（107 个文件正常回写）也全绿 ——
因为那条路径没有这个 bug，只有 MV 的 `Scenario.json` 会静默失效。

### 修法与护栏

1. `_commands_text` 加 `list_key` 参数：`""` 表示"没有 list 那一层"，
   `_extract_scenarios` 直接传数组 + `base=f"/{key}"`；
2. **硬闸门**：`apply` 记录"想写但一条都没写进去"的文件，
   只要存在且 `files_written == 0` 就 `res.ok = False` 并返回明确错误。

### 验证方式（比检查字符串前缀强）

把每个抽出的指针**真的走一遍 `_set_pointer`**，把原值写回去，
全部必须成功。这覆盖了**所有**抽取路径（Scenario 裸数组、Map 的
`page.list`、CommonEvents、数据库词条…）：

```
真实 MV 游戏：27642 个指针全部定位成功（修复前 Scenario 的 23159 个全失败）
```

> **判据**：一个"计数"字段如果在"什么都没做"和"做失败了"时取值相同，
> 它就不能用来判断成功。必须有一条**显式**判据把这两种情况分开。
> 另外：**给新功能写端到端测试时，一定要断言"产物真的被改了"** ——
> 只断言"阶段返回 ok"会漏掉整类静默失效。


## 第 55 条：校验判据自己也会"跨语言失效" —— 象声词被判复读

### 事故

复读判据有一条**正确**的设计：先减掉原文里本来就有的重复，
这样原文写 `no no no` 时译文重复不算错。

但它是**按字符**比对两侧的重复 n-gram，**跨语言时完全失效**：

```
源 '*Pant* *Pant* *Pant*...'   里的重复串是  *Pan / Pant
译 '喘... 喘... 喘...'          里的重复串是  喘...
```

字符上一个都对不上 ⇒ 译文的重复被当成"原文里没有的**新**重复" ⇒ 判死。
而实际上**必须**跟着重复 —— 原文就是靠重复表达动作发生了三次；
只写一遍"喘"才是**漏译**。

### 怎么确认是误报（不是猜的）

把被判 `repetition` 的条目抽 12 条**重新翻译一遍**，逐条看：

| 源 | 模型译文 |
|---|---|
| `*Pant* *Pant* *Pant*...` | `喘... 喘... 喘...` |
| `*Shake* *Shake*! *Wobble*...` | `摇一摇！摇！摇摇晃晃！` |
| `*Chomp* *Chomp* *Chomp*... *Slurp*...` | `哇啊… 咀嚼… 咀嚼… 咕噜…` |
| `*Slap* *Slap* *Slap* *Slap*!` | `啪！啪！啪！啪！` |

**12/12 全是忠实翻译。**

### 修法与依据

判据改成看**原文**：原文里同一个 4-gram 出现 ≥3 次 ⇒
"重复"是作者的手法（象声词、叠词）⇒ 整个跳过复读判据。

依据是：**"重复"这个特征，原文比译文更可信**。
译文里的重复可能来自模型故障、也可能来自原文；原文里的重复只可能来自作者。

### 代价的方向（为什么敢这么做）

* 漏判复读 ⇒ 一屏重复文字（难看，但**内容在**）；
* 误判忠实翻译 ⇒ **一条完全正确的译文被整条丢弃**（对话框空白），
  而且会送进重试、反复浪费模型调用。

后者更坏。

### 一个"减掉原文重复"的推广教训

这条判据的**意图**是对的（"原文本来就有的重复不算错"），
错的是**实现方式**（按字符比对）。跨语言的场景里，
"原文里也有"这个条件不能靠**字面匹配**来判断 ——
字面匹配只在同语言内成立。

> **判据**：任何"拿原文和译文做字面比对"的判据，都要问一句
> **跨语言还成立吗**。长度比、重复、标点形态都踩过这个坑。
> 另外：写反例时注意**输入要够长** —— `"no no"` 只有 5 个字符，
> 凑不出一个 4-gram，走的是长度短路，测不到真正的边界。


## 第 56 条：UID 换方案之后，旧译文会**静默变成孤儿**

### 事故

`/list/` 那个指针 bug 修掉之后，`CommonEvents.json` 的 UID 从
`/3/list/8/parameters/0` 变成 `/3/8/parameters/0`（少一层）。
同时 MV 的 `401` 分组让 `Scenario.json` 的条目数从 36396 掉到 23159。

结果：`translations/entries.jsonl` 里**有三代不同 UID 方案**的行共存 ——
一共 45858 行，其中只有 35388 行的 UID 对得上当前抽出的 unit，
**10470 行是孤儿**（旧 UID），还有 10184 个 unit 完全没有 entry。

而阶段报的覆盖率是 **100.20%**（"有译文"的行数 ÷ unit 数）。
它算的是"有多少行有译文"，**不是"有多少 unit 有译文"**。

### 为什么危险

孤儿行不会消失，它们会一直被算进"已翻译"，让覆盖率看起来正常。
真正没翻的 unit 混在里面看不出来 —— 又是一次
"报告全绿但产物不全"。

### 修法：按**原文**重新索引

旧译文本身没坏（翻译的就是同一段原文），只是**钥匙换了**。
所以用原文当钥匙重建：

```python
by_src = {r["source"]: r["target"] for r in 旧行 if 有译文 and 不是失败}
for u in 当前units:
    entry = 幂等保留(u.uid) or 按原文复用(by_src[u.source]) or 新建pending
```

实测：

```
幂等保留        35298 条
按原文复用       2840 条   ← 这部分工作被救回来了
重写后          45572 条（= units）
有译文          38138 条 (83.69%)
```

### 覆盖率的正确算法

```
✗ 有译文的行数 / unit 数          → 会 > 100%，把孤儿算成成绩
✓ 有译文的 unit 数 / unit 数      → 上界正好 100%
```

> **判据**：覆盖率这类"进度指标"必须**以目标集合为分母**遍历，
> 不能以"已完成集合"为分子去数。分母错了，指标就会超过 100% ——
> **指标超过 100% 本身就是 bug 的信号**，不要把它当"超额完成"。
> 另外：换 UID/主键方案时，旧数据要么迁移要么显式丢弃，
> **不能让它留在原地继续被计数**。
